# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this repo is

The **Tool Proxy** (this repo) is a customer-side **MCP connector**: a process that runs behind a customer's firewall, dials out to a controller URL via WSS, advertises locally-installed MCP servers as a `ToolManifest`, and dispatches inbound `tools/call` requests.

Tool Proxy is **not** a generic MCP framework. **Not** an agent. **No LLM lives here.** The connector is a tool dispatcher with policy.

The controller is **outside this repo** — this repo only ships the customer side.

## Topology — one connector, many MCPs

The repo ships **one connector binary** (`connector`) and MCPs under two roots:

- `customer-mcps/` — customer-authored (Type 1). Empty at ship time; customers populate via derived image or volume mount.
- `bundled-mcps/` — Twilio-authored bundles pre-installed in the connector image. Today: `agentic-memory` (Type 1 Node drop-in).

A single connector process: (a) reads `./connector.yaml` (resolved from CWD — repo root in dev, `/etc/tool-proxy/` or the customer's mounted config path in production) for yaml-managed MCPs; (b) auto-discovers customer-authored drop-in MCPs under `${MCP_DROPIN_DIR}/<name>/tools/*.ts` at boot or via runtime rescan; (c) receives a controller-pushed roster of Type 2 (3rd-party) MCPs over the WSS tunnel — where Twilio + Segment arrive today (see "v1.1 — 3rd-party MCP roster" in [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md)).

In production this is one container per `connector_id`; in dev, one local process.

In-repo demos: `examples/demos/sample/` (Type 1 drop-in — `now`, `slow_echo`, `uuid`, `weather`, plus prompts + resources), `examples/demos/crm/` (Type 1 drop-in — 9 tools incl. write endpoints, 3 prompts, 1 resource; consumes `examples/mock-backend/` via `MOCK_CUSTOMERS_URL`), `examples/demos/salesforce/` (Type 1 drop-in — 7 tools, 2 prompts, 2 resources; real Salesforce REST API access via OAuth 2.0 Client Credentials Flow, chosen over the official `@salesforce/mcp` package because that one persists auth to `~/.sfdx` and doesn't fit this connector's env-var creds pipeline). Same activation pattern as `sample`/`crm`: dev — symlink (or `cp -r`) into `customer-mcps/<name>` (gated, simulates the real customer drop-in flow); prod — the Dockerfile's `COPY examples/demos/salesforce bundled-mcps/salesforce` line ships it non-gated in the image, same as `sample`/`crm`. None of the three have any tracked presence under `bundled-mcps/` in the source repo — that path only exists inside the built image. Reference mock backend: `examples/mock-backend/` (Postgres-backed customer store, deploys as its own private-only Fly sibling app).

### Two MCP integration patterns

- **Type 1 (customer-authored, drop-in shape — default).** Folder under `customer-mcps/<name>/tools/` (and optionally `prompts/`, `resources/`) with `*.ts` files only. No `server.ts`, no `package.json`, no yaml entry, no `.env` (creds come from the controller). The drop-in scanner at [connector/src/dropin.ts](connector/src/dropin.ts) discovers the folder at boot; the synthesized child runtime at [connector/src/sdk/dropin-runner.ts](connector/src/sdk/dropin-runner.ts) wires each default-exported `Tool` / `Prompt` / `Resource` into a per-folder subprocess (`tsx dropin-runner.js` with `DROPIN_DIR=<folder> DROPIN_NAME=<name> PORT=<auto-assigned>`; auto-port probe from `MCP_BASE_PORT`, default 7100). Folder name = MCP name. Walkthrough at [docs/AUTHOR-LOCAL-MCP.md](docs/AUTHOR-LOCAL-MCP.md). Runtime refresh (no process restart): controller UI **Refresh local MCPs** → `local-mcps-rescan` frame → connector re-runs the scanner; loopback-only mirror at `/mcp/rescan-local` on the inspector. Drop-ins are **approval-gated** — the connector spawns and lists but withholds tools from the manifest until `mcp-enable` arrives (see approval gate under "Load-bearing properties").

  **Type 1 hand-written shape (legacy escape hatch).** Folder with its own `server.ts` (imports the SDK factory, lists tools, calls `createMcpHttpServer`) plus a yaml entry with `transport: http` + `dir:` + no `endpoint:`. Yaml + hand-written `server.ts` win over drop-in discovery for the same folder name. Stays available for Type 1 MCPs shipping their own `package.json` (third-party SDK that can't hoist to the workspace); no in-repo MCP uses it today. `MCP_DROPIN_DIR` defaults to `/var/lib/tool-proxy/customer-mcps/` in production; `scripts/start-connector.sh` exports `$ROOT/customer-mcps` for dev. Runtime rescan reconciliation lives in [connector/src/tunnel/local-mcps-coordinator.ts](connector/src/tunnel/local-mcps-coordinator.ts) — single-flight, filters by `source === "local"` so yaml + controller-config entries are immune. Since Phase 6 it adds a folder without starting it and detects code changes (see the approval gate block).

- **Type 2 (connect to existing MCP) — controller-pushed.** No yaml. The operator adds the MCP through the controller UI (Name, Transport, URL or command, Auth shape); the controller pushes it to this connector via `mcp-config-snapshot` / `mcp-config-delta` per [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) v1.1. The roster lives in connector RAM only (no yaml rewrite, no on-disk persistence — every **process restart** rebuilds from a fresh snapshot; WS reconnect is NOT a reset — see [`McpConfigCoordinator`](connector/src/tunnel/mcp-config-coordinator.ts)'s LIFETIME block). The supervisor + `servers/` connect path handle Type 2 entries identically whether they came from yaml (transitional) or the controller (target state). Auth on outbound HTTP-family calls is attached via `spec.headers`; stdio Type 2 entries receive creds via env, same as today.

The detection helper in [connector/src/config.ts](connector/src/config.ts) is `isType1Spawn(spec)` (http + dir + no endpoint). Don't widen it without thinking through the cross-product with `sameMcpServers`'s reconnect-comparison logic.

**Those two patterns are the whole model — there is no third.** Every MCP the connector runs is either a folder it spawns (Type 1) or an endpoint/command it dials (Type 2), and the difference is only *who owns the process*. Consequences worth internalizing:

- **Anything heavy belongs in an MCP, never in the connector.** A retrieval stack, an inference server, a document parser, a database driver — each lives in its own process behind one of the two patterns. The connector imports none of it. If a subsystem seems to need a special shape to fit, that is the signal it should be an MCP, not that the connector needs a new pattern.
- **Language is not a constraint.** Type 1 is Node-only because the connector spawns it with `tsx`; anything non-Node is Type 2, reached over streamable-http / SSE / stdio. A Python or Go service is a first-class MCP, just not a spawned one.
- **The customer owns their integrations.** Twilio ships the connector and the MCPs under `bundled-mcps/`; everything specific to a customer's data, corpus, or systems is theirs to author and run. A worked example of a subsystem in that shape — including the tool contract to implement — is [docs/KNOWLEDGE-MCP-INTERFACE.md](docs/KNOWLEDGE-MCP-INTERFACE.md).

## Architecturally load-bearing properties

- **Outbound-only.** The connector opens **no inbound ports** for the tunnel. It dials out; the controller pushes RPC requests back down the same WS the connector opened.

  Outbound is not the same as **direct**, and the difference is load-bearing on a network that mandates a forward proxy. `ws` drives its upgrade through `node:https`, which `NODE_USE_ENV_PROXY` does NOT reach (that wires undici, and undici doesn't sit under `node:https`), so [`connector/src/tunnel/proxy.ts`](connector/src/tunnel/proxy.ts) resolves `HTTPS_PROXY`/`NO_PROXY` itself and `client.ts` attaches an `HttpsProxyAgent`. Two things not to undo: **loopback is exempted independently of `NO_PROXY`** (folding it into the matcher would skip it whenever `HTTPS_PROXY` is set alone — the common case — and `CONNECT` our own children's `127.0.0.1:<port>/mcp` to the corporate proxy), and `HTTP_PROXY` is deliberately **not** applied to `wss://`. Reads existing standard env vars rather than adding config, because the `fetch` side of the connector's egress (OAuth mint, Type 2 endpoints) can honour the same vars through Node's own `NODE_USE_ENV_PROXY=1`. **The image does not set that flag today**, so that half stays unproxied by default — verified: `fetch` ignores `HTTPS_PROXY` without it. Consequence to keep straight: the static-bearer posture is fully covered by this change, but the **OAuth2 posture needs the flag as well**, because the mint runs *before* the dial in `connect()` and so fails first. With the flag set, the asymmetry this closes is the confusing one — the token mint SUCCEEDS through the proxy while only the tunnel times out, which reads as a broken controller rather than a network policy. Pinned by [`connector/tests/tunnel/client-proxy-dial.test.ts`](connector/tests/tunnel/client-proxy-dial.test.ts), which asserts a real `CONNECT` line reaches a fake proxy — a unit test on the resolver alone would stay green if the `agent` were dropped. TLS-intercepting proxies remain unhandled (needs `NODE_EXTRA_CA_CERTS`).

- **Spawned MCP children bind loopback only.** Every Type 1 child (bundled, drop-in, example) gets its HTTP listener from [`connector/src/sdk/http-server.ts`](connector/src/sdk/http-server.ts), which passes `LOOPBACK_BIND` (`127.0.0.1`) to `http.listen`. That is load-bearing, not incidental: `/mcp` carries the MCP's entire tool surface with **no authentication of any kind** — the trust boundary is per MCP *server*, i.e. which servers the customer runs, and nothing on the wire re-checks it — and `/envkeys` names the creds it wants. Omitting the host argument makes Node bind `::` (IPv6 wildcard, dual-stack), which puts that surface on the LAN in dev and on every sibling in the container's network namespace in production. Nothing needs the wider bind: `spawnChild` stamps `http://127.0.0.1:<port>/mcp` onto the spec and `fetchEnvKeys` derives its URL from that same endpoint. Don't drop the host argument and don't make it configurable. Pinned by [`connector/tests/sdk/http-server-bind.test.ts`](connector/tests/sdk/http-server-bind.test.ts), which asserts `handle.address` rather than probing binds — SO_REUSEADDR semantics differ between Linux and BSD, so a bind probe cannot discriminate portably. **Sibling reachability over loopback is NOT closed by this** — any child can still reach any other child's `/mcp`; see MCP-AUDIT #1a.

- **The pre-spawn port probe must test the same host the child binds.** `canBindLoopback` in [`port-allocator.ts`](connector/src/port-allocator.ts) probes `127.0.0.1`; the child binds `127.0.0.1` via `LOOPBACK_BIND`. Before the loopback fix those disagreed — the probe tested loopback while the child bound all interfaces, so a process holding `192.168.x.x:7100` left the probe reporting the port free and the child then failed `EADDRINUSE` at listen. Widening either side alone reopens that gap.

  **One `PortAllocator` per process, shared by every supervisor.** Probe-then-reserve runs inside a promise-chain mutex, so it is atomic across callers. Per-supervisor reservation sets (the old shape) were safe for one supervisor and racy for two: both could probe the same free port before either reserved it, and the second child failed `EADDRINUSE`. One workspace per tunnel (MULTI-PLATFORM-MCP Phase 6) means one supervisor per tunnel, so pass the same allocator to each via `SupervisorOpts.ports`; omitting it gives a private allocator (single-supervisor behaviour). Pinned by [`tests/port-allocator.test.ts`](connector/tests/port-allocator.test.ts).

- **One TunnelWorkspace per controller entry, sharing nothing mutable** (MULTI-PLATFORM-MCP Phase 6, D14). A connector process holds N `controllers[]` entries and runs one [`TunnelWorkspace`](connector/src/boot/workspace.ts) per entry: its own `TunnelClient`, reconnect controller, coordinators, `WebhookRegistry`, `Dispatcher`, `McpSupervisor` and children. The platform sees N ordinary tunnels and never learns they share a proxy (D13); every one registers with the process's single `proxyId`. [`boot/lifecycle.ts`](connector/src/boot/lifecycle.ts) is the process shell around them — store, inspector, health, machine API, signals, the shared scan and the one `PortAllocator`. Two consequences not to undo. **No map is re-keyed by `(controllerId, mcp)`**: each workspace keeps today's per-MCP-name keys, so a lookup that forgets the controller cannot exist. And **specs are cloned per workspace** (`structuredClone` on the way in): `spawnChild` writes `endpoint`/`__port` into the spec, so a shared spec object would let one workspace's child overwrite another's port. A workspace is identified by its entry `id` — adding an entry starts one, editing cycles it, removing stops it and deletes its storage, rotating its credential keeps it. Zero entries is N = 0, not a branch; that retired the old empty-store TDZ trap and its test (replaced by [`tests/boot/workspace-lifecycle.test.ts`](connector/tests/boot/workspace-lifecycle.test.ts)). Isolation is pinned with real children against two mock controllers by [`tests/boot/two-workspaces.test.ts`](connector/tests/boot/two-workspaces.test.ts).

  **A workspace is NOT an OS boundary, by decision (D15) — do not "fix" this with hardening defaults.** Every workspace runs as one uid in one network namespace, so a controller-pushed `stdio` entry can run any command, a pushed `http` entry can reach any sibling workspace's child on loopback (`/mcp` is unauthenticated; MCP-AUDIT #1a), and any child can read any workspace's `MCP_STATE_DIR`. That is accepted: the trust anchor is the proxy owner, who chooses which controllers' credentials to accept (D5, D9), and an owner who needs OS-level separation runs separate instances (Phase 3, [deploy/MULTI-INSTANCE.md](deploy/MULTI-INSTANCE.md)), which the OS isolates. Also accepted: one crash or OOM takes every workspace down, and every workspace runs the same image version (a controller refusing this proxy's `tunnelProtocol` is refused for that workspace only). The first consequence is why **an inspector route failure must never exit the process**: `startInspector` returns and catches every route promise, so a failing handler costs one request (500), not every tenant's tunnel — found when a single-controller-only store call threw inside a `void`ed handler on the first two-workspace run. Pinned by [`tests/inspector/route-failure-containment.test.ts`](connector/tests/inspector/route-failure-containment.test.ts).

  **`MCP_STATE_DIR` is a child's one write location** — `${CONNECTOR_STATE_DIR}/controllers/<entryId>/<mcp>/`, mode 0700, injected by the supervisor AFTER every user env layer so nothing can redirect it ([`boot/workspace-storage.ts`](connector/src/boot/workspace-storage.ts)). It nests inside the store's own directory, which the entrypoint already chowns, so it needs no new provisioning — and must not get a recursive chown. An entry id that is not a UUID is refused rather than joined into a path. agentic-memory reads it before `AGENTIC_MEMORY_STATE_PATH`, so each controller's memory lives in its own file.

- **Trust boundary is per MCP server, not per tool.** Every tool a server in `mcp_servers[]` exposes is forwarded to the controller. The customer controls *which* MCP servers run on their machine; that's the gate. The wire format keeps `ToolDescriptor.allowed` (controller may still display it) — the connector always sets it to `true`. Don't reintroduce per-tool `allow_list` without an explicit ask; it duplicated authority and forced a YAML edit on every new tool.

- **Manifest builds degrade per-MCP-server, not globally.** A single MCP's `tools/list` failure yields `tools: []` for that descriptor; the rest of the manifest still ships. Matches the existing `safeList()` behavior for prompts/resources/templates and the trust-boundary-is-per-server property. Enforced at [`connector/src/manifest/build.ts`](connector/src/manifest/build.ts); pinned by [`connector/tests/manifest/build-resilience.test.ts`](connector/tests/manifest/build-resilience.test.ts). Don't reintroduce a global `Promise.all` failure mode for any list method.

- **Every MCP the connector runs itself is gated by controller approval.** Bundled (Twilio-shipped, including the demos), customer drop-in and yaml-listed MCPs all ship **available but inactive** (decision D3, MULTI-PLATFORM-MCP Phase 2c). Since Phase 6 a gated child is **spawned lazily**, on that workspace's first `mcp-enable`; until then `mcp-discovered` describes it from the process-wide [`DiscoveryCache`](connector/src/boot/discovery-cache.ts), which spawns each folder once per content hash in a scratch supervisor (no controller env, throwaway state dir) and shares the result across workspaces — it describes code, not a tenant. A tool list that depends on creds is under-reported there; the real list ships in the manifest after enable. **Refresh is the change trigger** (plan §10 q6, hybrid): connect-time discovery stays, served from the cache, and the controller's **Refresh local MCPs** registers a NEW folder without starting it (described from the cache, started on enable) and detects a KNOWN folder whose code fingerprint (`folderFingerprint`) moved — a running child restarts (manifest-delta), one not running is re-described and announced with a second `mcp-discovered`, which the platform upserts. Pinned by the Refresh block in [`tests/boot/lazy-spawn.test.ts`](connector/tests/boot/lazy-spawn.test.ts). The child is started BEFORE the enable is handled, so the manifest-delta carrying its tools still precedes the ack. **`mcp-disable` does not stop the child**: [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) makes "no stop" part of that frame's contract (re-enable is sub-second), and a stop belongs to a future `mcp-stop` frame — the Phase 6 plan's "stop on disable" was not adopted for that reason. Lazy start alone bounds cost to what each tenant enabled. The controller operator's enable gesture flips tools in via `mcp-enable`, per proxy. **Only controller-pushed (Type 2) MCPs are not gated** — pushing one through the controller UI is already the operator's consent, so a second gate would be a double click. (Until Phase 2c only customer drop-ins were gated, with the predicate `author === "customer" && source === "local"`; yaml and bundled were pre-accepted.) The gated set is built per workspace as `gatedSpecsByName` in [`boot/workspace.ts`](connector/src/boot/workspace.ts) — distinct from `dropinSpecsByName`, which keeps its own jobs (author classification, `lookupSpec`) and is NOT the gate. The approved-set lives in connector RAM only — controller replays `mcp-enable` after every `register-ack` to restore state (decision D10). Don't add approval persistence to the state file — the controller is the source of truth by design. **Consequence:** after a restart every gated MCP is dark until the replay lands, one round-trip after `register-ack`; for bundled MCPs this is new.

  **`mcp-discovered` wire values (agreed with the platform):** `author: string` (`"twilio"` | `"customer"` today); `source: "bundled" | "dropin" | "yaml"`; `kind?: "example"`. The wire `source` is deliberately NOT the supervisor's internal `McpStatus.source`, which says `"local"` for both bundled and drop-in folders and cannot tell them apart. Pre-2c proxies sent the literal `"local"`; the platform accepts it as a synonym for `"dropin"`, and treats a connector as gated once it sends any of the three new values — so never emit `"local"` again. **A demo is marked by an `.example` file in its folder** ([`dropin.ts`](connector/src/dropin.ts) `EXAMPLE_MARKER`), because nothing else distinguishes one: the Dockerfile copies `examples/demos/*` into `bundled-mcps/` beside agentic-memory, so at runtime they are the same kind of thing. Every folder under `examples/demos/` carries the marker. Pinned by [`tests/boot/widened-gate.test.ts`](connector/tests/boot/widened-gate.test.ts).

  **The gate is enforced at every entry point, not just the manifest.** Withholding tools from the manifest is visibility, not access: a controller naming an unapproved drop-in directly in a `tools/call` used to reach it, because the `Dispatcher` checked only `servers.get`, and the aggregate `prompts/list` / `resources/list` iterated the raw `servers` map so an unapproved drop-in's prompts and resources leaked into them. One predicate, `isMcpEnabled` in [`boot/workspace.ts`](connector/src/boot/workspace.ts) (backed by `ApprovalCoordinator.isEnabled`), now gates four consumers: the `Dispatcher` (`isServerEnabled` — every per-server route treats an unapproved server as **absent**, same reply kind a non-existent server gets, so there's no existence oracle), `controller-call` (refused `403 mcp_not_enabled`), webhook **delivery** in `WebhookRegistry.dispatch`, and the inspector's own tool runner. **Webhook subscribe and allocate are deliberately NOT gated**: a child subscribes at spawn, before approval, and the SDK's `createWebhookEndpoint` rejects on a refused stream with no retry — gating there would break every webhook-using drop-in at boot. An unapproved MCP holds a URL but never sees a payload. Inside `Dispatcher`, every lookup goes through the private `server(name)` accessor; the one raw `servers.has` left is the `mcp_disconnected` check, which asks "is the child gone", not "is it enabled". Pinned by [`connector/tests/dispatcher/approval-gate.test.ts`](connector/tests/dispatcher/approval-gate.test.ts).

- **Schema declaration follows the trust boundary.** Tools we author or spawn (Type 1, whether customer-authored or Twilio-authored) declare `outputSchema` so controller-side procedure authors can write `{{ hydrate:<server>.<tool>.<field> }}` and have it type-checked. Tools we don't author (Type 2 externals) pass through verbatim — the controller handles missing schemas gracefully. The boot-time check at [`connector/src/manifest/validate.ts`](connector/src/manifest/validate.ts) logs `error` per offending Type 1 tool but does NOT throw — a missing schema is a per-tool bug, not a connector-wide failure. See [`connector/README.md`](connector/README.md) "Author a Type 1 MCP" for the six authoring rules.

- **WS-handshake auth is per-tunnel, controller-minted.** The connector sends `Authorization: Bearer <bearer>` and `X-Connector-Name: <name>` on the `/mcp-tunnel` upgrade. The bearer's ID prefix (`ts_tsec<rowId>_...`) locates the `tunnel_security_configs` row; the hash tail proves ownership. Mismatch → HTTP 401. Posture is DB-driven and mutually exclusive — boot fails if neither is configured. Header build at [connector/src/tunnel/client.ts](connector/src/tunnel/client.ts) branches:

  | Posture | Trigger | Rotation |
  |---------|---------|----------|
  | Static bearer (`ts_<rowId>_<random>`) | `oauth_client_id` unset | Row's **Rotate Secret** button, prior hash 24h grace |
  | OAuth2 `client_credentials` | `oauth_client_id` set | Connector mints 1h JWT, refreshes <60s before expiry; provider cached in [`auth/oauth-provider.ts`](connector/src/auth/oauth-provider.ts) survives WS reconnect |

  Twilio-takeover for OAuth2 deployments is `oauth_token_url` flip from controller to `https://oauth.twilio.com/v2/token` with no connector code change.

- **Identity established at WS register-frame time.** Separate from the handshake: once the WS is up, the connector sends a `register` frame and the controller binds the session to a `connectors` row. On first connect the row is minted using the resolved connector name and the controller returns a `registrationToken` in the register-ack. The connector persists that token to the sealed `registrationTokenCt` field of the store's controller record and presents it on every subsequent register frame. An unknown token is rejected (`unknown_registration_token`); the frame-router self-heals by clearing the token via the `onTokenCleared` callback (wired to `store.clearRegistrationToken`) and letting auto-reconnect re-mint. Identity + creds are configured entirely via the inspector's Configure Tunnel modal — no env vars.

- **No LLM, no agent loop, no document handling.** Unconditional, with no carve-out for any MCP shape. If you find yourself adding `openai`, a vector store, or a document parser to `connector/package.json`, stop: that work belongs in an MCP the connector *reaches over a transport*, not one it imports. The connector core is a dispatcher with policy and nothing else — the heavy, opinionated, customer-specific parts of any retrieval or inference stack are exactly the parts that must not ship from Twilio. [docs/KNOWLEDGE-MCP-INTERFACE.md](docs/KNOWLEDGE-MCP-INTERFACE.md) is the worked example.

- **Webhook ingress preserves the outbound-only invariant.** The public URL lives on the *controller* (`https://<controller-host>/api/webhook/<connectorId>/<token>`); the connector consumes events as `webhook` frames over the existing `/mcp-tunnel` WS. The connector opens **no** inbound port for webhook ingress, no per-MCP ngrok, no LB. Every webhook URL is bcrypt-protected per (connectorId, mcp); the URL prefix (rowId) is stable across reconnects but the random tail re-mints on every `webhook-allocate` — the connector pushes the new value to SDK consumers as a fresh `event: url` over the inspector loopback's SSE stream (see [`connector/src/tunnel/webhook-registry.ts`](connector/src/tunnel/webhook-registry.ts)). Don't reintroduce a per-MCP local listener for webhook delivery.

- **The inspector's message tap honours `policy.log_tool_args` only at `none`, deliberately.** The tap ([`servers/message-tap.ts`](connector/src/servers/message-tap.ts)) feeds the MCP Status message-history pane; the dispatcher renders the *same* arguments through `renderArgsForLog`. They disagree at the DEFAULT (`redacted`) and that asymmetry is the design, not an oversight: the log stream is durable and leaves the box, while the pane is in-memory, capped, cleared on restart, and loopback-only — and the pane exists precisely so a developer can see what went into a tool. Redacting at a setting nobody chose would delete the feature. `none` is the one setting honoured, because nobody reaches it by accident; `redactTapPayload` in [`policy/redact.ts`](connector/src/policy/redact.ts) blanks **request** payloads only, since the knob is named after arguments and makes no claim about results. The consequence — a credential passed as a tool argument is legible in that pane at the default — is stated in [docs/INSPECTOR.md](docs/INSPECTOR.md). Each entry's payload is additionally capped at 32 KB (`<elided: N bytes …>` above that) so the 500-entry ring is bounded by bytes and not by whatever the largest response happened to be. Pinned by [`connector/tests/inspector/message-tap-policy.test.ts`](connector/tests/inspector/message-tap-policy.test.ts).

- **Health endpoints are the ONE deliberately non-loopback listener, and they are a separate server.** `/livez` and `/readyz` live on `HEALTH_PORT` (default 9100) bound `0.0.0.0` — see [`src/health/server.ts`](connector/src/health/server.ts). They exist because **the inspector cannot be probed**: it binds `127.0.0.1` and refuses every non-loopback caller, so a kubelet / ECS agent / ALB probing the pod or task IP gets nothing. Measured in a real container: with the inspector's old `ports:` mapping, the host gets connection refused; widen `INSPECTOR_BIND_ADDR` and it answers `403 forbidden: loopback only`, because the gate judges the caller's source address and Docker's NAT rewrites it. Only a request originating *inside* the namespace returns 200.

  Splitting the inspector's bind by route was considered and rejected twice: one edit to that routing table would leak the rest of the dashboard. This server has exactly two GET routes, 404s everything else, and discloses a boolean plus a reason string — there is no third route for a mistake to expose, which [`tests/health/server.test.ts`](connector/tests/health/server.test.ts) asserts directly.

  **`/livez` must never consult the tunnel.** Liveness answers "restart this process", and during a controller outage the answer is no — gating it on the WS would make every orchestrator in the fleet kill its connector simultaneously, precisely when the decorrelated jitter in [`tunnel/reconnect.ts`](connector/src/tunnel/reconnect.ts) is trying to spread the herd out. `/readyz` does gate on it, plus config-loaded and children still starting, and reports the FIRST unmet condition — children before tunnel, because children come up first during a normal boot and reporting the downstream symptom would send an operator debugging their controller.

  Two consequences to internalise. **A fresh deploy is deliberately NOT ready**: `/readyz` is 503 `tunnel_not_open` until an operator completes Configure Tunnel, which is a human step — so every emitted manifest carries a long readiness grace, and liveness being separate is what keeps the process alive long enough to be configured. **Readiness aggregates across workspaces** (`workspacesHealth` in [`health/server.ts`](connector/src/health/server.ts)): a child a workspace was asked to run that is still starting gates it, summed over every workspace, but **no workspace's tunnel does** — under D5 one tenant's controller outage must not take the proxy out of rotation for the others. The one tunnel-shaped rule left is zero workspaces, which stays `tunnel_not_open`; a gated MCP nobody enabled is not "starting" and does not count. And **`permanently-failed` children do NOT gate readiness**: that state is terminal, so gating on it would hold a pod unready forever and hand the orchestrator a restart loop that cannot fix anything, while continue-on-fail means one broken drop-in must not take the deployment down. Only `restarting`/`stopped` count.

- **Inspector port is localhost-only and carries copy-able webhook URLs.** The inspector at `INSPECTOR_PORT` (default 9090) hosts both the operator UI *and* the SDK ↔ connector IPC routes (`/internal/webhook/stream`, `/internal/webhook/revoke`) used by bundled MCP children to subscribe to webhook events. The Webhooks panel exposes the full bcrypt-protected URL with a copy button by design. **Never bridge `INSPECTOR_PORT` to a public load balancer** — copying the URL out is intentional, and that URL *is* the secret.

- **Inspector session creds are loopback-only, in-memory, and write-only on the wire.** The routes `POST /mcp/session-creds-apply` and `POST /mcp/session-creds-clear` accept developer-pasted env values for an MCP; `GET /mcp/env-keys?mcp=<name>` lists declared key names (read-only, never values). Values land in the supervisor's private `entry.sessionEnv`, never persist to disk, never echo back through the loopback UI, and never cross to the controller. They expire 12h after paste (hard cap, not sliding-on-activity) — the supervisor's per-MCP `setTimeout` clears them and restarts the child without the value. Merge precedence is `process.env ⊕ spec.env ⊕ sessionEnv ⊕ controllerEnv` — controller wins per-key, session creds fill *gaps* the controller hasn't covered. There is no `GET /mcp/session-creds` and there never will be. Leak channels pinned by [`connector/tests/inspector/session-creds-leak.test.ts`](connector/tests/inspector/session-creds-leak.test.ts) and [`connector/tests/logger/redact.test.ts`](connector/tests/logger/redact.test.ts); pino has a `redact.paths` allowlist as runtime backstop. Customer-facing reference at [docs/INSPECTOR.md](docs/INSPECTOR.md) §"Right pane — MCP creds view".

## Wire protocol — frames

Wire-format authority: **the Zod schemas in [`protocol/`](protocol/), published as [`@gtmi/toolproxy-protocol`](https://www.npmjs.com/package/@gtmi/toolproxy-protocol)** (decision D7: the proxy owns the protocol; controllers depend on the package and never define frames of their own). [`docs/MCP-PROTOCOL.md`](docs/MCP-PROTOCOL.md) is the prose explanation — where the two disagree, the schemas win. [connector/src/tunnel/frames.ts](connector/src/tunnel/frames.ts) is still a hand-written TypeScript copy (interfaces, not Zod); [`protocol/tests/connector-parity.test.ts`](protocol/tests/connector-parity.test.ts) fails if its frame-type set drifts from the package's.

**Inbound frames are validated against the package, LOG-ONLY** ([`tunnel/client.ts`](connector/src/tunnel/client.ts) `handleMessage`). A frame that fails the schema fires `onschemaviolation` — logged at `warn` with the frame type and field **paths**, never values, since frames carry credentials — and is **still delivered unchanged**. That is deliberate for this rollout: strict validation against live traffic surfaces drift the hand-written types tolerated, and a tunnel that worked yesterday must not break on it. Verified 2026-10-09 against the live platform: zero violations. Making it enforcing is a later, separate step. Don't flip it by deleting the `onframe` call.

**Version handshake.** This proxy speaks protocol **3.x only** (hard cut, RENAME-TOOL-PROXY). `register` carries `tunnelProtocol` `"3.0"` (the package's `LATEST_PROTOCOL_VERSION`, `@gtmi/toolproxy-protocol` 3.0.0) and `proxyId`; it sends no `shimId` and there is no negotiating down. A controller that cannot speak 3.x refuses the register with `unsupported_tunnel_protocol`; `handleRegisterAckError` in [`tunnel/frame-router.ts`](connector/src/tunnel/frame-router.ts) logs both versions and suppresses auto-reconnect, so the fix is upgrading one side. Every tool and prompt name is `<proxyId>.<server>.<name>` ([`tunnel/naming.ts`](connector/src/tunnel/naming.ts)); a name carrying another proxy's id is refused as `tool_not_found`, and a bare name is `-32602`. The package still exports frozen `v1`/`v2` schemas for controllers serving older proxies, but this connector uses neither. A controller that echoes `register-ack.supportedTunnelProtocol` sets `TunnelClient.peerProtocol` via the frame-router's `onPeerProtocol`, and a newer minor of our major is then parsed tolerantly (unknown fields stripped). Absent → strict. Named `tunnelProtocol`, NOT `protocolVersion` — that is the negotiated MCP era on `ServerDescriptor`.

**The connector consumes `protocol/` through the npm workspace link, not the registry copy** — `npm` resolves `~1.0.0` to `"resolved": "protocol", "link": true`. The Dockerfile must therefore copy `protocol/` into the build stage AND `protocol/dist` + `protocol/package.json` into the runtime image: `node_modules/@gtmi/toolproxy-protocol` is a symlink to `../../protocol`, and without those lines it dangles and the connector fails at its first import. **Publishing:** `cd protocol && npm publish --access public`. `prepublishOnly` clean-builds and refuses to publish unless `dist/index.js` exists — a stale `tsconfig.tsbuildinfo` makes `tsc -b` skip emit after `dist/` is deleted, which produced a 2-file empty tarball on the first dry run. A published version can never be reused.

Frame categories:

- **Lifecycle**: `register` / `manifest-delta` / `rpc` / `heartbeat` / `goodbye`
- **Webhook ingress** (v1): `webhook-allocate` / `webhook-allocate-ack` / `webhook` / `webhook-revoke`
- **Creds** (v1): `creds-request` / `creds-response` / `creds-update` — `author` field is `"twilio"` for MCPs discovered under `MCP_BUNDLED_DIR`, `"customer"` otherwise
- **3rd-party roster** (v1.1): `mcp-config-snapshot` / `mcp-config-delta` / `mcp-config-ack` / `mcp-config-resync` — keyed by `mcpId`, connector-RAM-only, survives WS reconnect
- **Local rescan** (v1.2): `local-mcps-rescan` / `local-mcps-rescan-ack`
- **Server notifications** (v1.2 → superseded by §9.1/§9.4): the connector NO LONGER forwards raw `notifications/*`. Upstream `*/list_changed` re-lists → `manifest-delta`; `progress`/`message`/`resources/updated`/`cancelled` are consumed connector-side (no UI-only-controller consumer). `mcp-notification` stays a parseable frame type but is never emitted — the router lives in [`connector/src/tunnel/notification-forwarder.ts`](connector/src/tunnel/notification-forwarder.ts)
- **Approval gate** (v1.3): `mcp-discovered` / `mcp-enable` / `mcp-disable` / `mcp-enable-ack`

Backwards compat: an older controller that doesn't know `creds-request` triggers the 5s soft-wait timeout per MCP — the connector logs `warn` and falls back to `dir/.env`. WS stays open; not a fatal protocol error.

Inbound `tools/call` uses `name = "${proxyId}.${serverName}.${toolName}"` (the package's two-step parse). That split is why **no server name may contain a `.`, from any source**: one rule, [`identity/server-name.ts`](connector/src/identity/server-name.ts), is applied by the drop-in scanner, by `loadConfig` for yaml (boot error naming the rule), and by the mcp-config coordinator for controller-pushed Type 2 entries (per-MCP `skipped` ack with `invalid_server_name`, so one bad entry never blocks its siblings). Tool names may still contain dots — the tool is whatever follows the server. Previously only drop-ins were checked. Pinned by [`tests/config/server-name.test.ts`](connector/tests/config/server-name.test.ts) and the dotted-name case in [`tests/tunnel/mcp-config-coordinator.test.ts`](connector/tests/tunnel/mcp-config-coordinator.test.ts).

The dispatcher forwards beyond `tools/*`: `prompts/list`, `prompts/get`, `resources/list`, `resources/templates/list`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `completion/complete`, `logging/setLevel` all forward through `McpServerConnection`'s matching method. Routing: `prompts/get` mirrors `tools/call` (`${server}.${name}` qualifier); resource methods route by `params.serverName` with a fallback to URI scheme; aggregate `*/list` methods accept an optional `params.serverName` to narrow to one MCP; `completion/complete` and `logging/setLevel` REQUIRE `params.serverName`. `ServerDescriptor` carries optional `prompts[]` / `resources[]` / `resourceTemplates[]` / `capabilities` arrays — only populated when the upstream MCP advertised the matching capability — plus `protocolVersion` (§9.2: the negotiated MCP era string, e.g. `2026-07-28`, from `client.getNegotiatedProtocolVersion()`; present on the full manifest, i.e. the `register` frame, NOT in `manifest-delta`).

`webhook` frames share the WS with `rpc` traffic and `heartbeat`s. Three rules keep that mix safe:
- **No per-frame await.** The TunnelClient's `send()` is synchronous; webhook delivery doesn't block heartbeat scheduling.
- **No chunking.** Webhook frames are single JSON lines; the controller caps body at 256 KB (413 over) — that's also the implicit ceiling on tunnel frame size.
- **Webhook latency vs RPC latency.** Twilio's payment / status callbacks are not latency-sensitive. The controller is the synchronous HTTP responder — it returns 200 to the upstream immediately and forwards async over the WS.

Each `ServerDescriptor` in the manifest carries an `author: string` field — derived by the connector from the spec, never configured. Today's values: `"twilio"` for any MCP discovered under `MCP_BUNDLED_DIR` (the scanner stamps an `__author` marker), `"customer"` for everything else. The controller uses this to group MCPs in its UI. Type 2 (3rd-party) MCPs pushed by the controller arrive with `"customer"` and the controller does its own author-tagging server-side. Typed as `string` (not a union literal) so the controller forward-compats new author values without a wire-format break. Derivation in `authorOf(spec)` at [connector/src/config.ts](connector/src/config.ts), invoked once per server in [connector/src/manifest/build.ts](connector/src/manifest/build.ts).

Also on every dispatched `tools/call`: if the child MCP was closed under a live request (typical cause: supervisor restart triggered by `creds-update`), the dispatcher's catch block detects `!this.deps.servers.has(serverName)` and replies with `kind: "mcp_disconnected"` instead of the generic `tool_failed` — see [`connector/src/dispatcher.ts`](connector/src/dispatcher.ts). Lets the controller attribute the failure to a mid-flight restart rather than a genuine tool crash.

**A tool-level rejection is not a dispatch failure, and must not be converted into one.** When a child MCP rejects its arguments, the MCP SDK catches the zod failure and returns a *successful* JSON-RPC result carrying `isError: true` — `callTool` does not throw, so the dispatcher's catch block never runs. The connector relays that result **verbatim**: tool-level errors are meant to reach the controller's model, which reads the message and adapts. Rewriting them as `-32010` / `tool_failed` would collapse the distinction between "the tool ran and rejected the input" and "the transport died" — don't. The dispatcher inspects `isError` for **logging only**, emitting `tools/call <name> tool-error` instead of `ok` so a rejected call is distinguishable in the one durable record the connector produces (the result payload itself lives only in the capped, restart-cleared in-memory message tap). Error detail is deliberately omitted from that line — `isError` text often echoes arguments that `policy.log_tool_args` redacted. Pinned by [`connector/tests/dispatcher/tool-error-result-log.test.ts`](connector/tests/dispatcher/tool-error-result-log.test.ts), which asserts the reply stays a `result` with `error` absent.

## Workspace shape

npm workspaces, **two packages**: `@gtmi/toolproxy-connector` (`connector/`, private — ships only inside the OCI image) and `@gtmi/toolproxy-protocol` (`protocol/`, **published to public npm** — the tunnel wire protocol, which the connector consumes through the workspace link and controllers install from the registry). `protocol/` builds first (`tsc -b protocol connector`). It is the one deliberate exception to "nothing here is a library": it carries schemas, derived types and a parser, and no runtime behaviour.

**Module system: native ESM.** [connector/package.json](connector/package.json) declares `"type": "module"`; tsc emits `dist/**/*.js` as ESM (paired with `module: NodeNext` in [tsconfig.base.json](tsconfig.base.json)). Source files use `import`/`export` exclusively; relative imports MUST carry the `.js` extension (NodeNext requirement). For CJS-only ergonomics: use `createRequire(import.meta.url)` from `node:module` and `fileURLToPath(import.meta.url)` from `node:url` for `__dirname`/`__filename` equivalents. **Don't add `require()` calls or `__dirname` references in new code** — they fail at runtime under ESM.

Type 1 MCPs are **not** workspaces, but every one may carry a minimal `package.json` so it can grow third-party SDKs in isolation:

- **Framework deps (`zod`, `@gtmi/toolproxy-connector/sdk`)** are not listed per-folder. They resolve via Node's parent-dir walk to the workspace root `node_modules`, where npm hoists them once.
- **Third-party SDKs (`twilio`, `axios`, etc.)** are declared in the MCP's own `package.json` `dependencies` block and install into that folder's `node_modules`. They never hoist to the workspace root, so other MCPs can't accidentally `import "twilio"`.

A folder's `package.json` may have an empty `dependencies` block (or none at all) when it imports only framework deps. `scripts/start-connector.sh` runs `npm install --omit=dev` in any MCP folder whose `package.json` has a non-empty `dependencies` block but is missing `node_modules` — first-boot is one-shot. The Dockerfile mirrors the same loop at image-build time. Bumping a dep *version* in `package.json` while `node_modules` already exists is a case the auto-install doesn't catch — run `npm install` in that folder yourself.

Customers consume the OCI image, never the npm package. `connector/package.json` stays `"private": true` permanently; `bin`, `exports`, and `files` fields are retained because they're used by the `tool-proxy` CLI running *inside* the container and by the SDK re-export path for drop-in MCPs.

### Key modules

- **`connector`** — the customer-side process. Config, MCP clients to local servers, WSS tunnel, dispatcher, supervisor (Type 1 child supervisor + drop-in spawner + Type 2/3 connector), inspector UI, CLI (`start` / `discover` / `doctor` / `deploy` / `version` — there is no `init` or `register` subcommand; tunnel identity is configured only through the inspector's Configure Tunnel modal).
- **`connector/src/sdk/`** — the surface customer-authored Type 1 servers import. `Tool` interface (incl. optional `envKeys?: string[]`) + `createMcpHttpServer({name, tools, port?, envKeys?, capabilities?})` factory. Re-exported from `@gtmi/toolproxy-connector/sdk`, along with the empty-string-safe env readers `envString` / `envOptional` / `envNumber` — MCP authors must use those rather than `??`, since the connector-wide rule is "empty string == not set" and `??` treats `""` as set (see `docs/AUTHOR-LOCAL-MCP.md` authoring rule 8). The factory's HTTP server exposes `/envkeys` returning the de-duped union of every tool's `envKeys` (or the server-level list when `opts.envKeys` is set) — the supervisor queries it post-spawn so the connector can include it in `creds-request` frames. `capabilities?: Record<string, unknown>` is the seam for protocol extensions that need custom capability groups on the MCP `initialize` response (e.g. `bundled-mcps/agentic-memory` per [docs/AGENTIC-MEMORY-MOCK.md](docs/AGENTIC-MEMORY-MOCK.md)); custom shapes nest under the first-class `extensions` field (MCP `2026-07-28` — verified preserved through `getServerCapabilities()`) with a vendor namespace. (`experimental` still works for pre-2026 peers.) Drop-ins pick up an optional per-folder `capabilities.ts` (default-exported Record) via `loadCapabilities` in [`dropin-discovery.ts`](connector/src/sdk/dropin-discovery.ts).
- **`connector/src/sdk/dropin-runner.ts`** — synthesized child entrypoint for drop-in MCPs. Auto-discovers default-exported (or first-named-export-of-shape) `Tool` / `Prompt` / `Resource` objects from `${DROPIN_DIR}/{tools,prompts,resources}/*.{ts,js}` and calls `createMcpHttpServer(...)`. Discovery logic lives in [connector/src/sdk/dropin-discovery.ts](connector/src/sdk/dropin-discovery.ts) so it's unit-testable without spawning a real child process.
- **`connector/src/dropin.ts`** — `discoverDropins({ yamlNames })` scans `MCP_DROPIN_DIR`, returns synthesized Type 1 specs. Skips folders with a yaml entry or a hand-written `server.ts`. **Per-entry failures are isolated and discovery stays inside the root** (MCP-AUDIT #7/#31): `realpathSync`/`statSync` are wrapped per entry, so a dangling symlink skips *that entry* with a `warn` rather than throwing out of the scan — it previously took down the whole scan at boot AND on rescan, since neither call site wraps it, and the dev symlinks under `customer-mcps/` are absolute so a checkout move breaks all of them at once. A folder whose real path resolves outside the drop-in root is refused, so a symlink committed into a read-only production mount can't point discovery at a writable path; `MCP_DROPIN_ALLOW_SYMLINK_ESCAPE=1` opts out and `scripts/start-connector.sh` sets it because the documented dev workflow symlinks `examples/demos/<name>` in. A symlinked *root* is always fine (a volume mount often is one). Pinned by [`connector/tests/dropin/scanner-robustness.test.ts`](connector/tests/dropin/scanner-robustness.test.ts).
- **`connector/src/mcp-supervisor.ts`** — owns the lifecycle of every MCP child (Type 1 hand-written, Type 1 drop-in, Type 2 stdio, Type 2 http). Exposes `register(specs) / startAll() / restart(name, reason) / stopAll()`, applies controller-supplied env via `applyControllerEnv(mcp, env, source, reason)`, tracks per-MCP `McpStatus` (process / credsSource / credsLastUpdated / restartCount / lastRestartReason / toolsCount / **source** / **mcpId**), and mutates the SHARED `servers: Map<string, McpServerConnection>` so the dispatcher and inspector pick up new connections without re-wiring. **Before editing, read the invariant blocks in the source file** — spawn-mutation (`__port` gating in `stopEntry`), auth resolution ordering, `NODE_PATH` computed-once for drop-in spawns, sync-vs-async auth cache keying. `stopEntry`'s SIGTERM path logs a `warn` if the 2s SIGKILL fallback fires so operators can attribute a stuck restart.
- **`connector/src/tunnel/creds-coordinator.ts`** — fans out `creds-request` per MCP after register-ack, awaits the 5s soft-wait, applies responses via `supervisor.applyControllerEnv`. Late `creds-response` frames and `creds-update` push frames go through the same code path. Re-built per tunnel — the `pending: Map<requestId, …>` is pending IPC; a reply from a stale tunnel landing on a fresh one would be wrong.
- **`connector/src/servers/connect.ts`** — transport dispatch for outbound MCP connections. `stdio` specs go to `connectStdio`; `http` specs branch on the internal `__transportKind` marker: `"sse"` → `connectSse`, anything else → `connectHttp` (default). The wire-side `McpConfigEntry.transport` carries http / streamable-http / sse / stdio; the supervisor-side `McpServerSpec` stays two-valued (`http` / `stdio`) so the HTTP-family wire variants collapse to the `http` spec with the SUB-transport on `__transportKind`. Outbound clients set `versionNegotiation: { mode: "auto" }` — they speak `2026-07-28` when the upstream supports it and fall back to the 2025 handshake otherwise — and `inputRequired: { autoFulfill: false }` (§9.3: no MCP fulfiller exists in this system, so an `input_required` result surfaces as a typed `callTool` error → dispatcher `tool_failed`, rather than spinning `maxRounds` retries against absent handlers). On a modern connection the client opens a `subscriptions/listen` stream; the connector translates upstream `*/list_changed` into a `manifest-delta` (§9.1, debounced) instead of forwarding raw. **WebSocket was removed**: MCP SDK v2 dropped `WebSocketClientTransport` (WebSocket is not a spec transport), so a stale `websocket` entry from an older controller is rejected clearly in `connectServer` (non-fatal, continue-on-fail). The controller-side counterpart — removing WebSocket from the 3rd-party transport dropdown — lives on the controller (out of repo).
- **`connector/src/tunnel/mcp-config-coordinator.ts`** — in-memory roster of controller-pushed 3rd-party MCPs. Handles `mcp-config-snapshot` / `mcp-config-delta` / `mcp-config-resync` over the WS, translates `McpConfigEntry` → `SupervisedSpec`, reconciles via `supervisor.{hasEntry,registerOne,startOne,replaceSpec,unregister}`. Threads `mcpId` into `creds-request`. **Lifetime contract**: constructed once per workspace (in the `TunnelWorkspace` constructor — once per process before Phase 6), outlives that workspace's WS reconnects, rebound per tunnel via `bind({send, log?})` — see the source file's LIFETIME block.
- **`connector/src/tunnel/local-mcps-coordinator.ts`** — controller-triggered `local-mcps-rescan` + inspector loopback `/mcp/rescan-local`. Re-runs `discoverDropins({yamlNames})` and reconciles against supervisor entries filtered to `source === "local"`. Same lifetime contract as `mcp-config-coordinator.ts`. Single-flight; `onMcpAdded` fans out a `creds-request` for rescan-added MCPs.
- **`connector/src/dispatcher.ts`** — routes controller `rpc` frames to the right local MCP. On tool failure, distinguishes `tool_failed` (genuine crash / rejection) from `mcp_disconnected` (server was closed while awaiting the reply) via a check against the shared `servers` map.
- **`examples/demos/sample`** / **`examples/demos/crm`** — Type 1 drop-in demos.
- **`examples/mock-backend`** — Postgres-backed customer store consumed by the crm drop-in. Deploys as its own private-only Fly app. HTTP boundary is load-bearing — swapping Postgres for a real CRM (Salesforce / Zendesk / etc.) is a mock-side change; the drop-in stays a `fetch` client.
- **`bundled-mcps/agentic-memory`** — Type 1 drop-in (Node). Mock memory + identity provider. Wire-inventory + custom-capabilities envelope deviation at [docs/AGENTIC-MEMORY-MOCK.md](docs/AGENTIC-MEMORY-MOCK.md).

Type 1 servers use the MCP SDK v2 `createMcpHandler` (from `@modelcontextprotocol/server`) adapted to Node via `toNodeHandler` (from `@modelcontextprotocol/node`). It is **stateless** — a fresh `McpServer` per request, no `Mcp-Session-Id` — and serves MCP `2026-07-28` **and** the 2025-era protocol from one endpoint (createMcpHandler's default `legacy: 'stateless'`). The factory in `sdk/http-server.ts` is the one place this is set up; it also hosts the connector-specific `/envkeys` route alongside `/mcp`. Bundled + drop-in + example MCPs all flow through this factory, so they all serve the new protocol.

Tunnel identity + creds come from the sealed config store and are configured via the inspector Configure Tunnel modal. A credential that's set but doesn't match any controller row boots fine here and gets rejected at the WS handshake with HTTP 401 — that's a controller-side decision, not something we can detect locally before dialing.

Logging is **Pino** ([connector/src/logger.ts](connector/src/logger.ts)) — pretty-printed in dev TTY, raw JSON in non-TTY (CI / `> log.txt` / Docker). Set `LOG_LEVEL=debug` to raise verbosity. Every component (`connector`, `dispatcher`, `inspector`, each Type 1 MCP, `mock-customers`) gets a child logger via `createLogger('component')`. Type 1 MCP authors get the same logger via `import { createLogger } from "@gtmi/toolproxy-connector/sdk"`. Don't reintroduce `console.log` for runtime telemetry — CLI commands (`discover`, `doctor`, `deploy init`, `--help` / `--version`) are the only place direct stdout writes belong.

**Spawned children are piped, never `inherit`ed** (MCP-AUDIT #29). `spawnChild` uses `stdio: ["ignore", "pipe", "pipe"]` and `attachChildLogging` routes each line through the connector's logger — stdout at `info`, stderr at `warn`, with `mcp` / `stream` / `which` bindings for attribution and the (masked) line as the log **message** so pino-pretty stays readable in dev. `inherit` handed children the connector's own file descriptors, so uncaught stack traces, raw `process.stderr.write` (which `dropin-runner` itself uses), and upstream error bodies reached the log stream having passed through no connector code at all. Note what pino's `redact.paths` can and cannot do here: it censors whole **fields** by path, so censoring a free-text line field would blank the message rather than the secret inside it. The defence on free text is value-based — `secretValuesFor(entry)` collects the values the supervisor actually injected (`controllerEnv`, `sessionEnv`, `webhookToken`, plus `CONNECTOR_ONLY_ENV` values) and `maskSecrets` replaces them, longest-first. That covers an MCP echoing its own credential back in an error message; it cannot cover a secret the connector never knew. Blank lines are dropped, lines over 2000 chars truncated, and output is rate-limited to 200 lines / 10s per stream with a `suppressed` count logged rather than buffered. A child's own pino JSON is **unwrapped rather than double-encoded**: `parseChildRecord` lifts the child's `msg` to the record's message, keeps its remaining fields under `child`, and honours the level it chose (a child logging `error` on stdout still surfaces at `error`). Without that, every line from an SDK-logging child became a JSON string inside a JSON field — unqueryable in an aggregator and unreadable in dev. The pino-shape check (`level` and `time` both numeric) is what stops a child printing a bare JSON payload — a tool result, a config dump — from being mistaken for a log record. Masking runs on the raw text *before* the parse, so a secret is caught whether it sits in a field value or in free text. Pinned by [`connector/tests/mcp-supervisor/child-output-logging.test.ts`](connector/tests/mcp-supervisor/child-output-logging.test.ts).

## Inspector UI notes

The inspector lives inside the connector process at `INSPECTOR_PORT` (default 9090). It is part of the customer side; it does **not** proxy or impersonate the controller. **There is no admin login or session concept.** The operator dashboard (and every route except the one below) is loopback-only, unconditionally, forever — `127.0.0.1` / `::1` requests bypass the gate; every other route rejects a non-loopback caller outright, with no header, token, or opt-in that changes that.

The one exception is the machine API: `POST /oauth/token` (OAuth2 `client_credentials`, self-issued or federated) plus **three** JWT-bearer-gated `/v1/*` action routes — `POST /v1/outbound/calls` (triggers a real outbound Twilio call/message via `ControllerApiCoordinator` — see [docs/OUTBOUND-CALLS.md](docs/OUTBOUND-CALLS.md) §7), and the two that make up memory injection: `POST /v1/identity/list` and `POST /v1/memory/events` (see [docs/MEMORY-EVENTS.md](docs/MEMORY-EVENTS.md)). A fourth, `POST /v1/identity/find`, shipped briefly and was deleted when the controller merged that action into `identity.list` — its path is deliberately absent from the allowlist now, and pinned as rejected. All four become reachable non-loopback once an operator has, from that same trusted loopback session, either added at least one API client OR configured a federated trusted issuer — whichever happens first flips `network_access.enabled` and live-rebinds the listener (no restart); everything after is just another credential/config. Every one of them does its own bearer check inline; there is still no admin-session concept for any of them. **Each credential drives exactly one workspace** (Phase 6, [`boot/machine-api-routing.ts`](connector/src/boot/machine-api-routing.ts)): a self-issued token resolves through its API client's `controllerId`, a federated one through the entry whose trusted issuer matches its `iss` + `aud` — and that entry's JWKS verifies it, so forged claims only ever pick a JWKS the forger does not hold. A credential bound to a removed or unknown entry drives nothing. The same `iss` + `aud` on two entries is refused at configure time. The paths are unchanged, so `NON_LOOPBACK_ALLOWED_PATHS` and its exhaustive test are untouched. All three `/v1/*` routes are in `NON_LOOPBACK_ALLOWED_PATHS` (exact-match, deny-by-default — NOT a `/v1/` prefix rule; pinned exhaustively by [`tests/inspector/network-access-auth.test.ts`](connector/tests/inspector/network-access-auth.test.ts), so adding a path there without adding it to that test is how an operator-only route quietly becomes internet-reachable) and accept both self-issued (HS256) bearers from `/oauth/token` and federated (RS256) bearers once a trusted issuer is configured — `verifyAccessToken` dispatches by the token's own `alg` header, and each route reads the trusted-issuer config fresh from the config store per request (via `getVerifierConfig`), so an operator setting/clearing it live takes effect with no restart.

**Memory injection is resolve-then-write, and deliberately does not accept an address on the write.** `POST /v1/memory/events` ([`memory-events-route.ts`](connector/src/inspector/memory-events-route.ts)) takes `{agentId, identityId, event, occurredAt?, ttlSeconds?, idempotencyKey?}`, where `identityId` is an opaque controller handle from `POST /v1/identity/list` ([`identity-routes.ts`](connector/src/inspector/identity-routes.ts)). Two earlier shapes are retired — a nested `identity: {channel, value}` pair, then a flat `customer` string the controller resolved internally. That internal resolve was find-or-**create**, so a typo'd digit minted a phantom identity with a real working-memory row hanging off it, let an external caller grow the identity table at will, and failed *silently*. **Don't reintroduce address-shaped input on the write as a convenience.** The write targets the named agent's **working** memory, keyed `(accountId, agentId, identityKey)`, so `agentId` is required; both it and `identityId` resolve account-scoped, so a foreign or merged handle is `cross_account`, not `invalid_params`. No `channelId` — working memory is wire-blind. There is **no memory-tier selector and won't be** (working is the only tier with a legitimate external write; episodic rows are summariser-authored, semantic was retired controller-side) — a `type` field existed briefly and was cancelled outright, not deferred.

The `/v1/*` routes are deliberate mirrors of `outbound-calls-route.ts` — same bearer gate (three verbatim copies of `authenticate`; extracting a shared helper was deferred as out-of-scope), same `machine-api:<clientId>` audit identity, same `502`/`503` passthrough — differing only where the action contract forces it. **Unknown top-level body fields are rejected `400` rather than dropped** on all of them, mirroring the controller's `.strict()` schemas. Per-route deltas worth not re-litigating:

- **`/v1/memory/events`** — single wire action instead of a map; never mints an `idempotencyKey` (the controller doesn't dedup in v1 and a duplicate note is low-harm, unlike a double-dial); passes no `timeoutMs` (inherits the coordinator's 8s default — an identity resolve plus a row write, no LLM turn — rather than outbound's 30s). `ttlSeconds` is type-checked but **not** range-checked, because the controller's policy is asymmetric and a local copy would both drift and mispredict: values above 86400 are *clamped* (200 + a corrected `expiresAt`), while 0, negative, and fractional values are *rejected* with `invalid_params`. Guarded on `!== undefined` rather than truthiness, and that's load-bearing — a truthiness check would drop `ttlSeconds: 0`, silently substituting the 600s default instead of letting the caller learn the controller refuses it.
- **`/v1/identity/list`** — the only identity lookup, and both the browse call and the resolve call. `identifier` (renamed from `match`) is a case-insensitive **substring**, and an exact address is a substring of itself, which is why `identity.find` could be deleted. **The consequence is not just a renamed field:** a full address can match several rows (`des@example.com` also matches `des@example.com.au`), so nothing may take `identities[0]` as "the" resolve — callers disambiguate on each identity's full `aliases` set, and the connector passes the array through untouched rather than picking a winner. Exact-first-with-substring-fallback was rejected controller-side because a 1-element result would then be ambiguous between "exact hit" and "one substring hit". An empty `identities: []` is a **200**, never a 404, carrying the meaning `find`'s `identity: null` had — an unknown customer is a normal answer whose correct handling is `outbound.*` with the fact in `callContext`. `channel` is optional (it only narrows; `find` needed it required because its equality lookup ran against a kind-normalised column, and substring matching needs no kind) but still the one place a connector route enumerates a controller value rather than passing it through — `phone` | `email` | `webchat-uid`, because the set is closed and `test-harness` is a plausible caller guess the controller refuses; cost accepted is that a new kind needs a connector bump. `timeoutMs` is consumed route-side and **must never reach `params`** — the controller's schema is `.strict()` and explicitly refuses it, with tests pinning that on both sides. The retired `match` name is rejected `400` naming its replacement, not dropped, since silently ignoring it would run an unfiltered whole-account query while the caller believed they had narrowed it. No server-side cap and no cursor by controller design (a silent truncation can't be distinguished from "that's all of them"), so the connector must **never** substitute a default page size. The binding constraint is the clock, not payload size: defaults to 30s and accepts a caller `timeoutMs` clamped to 1000–120000. **Never add a retry on timeout** — there's no cancellation path, so the controller's query runs to completion and replies onto a discarded requestId; a retry loop stacks abandoned full-account scans on it while the caller sees only failures. Surface the timeout and say "raise `timeoutMs`". It is also the first machine-API route returning **bulk customer PII** rather than performing one targeted action — the blast radius of a leaked bearer is now "enumerate the customer base". That is *not* a reason to make it loopback-only (it's a remote API call by design; credential scoping is the lever that fits, and the controller's audit rows carry the returned row count so enumeration is detectable) — but weigh it before adding more read routes.

Federated config is a single unsealed `trustedIssuer` record (issuer/jwksUrl/audience — public IdP metadata, no allowlist); routes fold into `network-access-routes.ts` (`/internal/network-access/trusted-issuer[/clear]`). Full flow in [docs/INSPECTOR.md](docs/INSPECTOR.md#network-access) and [docs/NETWORK-ACCESS.md](docs/NETWORK-ACCESS.md).

Don't relax the bind to `0.0.0.0` any other way (env var, code change): the Webhooks panel exposes the bcrypt-protected URL by design, and only the machine-API rebind above pairs that widening with a real credential check — and even then, only for `/oauth/token`, never the dashboard. **Never bridge `INSPECTOR_PORT` to a public load balancer.**

**Reaching the dashboard on Fly is one command:** `./scripts/fly-inspector.sh <app>` (app defaults to the one in `deploy/fly/fly.toml`). It starts a relay INSIDE the Machine on a spare port, runs `fly proxy` to *that*, verifies the inspector answers 200 rather than 403, prints a URL, and tears both down on Ctrl-C with a 60-minute self-expiry. Use `http://` explicitly — Chrome's HSTS on localhost forces `https://`, which the inspector does not serve.

`fly proxy 9090:9090` **alone** returns 403: it arrives from the Machine's `fdaa:` mesh address, and `fly ssh` has no `-L`, so neither presents a loopback origin. The wrapper's relay is the missing hop. Note it *uses* `fly proxy` — the proxy is not the problem, the missing in-namespace hop is.

**A port-forward is the dashboard's access mechanism, not a convenience — and Fly has none.** Because the gate keys on the caller's address, reaching the dashboard remotely requires a forward that presents a genuine **loopback origin**: `ssh -L` (the remote sshd dials `localhost` itself), `kubectl port-forward` (enters the pod's netns), or `docker exec`. A forward that merely reaches the host's port from outside does not qualify, and `fly proxy` is exactly that case — it routes over Fly's 6PN mesh to the Machine's `fdaa:` address without entering its namespace, and `fly ssh` has no `-L`. So on Fly every dashboard route answers `403 forbidden: loopback only`, and since the Configure Tunnel modal is the ONLY way to set tunnel identity (no CLI subcommand, no env var), a fresh Fly deployment cannot complete first-connect until that hop exists. [`scripts/fly-inspector.sh`](scripts/fly-inspector.sh) supplies it — a relay inside the Machine forwarding to `127.0.0.1:9090` — and owns its teardown, because the relay launders the source address rather than authenticating and so exposes the dashboard to the org's private network for as long as it runs. Widening `INSPECTOR_BIND_ADDR` does NOT help and never did: the bind decides whether the process accepts the connection, the gate then judges where it came from. Those were the same thing only before the gate existed. Don't "fix" a Fly 403 by adding a path to `NON_LOOPBACK_ALLOWED_PATHS` or by trusting the 6PN range — peers and sibling machines are interleaved in the same `/64`, so no CIDR rule can admit an admin without admitting every app in the org.

**Two auth layers guard the inspector routes despite the loopback bind:**

1. **CSRF guard on every state-changing POST.** `guardCsrf(req, res)` requires `Content-Type: application/json` AND a custom `X-Inspector-Request: 1` header — either alone would still be a "simple request" per CORS, which any browser tab the operator has open could fire cross-origin. Content-Type validation alone forces preflight, and the custom header adds belt-and-braces. Pinned by [`connector/tests/inspector/csrf-guard.test.ts`](connector/tests/inspector/csrf-guard.test.ts).

2. **Per-MCP webhook token on `/internal/webhook/stream` + `/revoke`.** The supervisor mints `randomBytes(32).toString("base64url")` per MCP at `register()` and injects it as `MCP_WEBHOOK_TOKEN` in the child's env. The SDK's `createWebhookEndpoint` sends it as `Authorization: Bearer <token>`. Inspector's `authorizeWebhookMcp` constant-time-compares against `supervisor.resolveMcpByWebhookToken(token)` and requires the caller's token to identify them as owner of the requested `mcp`. Prevents same-container sibling drop-ins from eavesdropping on each other's webhook events. Pinned by [`connector/tests/inspector/webhook-stream-auth.test.ts`](connector/tests/inspector/webhook-stream-auth.test.ts).

Both layers are load-bearing — the loopback bind alone would let (a) any browser tab silently exercise POST routes, (b) any local drop-in subscribe to any other drop-in's webhooks. Also emitted on every static-asset response: `Content-Security-Policy` (strict, no `unsafe-eval`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`.

The left column is draggable; the width is persisted in `localStorage` under `inspector.leftColPx`.

## Config files

Runtime config is intentionally minimal. The connector's env-var surface is documented at [docs/ENV-VARS.md](docs/ENV-VARS.md).

**Tunnel credentials live in a sealed file.** Tunnel identity + creds live in a controller record inside `${CONNECTOR_STATE_DIR}/config.json` (default `/var/lib/tool-proxy/state/config.json`), each secret sealed at rest with libsodium `crypto_secretbox_easy`. The 32-byte master key comes from `CONNECTOR_KEY_FILE` (typically a K8s Secret / Docker Compose secret / Fly secret / cloud key-vault mount). Operators manage the record via the inspector's Tunnel panel — no shell access, no process restart on rotation. **An empty store at boot is a valid state**: the inspector renders "Configure tunnel" and no workspace exists until an operator submits the form. Since Phase 6 that also means **no MCP child spawns** with zero controllers — children belong to a workspace — which is a change from the single-tunnel shape, where MCPs spawned before any tunnel was configured. The store holds one entry per controller; `listControllers` / `addController` / `updateController(id)` / `removeController(id)` are the API, and the pre-Phase-6 `getController` / `upsertController` survive as single-controller shorthands that refuse to guess once there are several. API clients carry the `controllerId` they drive and the trusted issuer lives inside each entry; a pre-Phase-6 store binds both to its one controller at `open()`, exactly. Routes live in [`src/inspector/tunnel-routes.ts`](connector/src/inspector/tunnel-routes.ts).

This was Postgres until DB-TO-FILE, and the reason it no longer is, is worth keeping: `ENV-TO-DB` chose Postgres *because the enterprise-knowledge bundle already required one* — "zero new infrastructure". EK was later deleted and nobody revisited storage, leaving a database server to hold four secrets and under ten rows, and making it the single largest cost in every cloud deployment. Four properties are load-bearing in the replacement:

- **The store defaults to a SUBDIRECTORY of the state volume, not its root.** `writeDocAtomic` writes a sibling `.tmp` and renames, so it needs write permission on the containing directory; the volume root is deliberately left root-owned (see the entrypoint discussion under "Distribution"), and a mounted volume shadows whatever the image created. A store at the root boots fine under docker-compose — a named volume keeps the image's ownership — and fails `EACCES` on every cloud target. `entrypoint.sh` chowns `state/` alongside `agentic-memory/` and `customer-mcps/`; the agreement between the two files is pinned by [`connector/tests/deploy/entrypoint.test.ts`](connector/tests/deploy/entrypoint.test.ts).
- **The store carries the proxy's own identity, `proxyId`, and it is never silently re-minted.** 8 lowercase Crockford base32 characters ([`identity/proxy-id.ts`](connector/src/identity/proxy-id.ts)), minted by `emptyDoc`, back-filled once by `open()` for a store written before the field existed, and changed ONLY by the operator's `POST /internal/identity/regenerate` (loopback + CSRF, the fix for a cloned volume). It is distinct from the platform-minted `connectorId`, from each `controllers[]` entry's `id`, and from `keyFingerprint` (which changes on key rotation). It will name this proxy in every tool name it sends (MULTI-PLATFORM-MCP Phase 2b), so a silent re-mint would break every procedure ref with no error anywhere — which is one more reason the corrupt-file-throws rule below is load-bearing. **Deliberately not a version bump**: an older connector ignores the field, so a rollback still reads the store. Not secret and not sealed. A legacy `shimId` is read once on open, carried into `proxyId` with the same value, and dropped; it is never written again, so rolling back to a pre-rename connector would mint a new id. Pinned by [`tests/identity/proxy-id.test.ts`](connector/tests/identity/proxy-id.test.ts).
- **Writes are serialised through a promise-chain mutex** (`ConfigStore.mutate`), and the read happens INSIDE the lock. Postgres was arbitrating writes for us; two in-process writers exist (the inspector's routes, and the frame-router persisting a registration token after register-ack) and a whole-file read-modify-write can otherwise discard one. The queue swallows rejections so one failed mutation can't wedge every later write.
- **A corrupt or unparseable file throws; it never reads as a fresh install.** Reconfiguring over a store that still holds a recoverable registration token is worse than refusing to boot.
- **`open()` writes the initial document immediately** rather than lazily, so an unwritable directory fails at boot instead of on the operator's first Configure Tunnel submit. That lazy-failure shape is exactly what made agentic-memory's `EACCES` look like a healthy deploy.

**No TDZ discipline is needed any more, and that is by construction.** Before Phase 6 `bootFromDb` returned early on an empty store while closures wired above that return (the Configure Tunnel paste flow, the health state) could still fire, so every captured binding had to be hoisted above it or throw `Cannot access 'X' before initialization`; `tests/boot/lifecycle-tdz.test.ts` enforced that. Phase 6 removed the return: zero controllers is N = 0 workspaces, and every per-tunnel binding is a `TunnelWorkspace` field set in its constructor, so a closure cannot outrun its binding. The test was retired deliberately in the same commit; don't reintroduce an early return in `bootFromDb` that closures wired above it can reach.

|--------------|---------|
| `${MCP_BUNDLED_DIR}/<name>/tools/` | Twilio-shipped Type 1 drop-ins. Default `/app/bundled-mcps` in the image; dev overrides via `scripts/start-connector.sh`. Always on. |
| `${MCP_DROPIN_DIR}/<name>/tools/` | Customer-authored Type 1 drop-ins. Default `/var/lib/tool-proxy/customer-mcps/`. Approval-gated. |

The `controllers[]` entries (each with its own trusted-issuer config), the network-access flag, and the machine-API clients (each bound to one entry) — plus `keyFingerprint` (SHA-256 of the master key), which replaced the `encryption_meta` table and makes a wrong-key boot fail loudly instead of decrypting to garbage. The controller dispatches `/crelay` and `/mcp-tunnel` on a single port (default 3001), so one DNS entry / one ngrok tunnel covers both. `CONTROLLER_URL` is the HTTPS root; the connector internally upgrades `https://` → `wss://` and appends the `/mcp-tunnel` path in [connector/src/tunnel/client.ts](connector/src/tunnel/client.ts) before opening the socket.

**Optional yaml.** [`connector/src/config.ts`](connector/src/config.ts)'s `loadConfig` still parses a `connector.yaml` if one exists — its only remaining job is the hand-written Type 1 shape (an MCP shipping its own `server.ts`), which no in-repo MCP uses. Production customers using the derived-image or volume-mount delivery paths don't author yaml at all, and both in-repo yaml files now carry `mcp_servers: []`. When present, YAML `${VAR}` and `${VAR:-default}` interpolation apply; unknown vars without a default throw with the variable name and YAML line. Full-line yaml comments are treated as INERT by the interpolator so doc comments referencing `${CONTROLLER_URL}` don't hard-fail boot.

### Per-entry env precedence (subtle)

The highest-risk piece — read carefully before changing it. Four layers, lowest to highest precedence:

1. `dotenv/config` loads `./.env` (from CWD) once at startup → populates `process.env`.
2. `loadConfig` parses the yaml. Top-level `${VAR}` interpolation reads from `process.env` only. For each `mcp_servers[]` entry with `dir:`, the loader reads `<dir>/.env` into a **per-spec env map** (does **not** mutate `process.env`).
3. Inline `env:` map on the yaml entry (rare today; layered above `dir/.env`).
4. **Controller-supplied env from `creds-response` / `creds-update` frames.** The supervisor stores these in a per-MCP `controllerEnv` map and they win on conflict. See `mergeEnv` in [connector/src/mcp-supervisor.ts](connector/src/mcp-supervisor.ts) — merge order is `process.env ⊕ spec.env (yaml inline + dir/.env) ⊕ controllerEnv`.

Cross-entry leakage is impossible — child A's `API_TOKEN` (whether from `dir/.env` or controller-supplied) does not reach child B even if both declare the same key.

**Connector-only secrets are filtered out of layer 1.** `mergeEnv` skips `CONNECTOR_ONLY_ENV` (`POSTGRES_URL`, `POSTGRES_URL_TEMPLATE`, `POSTGRES_PW_FILE`, `POSTGRES_SCHEMA`, `CONNECTOR_KEY_FILE`, `CONNECTOR_KEY_B64`) when copying `process.env`. `CONNECTOR_KEY_FILE` is the only one `requireEnv()` demands now, and it is the libsodium master key that seals the config store. **The four `POSTGRES_*` entries deliberately remain** even though the connector no longer uses a database: the set is a deny-list for credential-shaped names, and deleting an entry can only ever *create* a leak path into child MCPs, never close one. A leftover `POSTGRES_URL` in an operator's environment is still a DSN, and still should not be inherited by a customer's MCP that didn't ask for it. Children run as the **same uid** as the connector (the entrypoint drops privileges once, before any spawn), so a child that learns the key path can read a mode-0400 key file and decrypt the tunnel bearer. **The filter is scoped to the inheritance layer only** — layers 2–4 may still set those keys, because there a value is a deliberate operator act and a customer MCP that genuinely wants its own `POSTGRES_URL` must keep working. Don't widen it into a blanket ban; pinned both ways by [`connector/tests/mcp-supervisor/env-inheritance.test.ts`](connector/tests/mcp-supervisor/env-inheritance.test.ts).

**Stdio entries go through the same merge.** The supervisor pre-builds merged env in `startEntry` and threads it through `connectServer(spec, env)` → `connectStdio(spec, env)` → `new StdioClientTransport({command, args, env})`. Same code path also decides restart-on-creds-rotation via `entry.child || entry.connection` — stdio entries leave `entry.child` undefined (the SDK owns the spawn), so the OR-clause is what catches them.

Per-spawn env-source telemetry: every spawn logs `mcp spawn env-sources` with `controller: [...]` and `dirDotEnv: [...]` — watch `dirDotEnv` trend toward `[]` as customers move creds into the controller (deprecation tracker).

Don't replace the per-spec env map with calls to `dotenv.config({path: ...})` in `loadConfig` — that mutates `process.env` and breaks the isolation guarantee. Don't widen the merge order without thinking through the cross-product with `applyControllerEnv` (which restarts the child with the new merged env).

### Env reading rule — empty string == not set

All `process.env` reads in `src/` go through [`src/env.ts`](connector/src/env.ts) (`envString` / `envOptional` / `envNumber`). The whole-module rule: **an empty-string env var is treated as "not set"** — fall back to the documented default. An admin who writes `FOO=` (blank line) in `.env` expects "leave this unset"; `??` previously let `""` flow through (`Number("")=0`, `resolve("")=cwd`, pino throws on empty level). `envNumber` additionally throws an admin-actionable error when set to a non-numeric value. The single deliberate exception is the YAML `${VAR}` interpolator in [`config.ts`](connector/src/config.ts), which substitutes the literal empty string.

Boot-time required-env preflight runs once in [`src/boot/require-env.ts`](connector/src/boot/require-env.ts) (`requireEnv()`) before yaml load or config-store open. It requires `CONNECTOR_KEY_FILE` and nothing else. One is the floor rather than a preference: the process needs the key to open the sealed store *before* it can serve the UI that supplies everything else. Tunnel identity, auth posture and controller URL all live in that store and are set via the inspector Configure Tunnel modal. A leftover `POSTGRES_URL` is inert — neither required nor rejected — so an upgrade doesn't fail on stale config; pinned by [`connector/tests/boot/require-env.test.ts`](connector/tests/boot/require-env.test.ts).

## Reconnect semantics

- WS close does **not** kill the connector process. It transitions the inspector to `closed` state and stops timers.
- Auto-reconnect is **on by default** (`policy.reconnect.enabled: true`). Per workspace: on unexpected close the `onclose` handler in [`connector/src/boot/workspace.ts`](connector/src/boot/workspace.ts) calls that workspace's `reconnectCtl.schedule()` and the inspector enters a `reconnecting` state showing "reconnecting in N.Ns · attempt K". A successful register-ack resets the attempt counter. SIGTERM/SIGINT and a manual click on the inspector's Reconnect button both cancel any pending auto-reconnect timer so a manual click fires immediately.
- Auto-reconnect is **suppressed when the controller rejects the register frame with a STICKY error** — `name_taken`, or any unrecognized code. `handleRegisterAckError` in [`connector/src/tunnel/frame-router.ts`](connector/src/tunnel/frame-router.ts) calls `reconnect.markRejected()`; the next `onclose` logs `auto-reconnect suppressed` and the inspector stays in `closed`. Recovery is via the inspector Reconnect button — the manual path clears the flag.
- **`unknown_registration_token` is the deliberate exception and does NOT suppress.** That branch clears the token (in memory, and on disk via `onTokenCleared` → `store.clearRegistrationToken`), leaves the rejected flag false so `onclose` schedules the next attempt, and the retry presents no token — which the controller treats as a first-connect and mints a fresh row. The operational consequence is the reason to keep the two apart: a controller **DB reset self-heals** across the whole fleet with zero human involvement, whereas a **partial restore** that leaves a `connectors` row still owning a connector's name collides on `name_taken` and needs an operator click per inspector. Pinned by [`connector/tests/tunnel/frame-router.test.ts`](connector/tests/tunnel/frame-router.test.ts) — don't hoist `markRejected()` to all error branches because two of the three do it.
- Backoff is **decorrelated jitter** (the AWS pattern), computed by `ReconnectController.nextDelay` in [`connector/src/tunnel/reconnect.ts`](connector/src/tunnel/reconnect.ts): each delay is drawn from `uniform(initial_backoff_ms, lastDelay * 3)`, capped at `max_backoff_ms`. Defaults are 1s / 30s with `max_attempts: 0` (infinite). It **re-draws from the floor each attempt** rather than climbing monotonically, so the very first redial is already spread across 1–3s and a fleet recovering from one outage does not resynchronize. Don't replace it with a flat or plain-exponential delay: the controller bcrypt-compares the tunnel bearer on every `/mcp-tunnel` upgrade **before** returning the 101, so a lockstep herd converts a controller restart into a self-inflicted CPU spike inside the connector's 10s `TunnelClient.DIAL_TIMEOUT_MS`. That cost lives in the controller repo and is invisible from here, which is why it's written down.
- Set `policy.reconnect.enabled: false` to opt out — useful in deployed containers where the orchestrator (Fargate / Container Apps / GKE) is the supervisor and you want the inspector to surface a hard `closed` state.
- Reconnect re-reads the YAML. `sameMcpServers()` in [`connector/src/boot/lifecycle.ts`](connector/src/boot/lifecycle.ts) (SIGHUP and the inspector Reconnect both reach it via `reloadConfig`) compares name + transport + endpoint + command + dir + env across the prior and new lists. If anything in `mcp_servers` changed, the connector logs a warning and uses the prior list (live MCP server reconnect is out of scope). `policy` changes take effect.

## Process lifecycle gotcha

`scripts/start-connector.sh` boots one connector process; the connector itself spawns Type 1 children. The script's pre-cleanup uses `pgrep -f 'scripts/start-connector\.sh'` and skips its own PID — do NOT replace this with `pkill -f` patterns that match `node dist/index.js`, because that catches unrelated node processes and does not catch orphan wrapper shells. The pgrep pattern must match the script's filename — if you rename the file, update the pattern in the same change.

The connector's SIGTERM handler stops every workspace (`Promise.allSettled`), and each calls its own `supervisor.stopAll()`, which sends SIGTERM to every Type 1 / drop-in / Type 2 stdio child it spawned (with a SIGKILL fallback after 2s + a warn log if the fallback fires). Combined with the script's `trap cleanup EXIT INT TERM` (which `kill 0`s the process group), Ctrl-C cleans up the whole tree.

## Distribution

Primary shape is a signed multi-arch OCI image. Build:

```bash
./scripts/build-image.sh                                # local single-arch
IMAGE=registry/tool-proxy:0.1.0 PUSH=1 ./scripts/build-image.sh  # multi-arch + push
```

[connector/Dockerfile](connector/Dockerfile) is two-stage (`node-build` → `runtime`); the runtime image carries the connector's `dist/` + `public/` + production `node_modules` (incl. `tsx`) + bundled MCPs. **Node only — no Python, no other language runtime.** Keep it that way: a non-Node MCP is a Type 2 entry reached over a transport, which needs nothing in this image.

**`/app` ships root-owned, deliberately** (MCP-AUDIT #3). `chown -R mcp:mcp /app` runs in the runtime stage BEFORE the `COPY --from=node-build` lines, and `COPY` defaults to `0:0` — so `/app/node_modules`, `/app/connector/dist` and `/app/bundled-mcps` are root-owned while the process runs as `mcp`. **Do not "fix" this by adding `--chown=mcp:mcp` to those COPY lines.** An immutable code tree is the stronger posture: children run as the same uid as the connector, so a writable `/app` would let a compromised child rewrite the connector's own `dist/` or a sibling MCP's tools and persist across a restart. The corollary is that **nothing may write inside `/app` at runtime** — anything needing persistence goes on the `/var/lib/tool-proxy` volume. The one violation (agentic-memory's state file, which resolved relative to its own module and so failed `EACCES` in the image while passing in dev) is now redirected there via `ENV AGENTIC_MEMORY_STATE_PATH`. Pinned by [`connector/tests/integration/agentic-memory-state-persistence.test.ts`](connector/tests/integration/agentic-memory-state-persistence.test.ts), which asserts the COPY lines carry no `--chown`.

**A mounted volume shadows the image directory, so the volume is provisioned at runtime.** The Dockerfile's `mkdir -p /var/lib/tool-proxy/customer-mcps` + `chown -R mcp:mcp /var/lib/tool-proxy` describe the *image*, and a volume mounted at that path discards all of it — Fly mounts it `uid: 0, gid: 0, chmod 0755`, and a K8s PVC or raw EFS mount behaves the same (a docker-compose *named* volume is the exception, since Docker seeds it from the image and keeps ownership, which is why this only bites the cloud targets). The connector then runs as `mcp` against a root-owned directory and cannot create anything in it. [`connector/entrypoint.sh`](connector/entrypoint.sh) therefore re-creates `agentic-memory/` and `customer-mcps/` and chowns them to `mcp` while it is still root, before the `su-exec`. Two properties are load-bearing: it must stay **above** the `su-exec` line (`chown` needs root, and below it the code still reviews as correct while doing nothing), and it must **not** be a `chown -R` on the volume root — the root stays root-owned for the same reason `/app` does, and a recursive chown would also rewrite a customer's read-only `customer-mcps` bind mount. Both commands tolerate failure, because a pre-provisioned or read-only mount is a valid setup and `set -eu` would otherwise kill boot. The failure this closes was **lazy**: `saveState` writes a sibling `.tmp` and renames, so a root-owned directory produced `EACCES` on the first memory write, not at boot — the deploy looked healthy. Note the entrypoint can only create these **empty**; it cannot restore content a derived image COPYed into the mount, so [deploy/DERIVED-IMAGE.md](deploy/DERIVED-IMAGE.md)'s masking pitfall still stands for customer MCPs. Pinned by [`connector/tests/deploy/entrypoint.test.ts`](connector/tests/deploy/entrypoint.test.ts).

**Runtime UID: non-root `mcp:mcp`.** The entrypoint runs as root long enough to `chown` the master-key file, then drops via `su-exec mcp:mcp`. `CONNECTOR_KEY_B64` is `unset` before the exec so it doesn't leak into `/proc/1/environ`. If a customer mounts `/var/lib/tool-proxy/customer-mcps/` from the host, the mount must be readable by UID `mcp`. Base images are pinned to `@sha256:...` digests — a Dockerfile FROM line without a digest is a security-hardening regression; pinned by [`connector/tests/security/hardening.test.ts`](connector/tests/security/hardening.test.ts).

Customers extend the image via one of two first-class delivery paths, both landing at `MCP_DROPIN_DIR` (`/var/lib/tool-proxy/customer-mcps/`) and the same discovery code in [`src/dropin.ts`](connector/src/dropin.ts):

- **Derived image** — `FROM ghcr.io/twilio-demos/tool-proxy:1.0` + `COPY ./my-mcps/ /var/lib/tool-proxy/customer-mcps/`, build their own image. Enterprise-friendly. Walkthrough: [deploy/DERIVED-IMAGE.md](deploy/DERIVED-IMAGE.md).
- **Volume mount** — bind-mount a host / K8s PVC / Fly volume / EFS at the same path. Faster dev loop, unlocks the "Refresh local MCPs" hot-rescan feature. Walkthrough: [deploy/VOLUME-MOUNT.md](deploy/VOLUME-MOUNT.md).

There is no "customer imports the npm package into their own Node service" path — the connector is a daemon, not a library.

[scripts/build-image.sh](scripts/build-image.sh) defaults to `linux/amd64,linux/arm64` (Graviton + ARM Macs). Per-cloud guides at [deploy/](deploy/) (AWS Fargate, Azure Container Apps, GCP GKE, Fly.io) document the foot-guns — most importantly, **don't put a load balancer in front of the connector** (nothing inbound) and **don't use Cloud Run / App Service / Fly `auto_stop_machines` / scale-to-zero anything** (kills the WSS). **Sizing is the third foot-gun**: each Type 1 child is three processes because `tsx` spawns a wrapper `node`, the real `node`, and a resident esbuild service, so the four bundled demo MCPs plus the connector measure **493 MB** in use (vs 412 MB with only three of them up). A 512 MB host offers 459 MB usable and so cannot boot the shipped image at all — the fourth child stalls on allocation and dies at the readiness probe with no output, which reads like a broken MCP rather than an undersized host, and `MCP_READINESS_TIMEOUT_MS` does not help because the memory is absent rather than late. Budget **1 GB minimum**; pinned for the Fly target by [`connector/tests/deploy/scaffold.test.ts`](connector/tests/deploy/scaffold.test.ts).

The runtime `ENTRYPOINT` is a shell script at [`connector/entrypoint.sh`](connector/entrypoint.sh). If `$CONNECTOR_KEY_B64` is set (Fly.io, ACA, or any secret-store-as-env platform), it base64-decodes into `$CONNECTOR_KEY_FILE` (default `/etc/tool-proxy/connector.key`) with mode 0400, then execs `node dist/index.js "$@"`. If `$CONNECTOR_KEY_B64` is unset (docker-compose, K8s Secret volume, hand-provisioned VM), it's a strict no-op. Pinned by [`connector/tests/deploy/entrypoint.test.ts`](connector/tests/deploy/entrypoint.test.ts). Don't add validation logic in the entrypoint — that's the connector's env-loading path's job.

## Deployment scaffolding

Three complementary shapes ship alongside the OCI image:

- **`deploy/compose/docker-compose.prod.yml`** — single-VM shape, `docker compose up -d` to a running connector. **One service**: the sibling Postgres, its `pg_password` secret and the `POSTGRES_URL_TEMPLATE`/`POSTGRES_PW_FILE` plumbing are gone. **The `127.0.0.1:9090:9090` port binding is load-bearing** — binding the inspector to `0.0.0.0` leaks the bcrypt-protected webhook URL. Pinned by [`connector/tests/compose/compose-lint.test.ts`](connector/tests/compose/compose-lint.test.ts).
- **`tool-proxy deploy init --target {fargate|aca|compose|fly|fly-mock}`** — CLI verb that renders the target's manifests. Kubernetes is served by the Helm chart, not a target here. Templates in [`src/deploy/templates.ts`](connector/src/deploy/templates.ts). The `fly` target's fly.toml deliberately has NO `[[services]]` / `[http_service]` / `auto_stop_machines` — pinned by [`connector/tests/deploy/scaffold.test.ts`](connector/tests/deploy/scaffold.test.ts) via line-start regex.
- **Reference bundles** — [`deploy/fly/`](deploy/fly/README.md) ships `fly.toml.example` + a full operator runbook.
- **IaC modules** — [`deploy/terraform/aws-fargate/`](deploy/terraform/aws-fargate/README.md) and [`deploy/helm/tool-proxy/`](deploy/helm/tool-proxy/README.md). Both hardcode `replicas: 1` / `desired_count: 1` — dup-name guard, don't template that.

`tool-proxy deploy apply --target fly` pairs with `deploy init`. Under the hood, `apply` spawns Fly's CLI directly — **four** commands with idempotency guards (see [`src/deploy/apply.ts`](connector/src/deploy/apply.ts)). It was five: `fly postgres create` + `attach` went away with DB-TO-FILE, and with them the only non-idempotent step, the only step that provisioned a second billable app, and the `<app>-db` name a second connector in the same org would have collided on. `spawn` is DI'd for test injection (native ESM blocks `vi.spyOn` on `child_process.spawnSync`). Other targets return "not yet implemented" from `apply`; operators use the cloud's native tool (`aws` / `kubectl` / `az` / `docker compose`) per the init README appendix.

**There is no CI/CD — the Twilio-demo Fly deploy is local-only.** GitHub Actions is disabled on the repo (`actions/permissions` → `enabled: false`, last run 2026-08-12), so pushing to `main` deploys nothing and runs no checks. Deploy by hand: `npm run build && (cd connector && npm test)`, then `./scripts/deploy/fly-deploy.sh --redeploy-only --skip-build` (`--redeploy-only` skips the one-time apps/secrets/volumes bootstrap; see the script header). The workflow files under [`.github/workflows/`](.github/workflows/) are dormant: do not count on them, and do not treat a push as a deploy. `tests/iac/terraform-helm.test.ts`'s `terraform validate` cases can exceed vitest's 5s default locally; if they are the only failures, re-run that file with `--testTimeout=60000` before calling the suite red. **Customer connectors deploy release-driven via `tool-proxy deploy apply`** (versioned OCI images + IaC modules), never push workflows.

**Every target that can carry a probe now probes `/readyz`, not the inspector.** Helm gets `livenessProbe: /livez` + `readinessProbe: /readyz` via `httpGet` on a named port (it had **no** probes before); Fargate and the Terraform module use a `CMD-SHELL` exec against `127.0.0.1:9100/readyz` because a task with no load balancer has no other mechanism; ACA gets native Liveness/Readiness blocks. The old probe hit the inspector's `/`, which only proved the HTTP server answered and could not distinguish a connector with no controller from a healthy one. `startPeriod`/`failureThreshold` are deliberately generous — `/readyz` stays 503 until Configure Tunnel is done, and a short grace kills the task before the operator reaches the modal.

`tool-proxy doctor` complements all three: run before boot to catch missing env, a bad key file, or a config store the process cannot use. Its `config-store` check replaced `postgres-url` and covers the four states worth distinguishing before boot: **absent file in a writable directory** is `ok` (it will be created at boot); **unwritable directory** is `fail`, which is the one that used to surface only as a crash-loop on a cloud volume; **unparseable file** is `fail`; and a **fingerprint mismatch** is `fail` naming a different master key, rather than letting the process decrypt to garbage. A key that cannot be resolved at all is `warn`.

Its `inspector-port` check distinguishes **self** from a genuine conflict: when the port is taken it asks the holder who it is, and a 200 carrying the dashboard title (or a 403 from the loopback gate — nothing else in this system answers that on `/`) reports `ok … already running`. Anything else stays a `fail`, deliberately, since a generous check would mask the collision the check exists for. Before this, running `doctor` inside a healthy container reported `FAIL` and exited 1, because the holder was the connector being checked.

Invoke it as `node dist/index.js doctor` inside the image, **not** `tool-proxy doctor` — WORKDIR is `/app/connector` and the workspace bin link at `/app/node_modules/.bin` is not on `PATH`, so the bare name fails with `not found`.
