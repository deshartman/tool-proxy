# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A customer-side **MCP connector**: a process that runs behind a customer's firewall, dials out to a controller URL via WSS, advertises locally-installed MCP servers as a `ToolManifest`, and dispatches inbound `tools/call` requests. Per the productized design in `MCP-TUNNEL.md` (held outside this repo).

**Not** a generic MCP framework. **Not** an agent. **No LLM lives here.** The connector is a tool dispatcher with policy.

## Topology — one connector, many MCPs

The repo ships **one connector binary** (`packages/connector`) and **MCPs** under `mcp/` — split into `mcp/local/` (customer-authored, Type 1) and `mcp/bundled/` (Twilio-authored, pre-installed in the connector image). Today the only thing under `mcp/bundled/` is `enterprise-knowledge/` (Type 3, Python venv stub) — the prior `mcp/bundled/twilio/` Type 1 bundle was removed 2026-06-30 once the standalone `@deshartman/twilio-mcp` + `@deshartman/segment-mcp` npm packages, loaded via the controller's "New 3rd Party MCP" flow, took over in production. Type 3 *source* lives at `bundles/<name>/` — deliberately outside `mcp/` so the runtime image only carries the installed venv (`/opt/bundled-mcps/<name>/.venv/`), not the build inputs (`pyproject.toml`, `src/`, `migrations/`). A single connector process: (a) reads `./connector.yaml` (resolved from CWD — repo root in dev, customer project root post `npm i`) listing any yaml-managed MCPs (today: just the `enterprise-knowledge` Type 3 entry); (b) **auto-discovers customer-authored drop-in MCPs** under `${MCP_DROPIN_DIR}/<name>/tools/*.ts` — these are NOT in the yaml; the scanner finds them at boot or via the W-L2 rescan; (c) receives a controller-pushed roster of **Type 2 (3rd-party)** MCPs over the WSS tunnel (see "v1.1 — 3rd-party MCP roster" in [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md)) — this is where Twilio + Segment now arrive. Yaml-listed MCPs are launched as Type 3 bundle entrypoints; drop-ins are spawned as Type 1 children via the synthesized `dropin-runner.js` entrypoint; controller-roster Type 2 entries are connected by the supervisor in-memory and never appear in the yaml. In production this is one container per `connector_id`; in dev it's one local process.


Sample tools (ships with the repo, `mcp/local/sample/`): `now`, `slow_echo`, `uuid`, `weather`. Dev-only drop-ins (gitignored, restored from history when needed for manual testing — see "Dev-only scaffolding" below): `mcp/local/crm/` exposes `get_customer`, `get_recent`, `issue_refund`, `check_availability`, `get_appointment`, `update_appointment`, `notify_agent` against the local `mock/customers/` service. Aviation-weather (Type 2 stdio): `wx_metar`, `wx_taf`, `wx_pireps`, `wx_sigmets`, `wx_icon_d2`, `wx_outlook`, `wx_preflight`, `wx_route`. Twilio + Segment now arrive as Type 2 controller-config entries from the standalone `@deshartman/twilio-mcp` + `@deshartman/segment-mcp` packages — the operator wires them through the controller UI's "New 3rd Party MCP" flow and the controller pushes them via `mcp-config-snapshot`. Enterprise Knowledge (Type 3 bundled stub): `sources_register`, `sources_fetch`, `sources_refresh`, `knowledge_query`.

The controller is **outside this repo** — this repo only ships the customer side.

### Three MCP integration patterns

- **Type 1 (customer-authored, drop-in shape — default).** Folder under `mcp/local/<name>/tools/` with `*.ts` files only. No `server.ts`, no `package.json`, no yaml entry, no `.env` (creds come from the controller). The drop-in scanner at [packages/connector/src/dropin.ts](packages/connector/src/dropin.ts) discovers the folder at boot, and the synthesized child runtime at [packages/connector/src/sdk/dropin-runner.ts](packages/connector/src/sdk/dropin-runner.ts) wires each default-exported `Tool` into a per-folder subprocess (`tsx dropin-runner.js` with `DROPIN_DIR=<folder> DROPIN_NAME=<name> PORT=<auto-assigned>`; auto-port probe from `MCP_BASE_PORT`, default 7100). Folder name = MCP name. `mcp/local/sample/` is the live drop-in demo — no `server.ts`, no `package.json`, no yaml entry. Walkthrough at [docs/AUTHOR-LOCAL-MCP.md](docs/AUTHOR-LOCAL-MCP.md). Runtime refresh (no process restart) is W-L2: controller UI **Refresh local MCPs** button → `local-mcps-rescan` frame → connector re-runs the scanner; same operation is exposed loopback-only at `/mcp/rescan-local` on the inspector. **Approval gate (v1.3+, branch `feature/mcp-creds-config`):** drop-ins do NOT auto-enable. The connector spawns the child and lists tools as before, but **withholds the tools from the manifest** and emits an `mcp-discovered` frame to the controller. Operator clicks Approve in the controller UI (with optional inline `envKeys` paste) → controller sends `mcp-enable` → connector adds tools to `manifest-delta`. Approval state lives **controller-only** (replayed via `mcp-enable` on every `register-ack`; connector keeps no approval persistence). Disable is manifest-visibility-only (child keeps running). Gate predicate: `author === "customer" && source === "local"`. Yaml-listed Type 1 hand-written, Twilio-bundled, and 3rd-party MCPs are NOT gated. See [.claude/plans/MCP-CUSTOM-APPROVAL.md](.claude/plans/MCP-CUSTOM-APPROVAL.md) and [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) §"v1.3 — Customer drop-in approval gate".

  **Type 1 hand-written shape (legacy escape hatch).** Folder with its own `server.ts` (5 lines: import the SDK factory, list tools, call `createMcpHttpServer`) plus a yaml entry with `transport: http` + `dir:` + no `endpoint:`. Yaml entries and hand-written `server.ts` files win over drop-in discovery for the same folder name. The supervisor runs `tsx <dir>/server.ts` with the same auto-port shape. New customer-authored MCPs should use the drop-in shape; the hand-written shape stays available as an escape hatch for a Type 1 MCP that needs to ship its own `package.json` (e.g. a third-party SDK that can't hoist to the workspace), but no in-repo MCP uses it today.
  - **Drop-in details.** The runner reads `DROPIN_DIR` / `DROPIN_NAME` from its env, scans `tools/*.{ts,js}`, picks each module's default export (fallback: first named export with a Tool shape), and calls `createMcpHttpServer({name, tools})`. `MCP_DROPIN_DIR` defaults to `/var/lib/mcp-connector/customer-mcps/` in production; `scripts/start-connector.sh` exports `MCP_DROPIN_DIR=$ROOT/mcp/local` for dev. The scanner skips folders that already have a yaml entry (yaml wins) or a hand-written `server.ts` (author intent). Runtime rescan goes through [packages/connector/src/tunnel/local-mcps-coordinator.ts](packages/connector/src/tunnel/local-mcps-coordinator.ts) — single-flight, reconciles by diff against `supervisor.statusList()` filtered to `source === "local"` so yaml + controller-config entries are immune. See [.claude/plans/Done/MCP-LOADING-LOCAL.md](.claude/plans/Done/MCP-LOADING-LOCAL.md).
- **Type 2 (connect to existing MCP) — controller-pushed.** No yaml. The operator adds the MCP through the controller UI (Name, Transport, URL or command, Auth shape); the controller pushes it to this connector via `mcp-config-snapshot` / `mcp-config-delta` per [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) v1.1. The roster lives in connector RAM only (no `connector.yaml` rewrite, no on-disk persistence — every **process restart** rebuilds it from a fresh snapshot). **WS reconnect is NOT a roster reset:** the [`McpConfigCoordinator`](packages/connector/src/tunnel/mcp-config-coordinator.ts) is constructed once per connector process (in `boot()`, alongside the supervisor it tracks); per-tunnel rebind goes through `mcpConfig.bind({send})` which only swaps the wire `send` callback and cancels any in-flight snapshot-wait timer. Roster + `lastAppliedGeneration` survive WS reconnect by design — see the LIFETIME comment in that file for the 2026-06-21 manual repro this prevents (false `name conflict with yaml entry "X"` error after reconnect because the per-tunnel coordinator's `nameToMcpId` was empty but the supervisor still carried the prior session's entry). Don't refactor it back to per-tunnel construction without thinking through the cross-product with the supervisor's lifetime — they're a pair. The connector's existing supervisor + `servers/` connect path handle Type 2 entries identically whether they came from yaml (transitional) or the controller (target state). Auth on outbound HTTP-family calls is attached inside the connector via `spec.headers` (set by the auth-resolution helper from the controller-supplied creds env). Stdio Type 2 entries receive creds via env, same as today.
- **Type 3 (bundled, Twilio-authored Python venv, pre-installed in this image).** Yaml entry sets `bundled: <name>` plus an optional `dir:` (under `mcp/bundled/<name>/`) for a per-bundle `.env`. The connector resolves `bundled:` against `BUNDLED_MCPS` in [packages/connector/src/config.ts](packages/connector/src/config.ts) — a registry of bundles laid down at image-build time under `/opt/bundled-mcps/<name>/`. Resolution synthesizes a stdio spec, so the rest of the supervisor code is unchanged. Bundle source lives in **`bundles/<name>/`** at the repo root (separate from `mcp/` so the runtime image carries only the installed venv, not the build inputs); the connector's Dockerfile reads it during the bundle-build stage and `pip install`s it into the venv. Customer surface area: one yaml line + one `.env` file. No code, no `pip install` from the customer's side. Local-dev override: `BUNDLE_DEV_OVERRIDE_<UPPER_NAME>=/abs/path/to/launcher` redirects launch to a working tree (`scripts/start-connector.sh` auto-exports this for any bundle that ships a `dev-launch.sh`).

Note: a Twilio-authored MCP doesn't have to be Type 3. A Node MCP that needs a third-party SDK could live under `mcp/bundled/` *because Twilio ships it* and be wired as Type 1 (yaml entry has `transport: http` + `dir:` and no `endpoint:`). Type 3 is specifically the Python+venv shape — use it when the bundle has its own non-Node deps that can't (or shouldn't) be hoisted into the connector workspace. Today the only bundled MCP is `enterprise-knowledge` (Type 3); Twilio + Segment are Type 2 entries pushed by the controller, not bundled.

The detection helpers in [packages/connector/src/config.ts](packages/connector/src/config.ts) are `isType1Spawn(spec)` (http + dir + no endpoint) and `isType3Bundled(spec)` (stdio + bundled set). Type 3 resolution happens in `loadConfig` *before* the discriminated union parses, because `bundled:` entries have no `transport` field. Don't widen the classifiers without thinking through the cross-product with `sameMcpServers`'s reconnect-comparison logic — `bundled` is part of that equality check so an edit from `bundled: a` to `bundled: b` is detected even when both happen to resolve to identical commands.

### Adding a new MCP

Three surfaces, picked by who authors the MCP:

- **Type 1 (customer-authored)** → drop a folder at `mcp/local/<name>/tools/*.ts`. No yaml edit, no `server.ts`, no `package.json`. The connector's drop-in scanner picks it up at boot or via the W-L2 **Refresh local MCPs** button. Walkthrough at [docs/AUTHOR-LOCAL-MCP.md](docs/AUTHOR-LOCAL-MCP.md).
- **Type 3 (Twilio bundle)** → edit `./connector.yaml`. Set `bundled: <name>` against a bundle that's already registered in `BUNDLED_MCPS`; supply only a `.env` in `mcp/bundled/<name>/`.
- **Type 2 (3rd-party MCP)** → controller UI. Operator clicks **New 3rd Party MCP** in the controller (Name, Transport, URL or command, Auth shape, optional extra envKeys); controller persists + pushes via `mcp-config-snapshot` / `mcp-config-delta`. Connector reconciles in-memory and connects through the existing supervisor path. No yaml edit, no folder under `mcp/`.

## Architecturally load-bearing properties

- **Outbound-only.** The connector opens **no inbound ports** for the tunnel. It dials out; the controller pushes RPC requests back down the same WS the connector opened.
- **Trust boundary is per MCP server, not per tool.** Every tool a server in `mcp_servers[]` exposes is forwarded to the controller. The customer controls *which* MCP servers run on their machine; that's the gate. We deliberately diverged from MCP-TUNNEL.md §"Configuration surface" (which prescribes a default-deny `allow_list.tools` block) — per-tool gating duplicated authority and forced a YAML edit on every new tool. Don't reintroduce `allow_list` without an explicit ask. The wire format keeps `ToolDescriptor.allowed` (controller may still display it; future enterprise-strict mode might use it) — the connector always sets it to `true`.
- **Customer drop-ins gated by controller approval (v1.3+).** A drop-in folder under `${MCP_DROPIN_DIR}` is a *proposal*, not an *acceptance*. The connector spawns the child and lists tools, but withholds the tools from the manifest and emits `mcp-discovered`. The controller's operator approval gesture is what flips the tools into the manifest via `mcp-enable`. Two-key model: the customer admin's filesystem write access proposes; the controller operator's approval click accepts. Yaml-listed Type 1 / Type 3 / 3rd-party MCPs are NOT gated (yaml or controller-UI-authored = pre-existing acceptance). The approved-set lives in connector RAM only — controller replays `mcp-enable` after every `register-ack` to restore state. Don't add approval persistence to `.connector-state.json` — the controller is the source of truth by design. See [.claude/plans/MCP-CUSTOM-APPROVAL.md](.claude/plans/MCP-CUSTOM-APPROVAL.md).
- **Schema declaration follows the trust boundary.** Tools we author (Type 1 customer-side, Type 3 Twilio bundles) declare `outputSchema` so controller-side procedure authors can write `{{ hydrate:<server>.<tool>.<field> }}` and have it type-checked. Tools we don't author (Type 2 externals) pass through verbatim — the controller handles missing schemas gracefully on its end. The boot-time check at [`packages/connector/src/manifest/validate.ts`](packages/connector/src/manifest/validate.ts) logs `error` per offending Type 1 / Type 3 tool but does NOT throw — a missing schema is a per-tool bug, not a connector-wide failure (the rest of the manifest still works). The boot log is the runtime backstop; the prior per-tool test tree under `tests/mcp-tools/` was retired with the `mcp/bundled/twilio/` bundle on 2026-06-30. See [.claude/plans/OUTPUT-SCHEMA.md](.claude/plans/OUTPUT-SCHEMA.md) and [`packages/connector/README.md`](packages/connector/README.md) "Author a Type 1 MCP" for the five authoring rules.
- **WS-handshake auth is per-tunnel, controller-minted.** The connector sends two headers on the `/mcp-tunnel` upgrade: `Authorization: Bearer <bearer>` and `X-Connector-Name: <CONNECTOR_NAME>` (the lookup key — must match the row's Name field exactly, case-sensitive). The controller looks up the `tunnel_security_configs` row by `(tenant_id, name)` and verifies the bearer; mismatch = HTTP 401. The legacy single-shared `TUNNEL_AUTH_TOKEN` env var on the controller is gone — every connector needs its own row, minted by an operator in **Tools → Connectors → Tunnel Security**. Two postures, picked per row:
  - **Long-lived `ts_<rowId>_<random>`** — operator pastes Twilio AccountSid + AuthToken (or AccountSid + ApiKey), the controller verifies against Twilio's API at create time, then mints + bcrypt-stores the secret. Customer pastes the plaintext (shown once) into `TUNNEL_AUTH_TOKEN`. Rotate via the row's **Rotate Secret** button — the previous hash stays valid 24h via `secret_rotation_grace_until`. Connector code path: header build at [packages/connector/src/tunnel/client.ts:65-69](packages/connector/src/tunnel/client.ts#L65-L69) takes the static `authToken` branch.
  - **OAuth2 `client_credentials`** — same row-creation flow, but the controller hands back `client_id` + `client_secret` instead. Customer pastes them into `OAUTH_CLIENT_ID` / `OAUTH_CLIENT_SECRET` and sets `OAUTH_TOKEN_URL`. The connector POSTs `grant_type=client_credentials` to `OAUTH_TOKEN_URL` to mint a 1h JWT, caches it (refreshes <60s before expiry), presents it as the WS-upgrade bearer. Code path: [packages/connector/src/auth/oauth-provider.ts](packages/connector/src/auth/oauth-provider.ts) is constructed once in `main()` when `OAUTH_CLIENT_ID` is set, passed into every `new TunnelClient(...)` so the cached JWT survives auto-reconnect cycles. The header build at [packages/connector/src/tunnel/client.ts:65-69](packages/connector/src/tunnel/client.ts#L65-L69) takes the `authProvider` branch.

  Posture dispatch is purely env-driven: `OAUTH_CLIENT_ID` set → OAuth2; otherwise the static-bearer path. They're mutually exclusive — boot fails if neither is configured. Twilio-takeover story for OAuth2 deployments is `OAUTH_TOKEN_URL` flip from controller to `https://oauth.twilio.com/v2/token` with no connector code change; the static-bearer posture has no equivalent migration path.
- **Identity established at WS register-frame time.** Separate from the handshake: once the WS is up, the connector sends a `register` frame and the controller binds the session to a `connectors` row. On first connect the row is minted using `${CONNECTOR_NAME}` and the controller returns a `registrationToken` in the register-ack. The connector persists that token to `./.connector-state.json` (CWD-relative — the repo root in dev, the customer's project root post `npm i`) and presents it on every subsequent register frame. Strict mode: an unknown token is rejected (`unknown_registration_token`); the customer must clear the state file to mint fresh. The yaml uses `${CONNECTOR_NAME}` with no default — an unset env var fails fast at boot rather than silently binding to a placeholder. To re-mint under a new name: change `CONNECTOR_NAME` in `.env`, **also update or recreate the Tunnel Security row** so the new name has a matching bearer (the row is keyed on name), and delete `.connector-state.json`.
- **No LLM, no agent loop, no document handling — *in the connector core*.** The connector itself stays a thin dispatcher. Type 3 bundles are a deliberate exception: a bundled MCP child process can do whatever it needs (LlamaIndex, vector stores, document parsers) because it runs in its own venv, isolated from the connector's Node code path, with its own deps and its own per-entry `.env`. The rule applies to `packages/connector/`; it doesn't apply to what the connector spawns. If you find yourself adding `openai` or document-parser deps to `packages/connector/package.json`, stop — that belongs in a Type 3 bundle under `bundles/<name>/`, not here.
- **Webhook ingress preserves the outbound-only invariant.** The Twilio statusCallback / inbound-webhook story (see [.claude/plans/STATUS-CALLBACK-MCP.md](.claude/plans/STATUS-CALLBACK-MCP.md)) puts the public URL on the *controller* (`https://<controller-host>/api/webhook/<connectorId>/<token>`); the connector consumes events as `webhook` frames over the existing `/mcp-tunnel` WS. The connector opens **no** inbound port for webhook ingress, no per-MCP ngrok, no LB. Every webhook URL is bcrypt-protected per (connectorId, mcp); the URL prefix (rowId) is stable across reconnects but the random tail re-mints on every `webhook-allocate` (the connector pushes the new value to SDK consumers as a fresh `event: url` over the inspector loopback's SSE stream — see [`packages/connector/src/tunnel/webhook-registry.ts`](packages/connector/src/tunnel/webhook-registry.ts)). Don't reintroduce a per-MCP local listener for webhook delivery — that breaks the load-bearing property.
- **Inspector port is localhost-only and carries copy-able webhook URLs.** The inspector at `INSPECTOR_PORT` (default 9090) hosts both the operator UI *and* the SDK ↔ connector IPC routes (`/internal/webhook/stream`, `/internal/webhook/revoke`) used by bundled MCP children to subscribe to webhook events. The Webhooks panel exposes the full bcrypt-protected URL with a copy button by design (operators paste it into Twilio configs). **Never bridge `INSPECTOR_PORT` to a public load balancer or expose it beyond the connector container** — copying the URL out is intentional, and that URL *is* the secret. Same trust boundary as the existing inspector, just made load-bearing by webhook ingress.
- **Inspector session creds are loopback-only, in-memory, and write-only on the wire.** The W-S4 routes `POST /mcp/session-creds-apply` and `POST /mcp/session-creds-clear` accept developer-pasted env values for an MCP from the inspector UI; `GET /mcp/env-keys?mcp=<name>` lists declared key names (read-only, never values). Values land in the supervisor's private `entry.sessionEnv`, never persist to disk, never echo back through the loopback UI, and never cross to the controller. They expire 12h after paste (hard cap, not sliding-on-activity) — the supervisor's per-MCP `setTimeout` clears them and restarts the child without the value. Merge precedence is `process.env ⊕ spec.env ⊕ sessionEnv ⊕ controllerEnv` — controller wins per-key, session creds fill *gaps* the controller hasn't covered. There is no `GET /mcp/session-creds` and there will never be one — value read-back would defeat the entire architecture's "creds live on the controller" pitch. Leak channels pinned by [`packages/connector/tests/inspector/session-creds-leak.test.ts`](packages/connector/tests/inspector/session-creds-leak.test.ts) and [`packages/connector/tests/logger/redact.test.ts`](packages/connector/tests/logger/redact.test.ts); pino has a `redact.paths` allowlist as runtime backstop. Don't add a value-read-back accessor to `McpSupervisor`, don't widen `McpStatus` with anything that surfaces values, don't loosen the loopback bind. Customer-facing reference at [docs/INSPECTOR.md](docs/INSPECTOR.md) §"Right pane — MCP creds view".

## Wire protocol — frames

Defined in [packages/connector/src/tunnel/frames.ts](packages/connector/src/tunnel/frames.ts):

- `register { manifest }` — first frame after WS open
- `manifest-delta { delta }` — diff of `added`/`removed`/`changed` tools
- `rpc { payload }` — opaque MCP JSON-RPC, both directions
- `heartbeat { ts }` — every `policy.heartbeat_interval_ms`
- `goodbye { reason? }` — sent on SIGTERM before WS close
- `webhook-allocate { mcp, ttlSeconds? }` — connector → controller; mint a public URL for `mcp` (`ttlSeconds` is reserved; v1 controller ignores it)
- `webhook-allocate-ack { mcp, url?, error? }` — controller → connector; reply to `webhook-allocate`. Echoes `mcp` for correlation (no requestId — same shape as `register-ack`)
- `webhook { mcp, queryParameters, body, headers?, receivedAt }` — controller → connector; an inbound HTTPS POST routed to `mcp`. `body` is JSON-normalised by the controller (form-urlencoded → object before forwarding); `headers` is allowlisted to `X-Twilio-*` (case-insensitive) + `Content-Type`
- `webhook-revoke { mcp }` — connector → controller; explicit teardown of an allocation. Not sent on WS close (the controller GCs by session)
- `creds-request { mcp, author, envKeys, requestId }` — connector → controller; ask for env values for `mcp`. `author` is `"twilio"` for Twilio-bundled MCPs (controller auto-fills from the tunnel-security row), `"customer"` otherwise. `envKeys` is the de-duped union of every tool's authored `envKeys` hint. `requestId` is connector-minted for correlation.
- `creds-response { requestId, env?, source?, error? }` — controller → connector; reply to `creds-request`. `source` is one of `"twilio-tunnel-row"`, `"operator-entered"`, `"none"` — surfaced verbatim in the inspector status panel. Late arrivals (after the 5s soft-wait) go through the same `supervisor.applyControllerEnv` path as a push.
- `creds-update { mcp, env, source }` — controller → connector; operator updated creds in the controller UI. Connector applies via `supervisor.restart(name, "creds-update")`. Optional `mcpId` for 3rd-party-MCP correlation (v1.1).
- `mcp-config-snapshot { generation, servers }` — controller → connector (v1.1); full 3rd-party MCP roster keyed by `mcpId`. Sent on every `register-ack` (always — even when empty), and as the reply to `mcp-config-resync`. Connector reconciles by diff against running supervisor entries; the yaml is NOT rewritten — controller-supplied roster lives in connector RAM only.
- `mcp-config-delta { generation, added?, updated?, removed? }` — controller → connector (v1.1); steady-state deltas for 3rd-party MCP CRUD. Generation is monotonic; gap → connector requests resync. `removed` carries `mcpId[]`, not names.
- `mcp-config-ack { generation, perMcp }` — connector → controller (v1.1); per-MCP `{mcpId, name, status, error?}` after applying a snapshot or delta. `status: "skipped"` for entries the connector cannot run (e.g. `http` entry missing `url`, `stdio` entry missing `command`); reserved for unrecognised future transports. As of v1.1 all five wire transports (`stdio` / `http` / `streamable-http` / `sse` / `websocket`) are supported.
- `mcp-config-resync { reason }` — connector → controller (v1.1); sent on generation gap (`reason: "gap"`) or boot soft-wait timeout (`reason: "boot"`). Controller MUST reply with a fresh `mcp-config-snapshot`.
- `local-mcps-rescan {}` — controller → connector (v1.2); operator clicked **Refresh local MCPs** in the controller UI. No payload — the connector decides what's in `MCP_DROPIN_DIR`; the controller just triggers. See [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) §"v1.2 — Local MCP rescan".
- `local-mcps-rescan-ack { added, removed, unchanged, errors }` — connector → controller (v1.2); diff summary after re-running `discoverDropins({yamlNames})` and reconciling against running supervisor entries with `source === "local"`. Manifest changes ride the existing `manifest-delta` path; this ack is just the "Done — N added, M removed" summary the controller's UI surfaces.
- `mcp-notification { server, payload }` — connector → controller (v1.2); forwards a server-initiated MCP notification (`notifications/progress`, `notifications/message`, `notifications/resources/updated`, `notifications/{tools,prompts,resources}/list_changed`). `payload` is the raw JSON-RPC envelope; the connector validates the shape but doesn't interpret. Wire-format authority: [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) §"v1.2 — MCP server-method extension".
- `mcp-discovered { mcp, author, source, envKeys, tools, discoveredAt }` — connector → controller (v1.3); customer-authored drop-in MCP whose tools are NOT yet in the manifest. Sent at boot (after `register`) for every drop-in, AND on rescan-added drop-ins. `author` is always `"customer"`, `source` is always `"local"` — the gate predicate. Tools list carries names + descriptions only; schemas are withheld until approval (the operator UI doesn't need them to render the approval form). See [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) §"v1.3 — Customer drop-in approval gate".
- `mcp-enable { mcp, env?, source? }` — controller → connector (v1.3); operator-side approval gesture, with optional inline pasted env values. Two emission points: initial approval click, and replay-on-register-ack for every previously-approved MCP (the controller is the durable authority for approval state, per CLAUDE.md "Customer drop-ins gated by controller approval"). Idempotent — re-enabling an already-enabled MCP is a no-op except for the ack frame. `env` merges via the existing `supervisor.applyControllerEnv` path; `creds-update` is the steady-state ongoing-rotation path post-approval.
- `mcp-disable { mcp }` — controller → connector (v1.3); operator revokes approval. Connector drops tools from the manifest (emits `manifest-delta { removed }`); the child KEEPS running. Re-enable via fresh `mcp-enable` is sub-second. No `stop` field on this frame — kill-the-child is reserved for a future `mcp-stop` if a real scenario emerges (RAM pressure, MCP misbehaviour); don't overload `mcp-disable`.
- `mcp-enable-ack { mcp, status: "enabled" | "disabled" | "error", error?, toolsCount? }` — connector → controller (v1.3); reply to `mcp-enable` and `mcp-disable`. `status: "enabled"` carries `toolsCount`; `status: "error"` carries `error` (`"unknown_mcp"`, `"apply_env_failed: <reason>"`, `"not_gated: ..."`). Frame-ordering rule: `manifest-delta` MUST precede the ack — the ack is the "I'm done" signal, the manifest-delta is the actual surface change.

Wire-format authority: **[`docs/MCP-PROTOCOL.md`](docs/MCP-PROTOCOL.md)** is the contract for the controller team. Connector-side schemas in [`packages/connector/src/tunnel/frames.ts`](packages/connector/src/tunnel/frames.ts) match it. Backwards compat: an older controller that doesn't know `creds-request` triggers the 5s soft-wait timeout per MCP — the connector logs `warn` and falls back to `dir/.env` for that MCP. WS stays open; not a fatal protocol error.

Inbound `tools/call` uses `name = "${serverName}.${toolName}"`. The connector splits on the first `.`. Some controllers also send a `register-ack` frame back; the connector parses and ignores it (non-spec, but harmless).

v1.2 widened the dispatcher beyond `tools/*`: `prompts/list`, `prompts/get`, `resources/list`, `resources/templates/list`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `completion/complete`, `logging/setLevel` all forward through `McpServerConnection`'s matching method. Routing follows three patterns: `prompts/get` mirrors `tools/call` (`${server}.${name}` qualifier), resource methods route by `params.serverName` with a fallback to URI scheme, and the aggregate `*/list` methods accept an optional `params.serverName` to narrow to one MCP. `completion/complete` and `logging/setLevel` REQUIRE `params.serverName`. `ServerDescriptor` carries optional `prompts[]` / `resources[]` / `resourceTemplates[]` / `capabilities` arrays — only populated when the upstream MCP advertised the matching capability. Older controllers ignore the new fields per the §"Frame envelope" unknown-fields rule.

`webhook` frames share the WS with `rpc` traffic and `heartbeat`s. Three rules keep that mix safe:
- **No per-frame await.** The TunnelClient's `send()` is synchronous; webhook delivery doesn't block heartbeat scheduling. Don't introduce an async hop on the send path or you'll starve heartbeats under burst load.
- **No chunking.** Webhook frames are single JSON lines like every other frame. The controller caps body at 256 KB (413 over) — that's also the implicit ceiling on tunnel frame size.
- **Webhook latency vs RPC latency.** Twilio's payment / status callbacks are not latency-sensitive (humans say digits). The controller is the synchronous HTTP responder anyway — it returns 200 to the upstream immediately and forwards async over the WS, so the upstream never sees connector queue depth.

Each `ServerDescriptor` in the manifest carries an `author: string` field — derived by the connector from the spec, never configured. Today's values: `"twilio"` for any MCP resolved via the `bundled:` yaml form (Type 3 — definitionally Twilio-shipped, pre-installed in the connector image), `"customer"` for everything else. The controller uses this to group MCPs in its UI (e.g. Twilio-shipped vs customer-side MCPs in different sections of the connector detail view); Type 2 (3rd-party) MCPs pushed by the controller — including the standalone Twilio + Segment packages — arrive with `"customer"` and the controller does its own author-tagging server-side. Typed as `string` rather than a union literal so the controller forward-compats new author values without a wire-format break. The derivation lives in `authorOf(spec)` in [packages/connector/src/config.ts](packages/connector/src/config.ts) and is invoked once per server in [packages/connector/src/manifest/build.ts](packages/connector/src/manifest/build.ts) — change the rule there if the bundled-shape convention shifts.

## Workspaces

npm workspaces, **one package**: `@mcp-shim/connector`. That's the only thing that ships.

**Module system: native ESM.** [packages/connector/package.json](packages/connector/package.json) declares `"type": "module"`; tsc emits `dist/**/*.js` as ESM (paired with `module: NodeNext` in [tsconfig.base.json](tsconfig.base.json)). Source files use `import`/`export` exclusively; relative imports MUST carry the `.js` extension (NodeNext requirement). For CJS-only ergonomics: use `createRequire(import.meta.url)` from `node:module` (see `TSX_BIN` resolution in [src/mcp-supervisor.ts](packages/connector/src/mcp-supervisor.ts)) and `fileURLToPath(import.meta.url)` from `node:url` for `__dirname`/`__filename` equivalents (see [src/dropin.ts](packages/connector/src/dropin.ts)). **Don't add `require()` calls or `__dirname` references in new code** — they fail at runtime under ESM. The CJS emit was retired in S6.5 of [.claude/plans/MCP-SHIM-MERGE.md](.claude/plans/MCP-SHIM-MERGE.md) because the tsx CJS-bridge had a quirk where dynamic `import()` of a `.ts` file inside a CJS dependency reported the wrong namespace shape under `Object.values()`, breaking the drop-in runner's named-export fallback for customer drop-ins.

Type 1 MCPs are **not** workspaces, but every one carries a minimal `package.json` so it can grow third-party SDKs in isolation. The rule:

- **Framework deps (`zod`, `@mcp-shim/connector/sdk`)** are not listed per-folder. They resolve via Node's parent-dir walk to the workspace root `node_modules`, where npm hoists them once.
- **Third-party SDKs (`twilio`, future `axios`, `@salesforce/sf-cli`, etc.)** are declared in the MCP's own `package.json` `dependencies` block and install into that folder's `node_modules`. They never hoist to the workspace root, so other MCPs can't accidentally `import "twilio"`.

A folder's `package.json` may have an empty `dependencies` block (or none at all) when it imports only framework deps — `mcp/local/sample/` is like this today. The moment a drop-in grows a third-party SDK, you add a `dependencies` block listing that one SDK; nothing else changes. No in-repo MCP currently uses the third-party-SDK shape (the prior `mcp/bundled/twilio/` did, but it's been retired in favor of standalone npm packages loaded as Type 2 entries).

`scripts/start-connector.sh` runs `npm install --omit=dev` in any MCP folder whose `package.json` has a non-empty `dependencies` block but is missing `node_modules` — first-boot is one-shot. The Dockerfile mirrors the same loop at image-build time. Bumping a dep *version* in `package.json` while `node_modules` already exists is a case the auto-install doesn't catch — run `npm install` in that folder yourself.

**Publish flip:** when `@mcp-shim/connector` is published to the npm registry (the `private: true` in [packages/connector/package.json](packages/connector/package.json) gets flipped), each Type 1 `package.json` will need to *also* list `"@mcp-shim/connector": "^<version>"` so the SDK resolves from the registry instead of the workspace. Today's hoist-from-workspace shape is the in-repo dev convenience; the registry pin is the customer-extracts-one-folder shape.

The `@mcp-shim/connector` package is publishable (`exports`, `bin`, and `name` are already set) — only `private: true` in [packages/connector/package.json](packages/connector/package.json) blocks publish. Flip when ready. The `twilio-mcp-shim` project consumes it via a `file:` dep in dev today; on publish, that flips to a registry pin with no consumer code change.

- **`packages/connector`** — the customer-side process. Config, MCP clients to local servers, WSS tunnel, dispatcher, supervisor (Type 1 child supervisor + drop-in spawner + Type 2/3 connector), inspector UI, CLI (`start` / `init` / `discover` / `register` / `version`). The connector + its `tsx` runtime + the `mcp/` tree are what go in the OCI image.
- **`packages/connector/src/sdk/`** — the surface customer-authored Type 1 servers import. `Tool` interface (incl. optional `envKeys?: string[]`) + `createMcpHttpServer({name, tools, port?, envKeys?})` factory. Re-exported from `@mcp-shim/connector/sdk`. The factory's HTTP server also exposes `/envkeys` returning the de-duped union of every tool's `envKeys` (or, when `opts.envKeys` is set at the server level, that list verbatim) — the supervisor queries it post-spawn so the connector can include it in `creds-request` frames. Server-level `envKeys` exists specifically for **creds-gated MCPs** that register zero tools at boot when their creds aren't yet present: the per-tool aggregate would be empty, but the controller still needs to know which keys to populate. **Empty-tools `tools/list` handler:** when `opts.tools.length === 0`, the factory installs an explicit `tools/list` handler returning `{tools: []}` — McpServer wires its own handler lazily on first `registerTool()`, and a tools-empty server would otherwise return `-32601 Method not found` to `tools/list` and crash the connector's `buildManifest` at boot. Don't remove this branch in [`packages/connector/src/sdk/http-server.ts`](packages/connector/src/sdk/http-server.ts) without restoring an equivalent compliance gate — empty-tools is a valid resting state for creds-gated MCPs.
- **`packages/connector/src/sdk/dropin-runner.ts`** — synthesized child entrypoint for drop-in MCPs. Auto-discovers default-exported (or first-named-export-of-shape) `Tool` / `Prompt` / `Resource` objects from `${DROPIN_DIR}/{tools,prompts,resources}/*.{ts,js}` and calls `createMcpHttpServer({ name: ${DROPIN_NAME}, tools, prompts, resources })`. The three sibling categories are independently optional — a tools-only folder still works (today's shape). Discovery logic lives in [packages/connector/src/sdk/dropin-discovery.ts](packages/connector/src/sdk/dropin-discovery.ts) so it's unit-testable without spawning a real child process. One shared bin parameterized by env, not a per-folder file write.
- **`packages/connector/src/dropin.ts`** — `discoverDropins({ yamlNames })` scans `MCP_DROPIN_DIR`, returns synthesized Type 1 specs (`Extract<HttpServer> & { __dropin: true }`, assignable to `McpServerSpec`). Skips folders with a yaml entry or a hand-written `server.ts`.
- **`packages/connector/src/mcp-supervisor.ts`** — owns the lifecycle of every MCP child (Type 1 hand-written, Type 1 drop-in, Type 2 stdio, Type 2 http, Type 3 bundled). Exposes `register(specs) / startAll() / restart(name, reason) / stopAll()`, applies controller-supplied env via `applyControllerEnv(mcp, env, source, reason)`, tracks per-MCP `McpStatus` (process / credsSource / credsLastUpdated / restartCount / lastRestartReason / toolsCount / **source** / **mcpId**), and **mutates the SHARED `servers: Map<string, McpServerConnection>`** so the dispatcher and inspector pick up new connections without re-wiring. Replaced the old `src/spawner.ts` (deleted in `feature/mcp-loading`). Auto-port probe + tsx resolution moved here unchanged. **Spawn-mutation invariant:** `spawnChild` mutates the spec's `endpoint` (and stamps a hidden `__port`) post-readiness so `connectServer` works unchanged — but that mutation flips `isType1Spawn(spec)` from `true` → `false`. `stopEntry` MUST clear both fields when `__port` is set so the next `startEntry` re-classifies the entry as a spawn and re-enters `spawnChild`. Without this clearing, a creds-driven restart kills the child and then dials the freed port → ECONNREFUSED. The `__port` gate is what keeps Type 2 http entries' author-supplied endpoints untouched. **Auth resolution invariant (W-E3/W-E4):** when the entry carries `auth?: McpAuthSpec` (set by the controller-config coordinator), `startEntry` calls `resolveSpecHeaders` AFTER `spawnChild` (which doesn't apply for Type 2) and BEFORE `connectServer`. Sync shapes (`none` / `bearer` / `header`) flow through [`src/auth/resolve-mcp-auth.ts`](packages/connector/src/auth/resolve-mcp-auth.ts); OAuth2 `client_credentials` flows through [`src/auth/resolve-mcp-auth-async.ts`](packages/connector/src/auth/resolve-mcp-auth-async.ts) backed by a per-supervisor cache keyed on `${tokenUrl} ${clientId} ${clientSecret}`. Strategy is mint-at-connect, restart-on-401 — chosen over a fetch-override transport wrapper because the SDK's `requestInit.headers` is a static object and a wrapper would couple to SDK transport internals. Empty-string env values are treated as missing in both helpers (matches `stripEmptyValues` at the wire boundary). **Source/mcpId plumbing (W-E6 / W-L1):** `McpStatus.source` is one of three values — `"yaml"` (yaml-listed bundled / hand-written Type 1), `"local"` (drop-in folder under `MCP_DROPIN_DIR`, auto-detected via the `__dropin` marker), or `"controller-config"` (controller-pushed 3rd-party MCP). `register()` and `registerOne()` default to `"local"` for drop-in specs and `"yaml"` otherwise; the controller-config coordinator overrides via `registerOne(spec, { source: "controller-config", mcpId })`. The L2 rescan coordinator filters by `source === "local"` to decide which entries it owns — the other two sources are immune to drop-in rescan. **NODE_PATH for drop-in spawns:** `computeDropinNodePath()` walks ancestors of the supervisor's own `import.meta.url` and joins every `node_modules` it finds with the platform delimiter; the resulting string is set as `NODE_PATH` on every drop-in spawn env. Without it, a `MCP_DROPIN_DIR` that points OUTSIDE the repo (production: `/var/lib/mcp-connector/customer-mcps/`; dev with `MCP_DROPIN_DIR=/tmp/customer-mcps`) crashes the child with `Cannot find module 'zod'` because Node's parent-dir climb has no path to the workspace's hoisted `node_modules`. Restoring resolution via `NODE_PATH` is preferred over forcing every drop-in folder to ship its own `package.json` (which would defeat the "drop a folder, that's it" pitch). **Don't move this to the boot path or per-spawn recompute** — `import.meta.url` doesn't change at runtime, and spawn perf is not free. The closure capture in `DROPIN_NODE_PATH` is intentional.
- **`packages/connector/src/tunnel/creds-coordinator.ts`** — fans out `creds-request` per MCP after register-ack, awaits the 5s soft-wait, applies responses via `supervisor.applyControllerEnv`. Late `creds-response` frames and `creds-update` push frames go through the same code path. Re-built per tunnel — the `pending: Map<requestId, …>` is pending IPC; a reply from a stale tunnel landing on a fresh one would be wrong. Exposed to the inspector via `mcpActions.reloadCreds(name)` for the per-MCP "Reload creds" button.
- **`packages/connector/src/servers/connect.ts`** — transport dispatch for outbound MCP connections. `stdio` specs go to `connectStdio`; `http` specs branch on the internal `__transportKind` marker (mirrors `__dropin` / `__port`): `"sse"` → `connectSse`, `"websocket"` → `connectWebSocket`, anything else → `connectHttp` (today's default for Type 1 spawned children, Type 2 author-supplied http endpoints, and `streamable-http` 3rd-party MCPs). The wire-side `McpConfigEntry.transport` is multi-valued (http / streamable-http / sse / websocket / stdio); the supervisor-side `McpServerSpec` stays two-valued (`http` / `stdio`) so the four HTTP-family wire variants collapse to the `http` spec with the SUB-transport on `__transportKind`. WebSocket caveat: the SDK's `WebSocketClientTransport` accepts only a URL — custom headers from the W-E3/W-E4 auth resolver are dropped with a warn; operators on a WebSocket upstream must embed auth in the URL (token query param, etc.). SSE forwards `spec.headers` through `requestInit.headers` on recurring POSTs same as `connectHttp`.
- **`packages/connector/src/tunnel/mcp-config-coordinator.ts`** — owns the in-memory roster of controller-pushed 3rd-party MCPs (v1.1). Handles `mcp-config-snapshot` / `mcp-config-delta` / `mcp-config-resync` over the WS, translates `McpConfigEntry` → `SupervisedSpec`, and reconciles by diff against running supervisor entries via `supervisor.{hasEntry,registerOne,startOne,replaceSpec,unregister}`. Threads `mcpId` into `creds-request` for roster entries via `mcpIdFor(name)` so the controller can scope `(connectorId, mcpId)` instead of `(connectorId, mcp)`. **Constructed once per connector process** (in `boot()`, alongside the supervisor) — UNLIKE `creds-coordinator.ts` it does NOT rebuild per tunnel. Per-tunnel rebind goes through `bind({send, log?})` which only swaps the wire `send` callback and cancels any in-flight snapshot-wait timer; `roster` (mcpId → entry) + `nameToMcpId` + `lastAppliedGeneration` are steady-state membership and survive WS reconnect by design. **Don't refactor it back to per-tunnel construction without thinking through the cross-product with the supervisor's lifetime — they're a pair.** The 2026-06-21 manual repro this prevents: after a WS reconnect, a `gen=N` snapshot from the controller correctly omits a row the operator deleted while the WS was down; the per-tunnel coordinator's empty `roster` would skip the "Removed" loop and then misclassify the supervisor's still-running prior entry as a yaml-clash on the re-add. Snapshot-wait timer (`armSnapshotWait`) re-arms on every register-ack — the `mcp-config-resync { reason: "boot" }` frame name is the wire contract, not literally a process-boot signal.
- **`packages/connector/src/tunnel/local-mcps-coordinator.ts`** — handles W-L2 controller-triggered `local-mcps-rescan` and the inspector loopback `/mcp/rescan-local` route. Re-runs `discoverDropins({yamlNames})` and reconciles by diff against `supervisor.statusList()` filtered to `source === "local"` — yaml + controller-config entries are immune (they're not "ours" to manage). Same lifetime contract as `mcp-config-coordinator.ts` — constructed once per process, rebound per-tunnel via `bind({send})` so its single-flight guard (the `rescanInFlight` flag) survives WS reconnect. Single-flight is intentional: a second click during a mid-flight scan returns an empty ack, since the in-flight scan covers the same disk state. The `onMcpAdded` hook fans out a `creds-request` for freshly-spawned MCPs via the inspector's `mcpActions.reloadCreds` (rescan-added MCPs miss the boot-time fan-out).
- **`mcp/local/sample`** — Type 1 drop-in demo. `tools/now.ts`, `slow-echo.ts`, `uuid.ts`, `weather.ts` (weather.gov, US-only) + `prompts/weather-briefing.ts` + `resources/uuids-recent.ts`. No `server.ts`, no `package.json`, no yaml entry — picked up by the drop-in scanner.
- **`mcp/bundled/enterprise-knowledge`** — Type 3 config stub. Just a `.env.example`. Bundle *source* lives at [`bundles/enterprise-knowledge/`](bundles/enterprise-knowledge/); this folder exists so the customer's yaml can `dir: ../../mcp/bundled/enterprise-knowledge` and the standard per-entry `.env` loader picks up the customer's secrets without dragging the bundle's source into the runtime image.
- **`bundles/enterprise-knowledge`** — Type 3 source. Python package (`pyproject.toml`, `src/customer_ek_mcp/`, `migrations/`, `dev-launch.sh`). Read by `pip install` during the Dockerfile's bundle-build stage to populate `/opt/bundled-mcps/enterprise-knowledge/.venv/` in the runtime image; the source tree itself does *not* ship.

Type 1 servers use a stateful `StreamableHTTPServerTransport` with `randomUUID` session IDs. **Stateless mode does not work** with the SDK's HTTP transport — it requires a per-request transport instance. The factory in `sdk/http-server.ts` is the one place this is set up.

Don't soften either check — the failure modes are intentional, and a silently-unauthenticated or unnamed connector is exactly the bug they prevent. Note: a credential that's *set but doesn't match any controller row* boots fine here and gets rejected at the WS handshake with HTTP 401 — that's a controller-side decision (`bearer did not match any tunnel security config` for static, `OAuth2 token mint rejected` for OAuth2), not something we can detect locally before dialing.

Every component (`connector`, `dispatcher`, `inspector`, each Type 1 MCP, `mock-customers`) gets a child logger via `createLogger('component')`, and the bound `component:` field replaces the old `[component]` line prefixes. Type 1 MCP authors get the same logger via `import { createLogger } from "@mcp-shim/connector/sdk"`. Don't reintroduce `console.log` for runtime telemetry — CLI commands (`init`, `discover`, `--help` / `--version`) are the only place direct stdout writes belong, since their output is user-facing CLI text, not telemetry.

## Inspector UI notes

The inspector lives inside the connector process at `INSPECTOR_PORT` (default 9090) and **binds to `127.0.0.1` only** (enforced in [packages/connector/src/inspector/server.ts](packages/connector/src/inspector/server.ts)'s `server.listen(port, "127.0.0.1", …)`). It is part of the customer side; it does **not** proxy or impersonate the controller. It only renders what *this* connector is doing. Reach it from outside the container via port-forward / exec — never via an LB. Don't relax the bind to `0.0.0.0` or pass an external host argument: the Webhooks panel exposes the bcrypt-protected URL by design and the SDK ↔ connector IPC routes (`/internal/webhook/*`) carry no auth of their own.

Token-based renderer for tool shape cards in [packages/connector/public/app.js](packages/connector/public/app.js): each token is `[cssClass, text]` and gets HTML-escaped at render time. Don't reintroduce regex-based replacement for syntax highlighting — it dragged in control-character ambiguity that the linter rightly complained about.

The left column is draggable; the width is persisted in `localStorage` under `inspector.leftColPx`.

Live config sits at the **root of the working directory** (repo root in dev, customer project root post `npm i`) — mirroring what a customer sees when they `npm install @mcp-shim/connector`: `.env` and `connector.yaml` sit next to `node_modules/`, not inside it. Templates ship inside the package (`packages/connector/*.example`) so `mcp-connector init` can copy them out.

**Two modes for tunnel credentials, chosen by `CONNECTOR_CREDS_SOURCE`.** As of the env-to-db migration (`feature/env-to-db`, 2026-07-11) the connector supports two mutually-exclusive ways to load the controller URL, connector name, and bearer/OAuth secret needed to open the WSS tunnel:

- **`db` (default, recommended).** Tunnel identity + creds live in a `controllers` row in Postgres, sealed at rest with libsodium `crypto_secretbox_easy`. The 32-byte master key comes from `CONNECTOR_KEY_FILE` (typically a K8s / Docker secret mount). Operators manage the row via the inspector's Tunnel panel — no shell access needed; no process restart on rotation. **Empty DB at boot is a valid state**: the inspector renders "Configure tunnel", MCPs still spawn, no `TunnelClient` is constructed until an operator submits the form. See [.claude/plans/ENV-TO-DB.md](.claude/plans/ENV-TO-DB.md) for the full design; the routes live in [`src/inspector/tunnel-routes.ts`](packages/connector/src/inspector/tunnel-routes.ts).
- **`env` (legacy, being removed one release after `db` is proven stable).** Tunnel identity from `.env` + `connector.yaml`'s `tunnel:` block + `.connector-state.json`. Editing requires `vim .env` + restart. Preserved for one release cycle as a rollback lane; do NOT choose it for new deployments. The Step 14 follow-up PR (per [.claude/plans/ENV-TO-DB.md](.claude/plans/ENV-TO-DB.md)) will delete this branch entirely.

Dispatch is a single point in [`src/boot/lifecycle.ts`](packages/connector/src/boot/lifecycle.ts)'s `boot()`: `resolveCredsSource()` picks the flag value (default `"db"`) and calls `bootFromDb()` or `bootFromEnv()`. Do NOT add `if (credsSource === "db")` checks anywhere else — the two branches diverge cleanly at boot and everything downstream (dispatcher, supervisor, reconnect controller) is mode-agnostic.

**TDZ discipline inside `bootFromDb`.** The empty-DB boot path returns from `bootFromDb` before most of the row-driven setup runs; the inspector's tunnel routes are wired BEFORE that return, so an operator submitting the Configure Tunnel modal invokes the `dialTunnel` closure while the function is in its "waiting for configuration" resting state. Any `let` / `const` binding referenced from the closure body (or from `connectTunnelDb`, which the closure invokes) MUST be declared ABOVE the `if (!row) return` early exit — otherwise the closure fires while the binding is still in JavaScript's Temporal Dead Zone and throws `Cannot access 'X' before initialization`. Historical fixes: `de52157` (`auth`, `tunnelDialUrl`), `9dfcdfe` (`registrationToken` — read inline from `row.*` instead of capturing an outer const). Pinned by [`tests/boot/lifecycle-tdz.test.ts`](packages/connector/tests/boot/lifecycle-tdz.test.ts), a source-level static analyzer that fails CI if any captured identifier moves back below the empty-DB return. If you need to add a new binding used by the empty-DB paste flow, hoist it with an `| undefined` union type at the top of `bootFromDb` and guard on read.

**One-shot env→db migration.** Operators upgrading from `env` mode have a stale `./.connector-state.json` holding the `registrationToken` the controller minted for their prior connector row. The db-mode boot doesn't auto-import it (D10 says no auto-import; D11 only deletes-after-success), so the first register-ack under `db` mode is rejected with `code: "organisation_has_connector"`. Recovery is [`scripts/migrate-registration-token.mjs`](scripts/migrate-registration-token.mjs) — reads the state file, seals + writes the token into `controllers.registration_token_ct`, then the operator clicks Reconnect. Step 14 (feature-flag removal, follow-up PR) will promote this to unconditional in-boot logic so the env→db path is friction-free. Do NOT add auto-import to `bootFromDb` before Step 14 — the deliberate friction is what forces operators to acknowledge the migration.

`CONTROLLER_URL` is the controller's HTTPS root; it's used for both the register API call and the WS tunnel dial. The connector internally upgrades `https://` → `wss://` and appends the `/mcp-tunnel` path in [packages/connector/src/tunnel/client.ts](packages/connector/src/tunnel/client.ts) before opening the socket. Don't expose the wire scheme or path as a customer-facing config knob — keep it as `https://<host>` everywhere customers touch and let the connector do the upgrade. The controller dispatches `/crelay` (Conversation Relay) and `/mcp-tunnel` on a single port (default 3001), so one DNS entry / one ngrok tunnel covers both.

The YAML supports `${VAR}` and `${VAR:-default}` interpolation; unknown vars without a default throw with the variable name and YAML line so the customer can fix the right line. `start-connector.sh` sources `$ROOT/.env` and invokes `node packages/connector/dist/index.js start` with `CONNECTOR_CONFIG=$ROOT/connector.yaml`. The connector handles registration inline: on the first WS register frame it presents `tunnel.name`, the controller mints a row + token, the connector persists the token in `.connector-state.json`. Subsequent restarts present the token and re-bind to the same row — no separate provisioning step. In Docker, set the same vars via container env — there is no `.env` inside the image; the customer mounts `connector.yaml` at `CONNECTOR_CONFIG` (default `/etc/mcp-connector/config.yaml`) and a writable volume for `.connector-state.json` (or accepts re-mint on every restart, which the controller's dup-name guard catches). The image bundles `mcp/` at `/app/mcp/` for Type 1 entries to spawn from and Type 2/3 `dir:` resolution.

### Per-entry env precedence (subtle)

The plan called this out as the highest-risk piece — read carefully before changing it. Four layers, lowest to highest precedence:

1. `dotenv/config` loads `./.env` (from CWD) once at startup → populates `process.env`.
2. `loadConfig` parses the yaml. Top-level `${VAR}` interpolation reads from `process.env` only. For each `mcp_servers[]` entry with `dir:`, the loader reads `<dir>/.env` into a **per-spec env map** (does **not** mutate `process.env`).
3. Inline `env:` map on the yaml entry (rare today; layered above `dir/.env`).
4. **Controller-supplied env from `creds-response` / `creds-update` frames.** The supervisor stores these in a per-MCP `controllerEnv` map and they win on conflict. See `mergeEnv` in [packages/connector/src/mcp-supervisor.ts](packages/connector/src/mcp-supervisor.ts) — the merge order is `process.env ⊕ spec.env (yaml inline + dir/.env) ⊕ controllerEnv`.

When the supervisor launches a Type 1 child / drop-in / Type 2 stdio / Type 3 bundled child, it passes the merged env. Cross-entry leakage is still impossible — child A's `API_TOKEN` (whether from `dir/.env` or controller-supplied) does not reach child B even if both declare the same key.

**Stdio entries go through the same merge** (since 2026-06-28). The supervisor pre-builds the merged env in `startEntry` and threads it through `connectServer(spec, env)` → `connectStdio(spec, env)` → `new StdioClientTransport({command, args, env})`. Before this change, `connectStdio` built env from `process.env + spec.env` directly, bypassing `controllerEnv` and `sessionEnv` — controller-config stdio MCPs (e.g. `@deshartman/twilio-mcp` added via the controller UI) booted with empty env regardless of what the operator pasted. Same gate also broke creds rotation: `applyControllerEnv` / `applySessionEnv` / `clearSessionEnv` decide whether to restart based on `entry.child || entry.connection` — stdio entries leave `entry.child` undefined (the SDK's `StdioClientTransport` owns the spawn), so the OR-clause is what catches them. Pinned by `tests/servers/connect-dispatch.test.ts` (env-flow-through contract) and `tests/mcp-supervisor/apply-controller-env.test.ts` (restart-trigger contract). Don't drop either branch of the OR-gate, and don't add a stdio code path that builds env without going through the supervisor.

Per-spawn env-source telemetry: every spawn logs `mcp spawn env-sources` with two arrays — `controller: [...]` and `dirDotEnv: [...]` — listing the env-key names sourced from each layer. Watch the `dirDotEnv` array trend toward `[]` as customers move creds into the controller (D2 deprecation tracker). Stdio entries are covered too (since 2026-06-28).

Don't replace the per-spec env map with calls to `dotenv.config({path: ...})` in `loadConfig` — that mutates `process.env` and breaks the isolation guarantee. Don't widen the merge order without thinking through the cross-product with `applyControllerEnv` (which restarts the child with the new merged env).

### Env reading rule — empty string == not set

All `process.env` reads in `src/` go through [`src/env.ts`](packages/connector/src/env.ts) (`envString` / `envOptional` / `envNumber`). The whole-module rule: **an empty-string env var is treated as "not set"** — fall back to the documented default. An admin who writes `FOO=` (blank line) in `.env` expects "leave this unset"; `??` previously let `""` flow through (`Number("")=0`, `resolve("")=cwd`, pino throws on empty level). `envNumber` additionally throws an admin-actionable error when set to a non-numeric value (naming the var, the bad value, and the recovery), instead of silently coercing to `NaN`. The single deliberate exception is the YAML `${VAR}` interpolator in [`config.ts`](packages/connector/src/config.ts), which substitutes the literal empty string and lets the zod schema produce a more specific validation error.

Boot-time required-env preflight runs once in [`src/boot/require-env.ts`](packages/connector/src/boot/require-env.ts) (`requireEnv()`) before yaml load or auth resolution. It consolidates every missing required var into a single error block so an admin fixes them in one `.env` edit pass. The function branches on `resolveCredsSource(env)` at its start — under `db` mode it requires `POSTGRES_URL` + `CONNECTOR_KEY_FILE` only; under `env` mode it requires `CONNECTOR_CONFIG`, `CONTROLLER_URL`, `CONNECTOR_NAME`, plus the static-bearer-vs-OAuth2 posture. The auth-posture branch (env mode) is posture-aware: setting `OAUTH_CLIENT_ID` triggers a "you started OAuth2; here's what else you need" message rather than three separate "X is required" lines.

In production, each connector deployment is its own container — same yaml shape, just one container per `tunnel.name`.

## Reconnect semantics

- WS close does **not** kill the connector process. It transitions the inspector to `closed` state and stops timers.
- Auto-reconnect is **on by default** (`policy.reconnect.enabled: true`). On an unexpected close the connector schedules a redial via `scheduleAutoReconnect()` in `index.ts` and the inspector enters a fourth `reconnecting` state showing "reconnecting in N.Ns · attempt K". A successful register-ack resets the attempt counter. SIGTERM/SIGINT and a manual click on the inspector's Reconnect button both cancel any pending auto-reconnect timer (`cancelAutoReconnect()`) so a manual click fires immediately.
- Auto-reconnect is **suppressed when the controller rejects the register frame** (e.g. `unknown_registration_token` after the controller's connector row was deleted or the DB was reset). The connector sets a `registrationRejected` flag in the `register-ack` handler; the next `onclose` logs `auto-reconnect suppressed` and stays in `closed` instead of looping forever on a token the controller already said it doesn't recognize. The operator's recovery is to clear `.connector-state.json` and click Reconnect — the manual reconnect path clears the flag, so the next attempt re-mints a fresh row.
- Backoff is computed by `nextReconnectDelay(attempt, policy)` at the bottom of `index.ts`. Today it returns a fixed delay (= `initial_backoff_ms`); swapping in a real backoff curve (full jitter / decorrelated jitter / etc.) is a localized change that doesn't touch the rest of the loop.
- Set `policy.reconnect.enabled: false` to opt out — useful in deployed containers where the orchestrator (Fargate / Container Apps / GKE) is the supervisor and you want the inspector to surface a hard `closed` state. With auto-reconnect disabled, behavior matches the original PoC: `closed` until a manual click or SIGHUP.
- Reconnect re-reads the YAML. `sameMcpServers()` in `index.ts` compares name + transport + endpoint + command + dir + env across the prior and new lists. If anything in `mcp_servers` changed, the connector logs a warning and uses the prior list (live MCP server reconnect is out of scope — the spawned children, the stdio transport, the per-entry env are all wired at boot). `policy` changes take effect.
- Controller-side restarts (e.g. ngrok tunnel cycling) are recovered automatically; the inspector pill flips through closed → reconnecting → connecting → open as the controller comes back. No action required.

## Process lifecycle gotcha

`scripts/start-connector.sh` boots one connector process; the connector itself spawns Type 1 children. The script's pre-cleanup uses `pgrep -f 'scripts/start-connector\.sh'` and skips its own PID — do NOT replace this with `pkill -f` patterns that match `node dist/index.js`, because that catches unrelated node processes and does not catch orphan wrapper shells. The pgrep pattern must match the script's filename — if you rename the file, update the pattern in the same change or the pre-cleanup silently misses prior runs.

The connector's SIGTERM handler calls `supervisor.stopAll()`, which sends SIGTERM to every Type 1 / drop-in / Type 2 stdio / Type 3 child it spawned (with a SIGKILL fallback after timeout). Combined with the script's `trap cleanup EXIT INT TERM` (which `kill 0`s the process group), Ctrl-C cleans up the whole tree.

## Distribution

Primary shape is a signed multi-arch OCI image. Build:

```bash
./scripts/build-image.sh                                # local single-arch
IMAGE=registry/mcp-connector:0.1.0 PUSH=1 ./scripts/build-image.sh  # multi-arch + push
```

[packages/connector/Dockerfile](packages/connector/Dockerfile) is multi-stage; runtime image carries the connector's `dist/` + `public/` + production `node_modules` (incl. `tsx`) + the `mcp/` tree + Python venvs for Type 3 bundles under `/opt/bundled-mcps/<name>/`. The `mcp/` tree is bundled because Type 1 entries in `connector.yaml` reference them via `dir:` and the spawner must be able to `tsx <dir>/server.ts`. Customers who want their own Type 1 MCPs extend the image with additional folders under `/app/mcp/local/`.

The build stage runs `npm install --omit=dev --no-package-lock` inside any `mcp/local/*/` or `mcp/bundled/*/` that has a non-empty `dependencies` block. No in-repo MCP carries Node deps today, so the loop is a no-op — it stays in the Dockerfile because a future bundle (or a customer-extended image) might add one. Folders whose `package.json` only declares the MCP's identity (sample shipped, crm dev-only) skip cleanly — `zod` and `@mcp-shim/connector/sdk` resolve up to `/app/node_modules` from the hoisted workspace install. Folders without any `package.json` at all (enterprise-knowledge — no Node code in this repo) skip too.

[scripts/build-image.sh](scripts/build-image.sh) defaults to `linux/amd64,linux/arm64` (Graviton + ARM Macs). Per-cloud guides at [docs/deploy/](docs/deploy/) (AWS Fargate, Azure Container Apps, GCP GKE) document the foot-guns of each platform — most importantly, **don't put a load balancer in front of the connector** (nothing inbound) and **don't use Cloud Run / App Service / scale-to-zero anything** (kills the WSS).
