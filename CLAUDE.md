# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A customer-side **MCP connector**: a process that runs behind a customer's firewall, dials out to a controller URL via WSS, advertises locally-installed MCP servers as a `ToolManifest`, and dispatches inbound `tools/call` requests. Per the productized design in `MCP-TUNNEL.md` (held outside this repo).

**Not** a generic MCP framework. **Not** an agent. **No LLM lives here.** The connector is a tool dispatcher with policy.

## Topology — one connector, many MCPs

The repo ships **one connector binary** (`packages/connector`) and **MCPs** under `mcp/` — split into `mcp/local/` (customer-authored, Type 1) and `mcp/bundled/` (Twilio-authored, pre-installed in the connector image). Today `mcp/bundled/` holds only `enterprise-knowledge/` (Type 3, Python venv stub); Type 3 *source* lives at `bundles/<name>/` outside `mcp/` so the runtime image carries only the installed venv (`/opt/bundled-mcps/<name>/.venv/`), not the build inputs. A single connector process: (a) reads `./connector.yaml` (resolved from CWD — repo root in dev, `/etc/mcp-connector/` or the customer's mounted config path in production) listing yaml-managed MCPs; (b) auto-discovers customer-authored drop-in MCPs under `${MCP_DROPIN_DIR}/<name>/tools/*.ts` at boot or via W-L2 rescan; (c) receives a controller-pushed roster of Type 2 (3rd-party) MCPs over the WSS tunnel — where Twilio + Segment arrive today (see "v1.1 — 3rd-party MCP roster" in [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md)). Yaml-listed MCPs launch as Type 3 bundle entrypoints; drop-ins spawn as Type 1 children via the synthesized `dropin-runner.js`; controller-roster Type 2 entries connect in-memory and never appear in the yaml. In production this is one container per `connector_id`; in dev, one local process.

In-repo demos: `mcp/local/sample/` (Type 1 drop-in — `now`, `slow_echo`, `uuid`, `weather`, plus prompts + resources demos), `mcp/local/agentic-memory/` (Type 1 drop-in — mock external memory + identity provider implementing [MEMORY-MCP-INTERFACE.md](https://github.com/twilio-internal/AgenticProcedure/blob/main/.claude/plans/MEMORY-MCP-INTERFACE.md); wire-inventory + custom-capabilities envelope deviation documented at [docs/AGENTIC-MEMORY-MOCK.md](docs/AGENTIC-MEMORY-MOCK.md)), `mcp/bundled/enterprise-knowledge/` (Type 3 stub — `sources_register` / `sources_fetch` / `sources_refresh` / `knowledge_query`). Dev-only drop-ins (gitignored — see "Dev-only scaffolding"): `mcp/local/crm/` against `mock/customers/`. The controller is **outside this repo** — this repo only ships the customer side.

### Three MCP integration patterns

- **Type 1 (customer-authored, drop-in shape — default).** Folder under `mcp/local/<name>/tools/` with `*.ts` files only. No `server.ts`, no `package.json`, no yaml entry, no `.env` (creds come from the controller). The drop-in scanner at [packages/connector/src/dropin.ts](packages/connector/src/dropin.ts) discovers the folder at boot; the synthesized child runtime at [packages/connector/src/sdk/dropin-runner.ts](packages/connector/src/sdk/dropin-runner.ts) wires each default-exported `Tool` into a per-folder subprocess (`tsx dropin-runner.js` with `DROPIN_DIR=<folder> DROPIN_NAME=<name> PORT=<auto-assigned>`; auto-port probe from `MCP_BASE_PORT`, default 7100). Folder name = MCP name. Walkthrough at [docs/AUTHOR-LOCAL-MCP.md](docs/AUTHOR-LOCAL-MCP.md). Runtime refresh (no process restart) is W-L2: controller UI **Refresh local MCPs** → `local-mcps-rescan` frame → connector re-runs the scanner; loopback-only mirror at `/mcp/rescan-local` on the inspector. Drop-ins are **approval-gated** — the connector spawns and lists but withholds tools from the manifest until `mcp-enable` arrives; see the load-bearing property below, [.claude/plans/Done/MCP-CUSTOM-APPROVAL.md](.claude/plans/Done/MCP-CUSTOM-APPROVAL.md), and [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) §"v1.3 — Customer drop-in approval gate".

  **Type 1 hand-written shape (legacy escape hatch).** Folder with its own `server.ts` (imports the SDK factory, lists tools, calls `createMcpHttpServer`) plus a yaml entry with `transport: http` + `dir:` + no `endpoint:`. Yaml + hand-written `server.ts` win over drop-in discovery for the same folder name. Stays available for Type 1 MCPs shipping their own `package.json` (third-party SDK that can't hoist to the workspace); no in-repo MCP uses it today. `MCP_DROPIN_DIR` defaults to `/var/lib/mcp-connector/customer-mcps/` in production; `scripts/start-connector.sh` exports `$ROOT/mcp/local` for dev. Runtime rescan reconciliation lives in [packages/connector/src/tunnel/local-mcps-coordinator.ts](packages/connector/src/tunnel/local-mcps-coordinator.ts) — single-flight, filters by `source === "local"` so yaml + controller-config entries are immune. See [.claude/plans/Done/MCP-LOADING-LOCAL.md](.claude/plans/Done/MCP-LOADING-LOCAL.md).
- **Type 2 (connect to existing MCP) — controller-pushed.** No yaml. The operator adds the MCP through the controller UI (Name, Transport, URL or command, Auth shape); the controller pushes it to this connector via `mcp-config-snapshot` / `mcp-config-delta` per [docs/MCP-PROTOCOL.md](docs/MCP-PROTOCOL.md) v1.1. The roster lives in connector RAM only (no yaml rewrite, no on-disk persistence — every **process restart** rebuilds from a fresh snapshot; WS reconnect is NOT a reset — see [`McpConfigCoordinator`](packages/connector/src/tunnel/mcp-config-coordinator.ts)'s LIFETIME block). The supervisor + `servers/` connect path handle Type 2 entries identically whether they came from yaml (transitional) or the controller (target state). Auth on outbound HTTP-family calls is attached via `spec.headers`; stdio Type 2 entries receive creds via env, same as today.
- **Type 3 (bundled, Twilio-authored Python venv, pre-installed in this image).** Yaml entry sets `bundled: <name>` plus an optional `dir:` (under `mcp/bundled/<name>/`) for a per-bundle `.env`. The connector resolves `bundled:` against `BUNDLED_MCPS` in [packages/connector/src/config.ts](packages/connector/src/config.ts) — a registry of bundles laid down at image-build time under `/opt/bundled-mcps/<name>/`. Resolution synthesizes a stdio spec, so the rest of the supervisor code is unchanged. Bundle source lives in **`bundles/<name>/`** at the repo root (separate from `mcp/` so the runtime image carries only the installed venv, not the build inputs); the connector's Dockerfile reads it during the bundle-build stage and `pip install`s it into the venv. Customer surface area: one yaml line + one `.env` file. No code, no `pip install` from the customer's side. Local-dev override: `BUNDLE_DEV_OVERRIDE_<UPPER_NAME>=/abs/path/to/launcher` redirects launch to a working tree (`scripts/start-connector.sh` auto-exports this for any bundle that ships a `dev-launch.sh`).

Note: a Twilio-authored MCP doesn't have to be Type 3. A Node MCP that needs a third-party SDK could live under `mcp/bundled/` *because Twilio ships it* and be wired as Type 1 (yaml entry has `transport: http` + `dir:` and no `endpoint:`). Type 3 is specifically the Python+venv shape — use it when the bundle has its own non-Node deps that can't (or shouldn't) be hoisted into the connector workspace. Today the only bundled MCP is `enterprise-knowledge` (Type 3); Twilio + Segment are Type 2 entries pushed by the controller, not bundled.

The detection helpers in [packages/connector/src/config.ts](packages/connector/src/config.ts) are `isType1Spawn(spec)` (http + dir + no endpoint) and `isType3Bundled(spec)` (stdio + bundled set). Type 3 resolution happens in `loadConfig` *before* the discriminated union parses, because `bundled:` entries have no `transport` field. Don't widen the classifiers without thinking through the cross-product with `sameMcpServers`'s reconnect-comparison logic — `bundled` is part of that equality check so an edit from `bundled: a` to `bundled: b` is detected even when both happen to resolve to identical commands.

## Architecturally load-bearing properties

- **Outbound-only.** The connector opens **no inbound ports** for the tunnel. It dials out; the controller pushes RPC requests back down the same WS the connector opened.
- **Trust boundary is per MCP server, not per tool.** Every tool a server in `mcp_servers[]` exposes is forwarded to the controller. The customer controls *which* MCP servers run on their machine; that's the gate. We deliberately diverged from MCP-TUNNEL.md §"Configuration surface" (which prescribes a default-deny `allow_list.tools` block) — per-tool gating duplicated authority and forced a YAML edit on every new tool. Don't reintroduce `allow_list` without an explicit ask. The wire format keeps `ToolDescriptor.allowed` (controller may still display it; future enterprise-strict mode might use it) — the connector always sets it to `true`.
- **Customer drop-ins gated by controller approval (v1.3+).** A drop-in folder under `${MCP_DROPIN_DIR}` is a *proposal*, not an *acceptance*. The connector spawns the child and lists tools, but withholds the tools from the manifest and emits `mcp-discovered`. The controller's operator approval gesture is what flips the tools into the manifest via `mcp-enable`. Two-key model: the customer admin's filesystem write access proposes; the controller operator's approval click accepts. Yaml-listed Type 1 / Type 3 / 3rd-party MCPs are NOT gated (yaml or controller-UI-authored = pre-existing acceptance). The approved-set lives in connector RAM only — controller replays `mcp-enable` after every `register-ack` to restore state. Don't add approval persistence to `.connector-state.json` — the controller is the source of truth by design. See [.claude/plans/Done/MCP-CUSTOM-APPROVAL.md](.claude/plans/Done/MCP-CUSTOM-APPROVAL.md).
- **Schema declaration follows the trust boundary.** Tools we author (Type 1 customer-side, Type 3 Twilio bundles) declare `outputSchema` so controller-side procedure authors can write `{{ hydrate:<server>.<tool>.<field> }}` and have it type-checked. Tools we don't author (Type 2 externals) pass through verbatim — the controller handles missing schemas gracefully on its end. The boot-time check at [`packages/connector/src/manifest/validate.ts`](packages/connector/src/manifest/validate.ts) logs `error` per offending Type 1 / Type 3 tool but does NOT throw — a missing schema is a per-tool bug, not a connector-wide failure (the rest of the manifest still works). The boot log is the runtime backstop; the prior per-tool test tree under `tests/mcp-tools/` was retired with the `mcp/bundled/twilio/` bundle on 2026-06-30. See [.claude/plans/Done/OUTPUT-SCHEMA.md](.claude/plans/Done/OUTPUT-SCHEMA.md) and [`packages/connector/README.md`](packages/connector/README.md) "Author a Type 1 MCP" for the five authoring rules.
- **WS-handshake auth is per-tunnel, controller-minted.** The connector sends `Authorization: Bearer <bearer>` and `X-Connector-Name: <name>` on the `/mcp-tunnel` upgrade. The bearer's ID prefix (`ts_tsec<rowId>_...`) locates the `tunnel_security_configs` row; the hash tail proves ownership. Mismatch → HTTP 401. `X-Connector-Name` is passed through to the register-frame handler for the `connectors` row lookup — under db mode it's the URL-derived hostname, auto-filled server-side by the inspector's tunnel-routes handler. The legacy shared `TUNNEL_AUTH_TOKEN` env var is gone; every connector needs its own Tunnel Security row, minted in **Tools → Connectors → Tunnel Security**. Posture dispatch is env-driven and mutually exclusive — boot fails if neither is configured. Header build at [packages/connector/src/tunnel/client.ts:65-69](packages/connector/src/tunnel/client.ts#L65-L69) branches:

  | Posture | Trigger | Customer env vars | Rotation |
  |---------|---------|-------------------|----------|
  | Static bearer (`ts_<rowId>_<random>`) | `OAUTH_CLIENT_ID` unset | `TUNNEL_AUTH_TOKEN` | Row's **Rotate Secret** button, prior hash 24h grace |
  | OAuth2 `client_credentials` | `OAUTH_CLIENT_ID` set | `OAUTH_CLIENT_ID` + `OAUTH_CLIENT_SECRET` + `OAUTH_TOKEN_URL` | Connector mints 1h JWT, refreshes <60s before expiry; provider cached in [`auth/oauth-provider.ts`](packages/connector/src/auth/oauth-provider.ts) survives WS reconnect |

  Twilio-takeover for OAuth2 deployments is `OAUTH_TOKEN_URL` flip from controller to `https://oauth.twilio.com/v2/token` with no connector code change; static-bearer has no equivalent migration path.
- **Identity established at WS register-frame time.** Separate from the handshake: once the WS is up, the connector sends a `register` frame and the controller binds the session to a `connectors` row. On first connect the row is minted using the resolved connector name (from the DB row's `name` column under `db` mode, or `${CONNECTOR_NAME}` yaml interpolation under `env` mode) and the controller returns a `registrationToken` in the register-ack. The connector persists that token to `./.connector-state.json` under `env` mode / the sealed `controllers.registration_token_ct` column under `db` mode (CWD-relative — the repo root in dev, the container's mounted config path in production) and presents it on every subsequent register frame. Strict mode: an unknown token is rejected (`unknown_registration_token`); the customer must clear the state file / DB column to mint fresh. Under `env` mode, `requireEnv()` gates `CONNECTOR_NAME` presence before yaml load so an unset var fails with an operator-actionable error, not with a mid-yaml interpolation throw; under `db` mode the yaml's `${CONNECTOR_NAME:-}` interpolates to empty and `bootFromDb` reads the name from the DB row instead (see [ENV-TO-DB.md](.claude/plans/ENV-TO-DB.md) §"Post-Step-12 runtime discoveries" entry G for why the yaml uses `${VAR:-}` defaults now). **`CONNECTOR_NAME` matches the controller's `MCP Tunnel` row Name (the `connectors` table row), NOT the Tunnel Security row name — those are two distinct rows in the controller UI under Conversation Agent → Settings → Connectors.** To re-mint under a new name: change the name in the inspector's Configure Tunnel modal (db mode) or `CONNECTOR_NAME` in `.env` (env mode), delete the persisted registration token.
- **No LLM, no agent loop, no document handling — *in the connector core*.** The connector itself stays a thin dispatcher. Type 3 bundles are a deliberate exception: a bundled MCP child process can do whatever it needs (LlamaIndex, vector stores, document parsers) because it runs in its own venv, isolated from the connector's Node code path, with its own deps and its own per-entry `.env`. The rule applies to `packages/connector/`; it doesn't apply to what the connector spawns. If you find yourself adding `openai` or document-parser deps to `packages/connector/package.json`, stop — that belongs in a Type 3 bundle under `bundles/<name>/`, not here.
- **Webhook ingress preserves the outbound-only invariant.** The Twilio statusCallback / inbound-webhook story (see [.claude/plans/Done/STATUS-CALLBACK-MCP.md](.claude/plans/Done/STATUS-CALLBACK-MCP.md)) puts the public URL on the *controller* (`https://<controller-host>/api/webhook/<connectorId>/<token>`); the connector consumes events as `webhook` frames over the existing `/mcp-tunnel` WS. The connector opens **no** inbound port for webhook ingress, no per-MCP ngrok, no LB. Every webhook URL is bcrypt-protected per (connectorId, mcp); the URL prefix (rowId) is stable across reconnects but the random tail re-mints on every `webhook-allocate` (the connector pushes the new value to SDK consumers as a fresh `event: url` over the inspector loopback's SSE stream — see [`packages/connector/src/tunnel/webhook-registry.ts`](packages/connector/src/tunnel/webhook-registry.ts)). Don't reintroduce a per-MCP local listener for webhook delivery — that breaks the load-bearing property.
- **Inspector port is localhost-only and carries copy-able webhook URLs.** The inspector at `INSPECTOR_PORT` (default 9090) hosts both the operator UI *and* the SDK ↔ connector IPC routes (`/internal/webhook/stream`, `/internal/webhook/revoke`) used by bundled MCP children to subscribe to webhook events. The Webhooks panel exposes the full bcrypt-protected URL with a copy button by design (operators paste it into Twilio configs). **Never bridge `INSPECTOR_PORT` to a public load balancer or expose it beyond the connector container** — copying the URL out is intentional, and that URL *is* the secret. Same trust boundary as the existing inspector, just made load-bearing by webhook ingress.
- **Inspector session creds are loopback-only, in-memory, and write-only on the wire.** The W-S4 routes `POST /mcp/session-creds-apply` and `POST /mcp/session-creds-clear` accept developer-pasted env values for an MCP from the inspector UI; `GET /mcp/env-keys?mcp=<name>` lists declared key names (read-only, never values). Values land in the supervisor's private `entry.sessionEnv`, never persist to disk, never echo back through the loopback UI, and never cross to the controller. They expire 12h after paste (hard cap, not sliding-on-activity) — the supervisor's per-MCP `setTimeout` clears them and restarts the child without the value. Merge precedence is `process.env ⊕ spec.env ⊕ sessionEnv ⊕ controllerEnv` — controller wins per-key, session creds fill *gaps* the controller hasn't covered. There is no `GET /mcp/session-creds` and there will never be one — value read-back would defeat the entire architecture's "creds live on the controller" pitch. Leak channels pinned by [`packages/connector/tests/inspector/session-creds-leak.test.ts`](packages/connector/tests/inspector/session-creds-leak.test.ts) and [`packages/connector/tests/logger/redact.test.ts`](packages/connector/tests/logger/redact.test.ts); pino has a `redact.paths` allowlist as runtime backstop. Don't add a value-read-back accessor to `McpSupervisor`, don't widen `McpStatus` with anything that surfaces values, don't loosen the loopback bind. Customer-facing reference at [docs/INSPECTOR.md](docs/INSPECTOR.md) §"Right pane — MCP creds view".

## Wire protocol — frames

Wire-format authority: **[`docs/MCP-PROTOCOL.md`](docs/MCP-PROTOCOL.md)** — the contract for the controller team, full per-frame schemas + examples. Connector-side zod schemas in [packages/connector/src/tunnel/frames.ts](packages/connector/src/tunnel/frames.ts) match it. Frame categories:

- **Lifecycle**: `register` / `manifest-delta` / `rpc` / `heartbeat` / `goodbye`
- **Webhook ingress** (v1): `webhook-allocate` / `webhook-allocate-ack` / `webhook` / `webhook-revoke`
- **Creds** (v1): `creds-request` / `creds-response` / `creds-update` — `author` field is `"twilio"` for Type 3, `"customer"` otherwise
- **3rd-party roster** (v1.1): `mcp-config-snapshot` / `mcp-config-delta` / `mcp-config-ack` / `mcp-config-resync` — keyed by `mcpId`, connector-RAM-only, survives WS reconnect
- **Local rescan** (v1.2): `local-mcps-rescan` / `local-mcps-rescan-ack`
- **Server notifications** (v1.2): `mcp-notification` — forwards `notifications/*` verbatim
- **Approval gate** (v1.3): `mcp-discovered` / `mcp-enable` / `mcp-disable` / `mcp-enable-ack` — gate predicate is `author === "customer" && source === "local"`

Backwards compat: an older controller that doesn't know `creds-request` triggers the 5s soft-wait timeout per MCP — the connector logs `warn` and falls back to `dir/.env`. WS stays open; not a fatal protocol error.

Inbound `tools/call` uses `name = "${serverName}.${toolName}"`. The connector splits on the first `.`. Some controllers also send a `register-ack` frame back; the connector parses and ignores it (non-spec, but harmless).

v1.2 widened the dispatcher beyond `tools/*`: `prompts/list`, `prompts/get`, `resources/list`, `resources/templates/list`, `resources/read`, `resources/subscribe`, `resources/unsubscribe`, `completion/complete`, `logging/setLevel` all forward through `McpServerConnection`'s matching method. Routing follows three patterns: `prompts/get` mirrors `tools/call` (`${server}.${name}` qualifier), resource methods route by `params.serverName` with a fallback to URI scheme, and the aggregate `*/list` methods accept an optional `params.serverName` to narrow to one MCP. `completion/complete` and `logging/setLevel` REQUIRE `params.serverName`. `ServerDescriptor` carries optional `prompts[]` / `resources[]` / `resourceTemplates[]` / `capabilities` arrays — only populated when the upstream MCP advertised the matching capability. Older controllers ignore the new fields per the §"Frame envelope" unknown-fields rule.

`webhook` frames share the WS with `rpc` traffic and `heartbeat`s. Three rules keep that mix safe:
- **No per-frame await.** The TunnelClient's `send()` is synchronous; webhook delivery doesn't block heartbeat scheduling. Don't introduce an async hop on the send path or you'll starve heartbeats under burst load.
- **No chunking.** Webhook frames are single JSON lines like every other frame. The controller caps body at 256 KB (413 over) — that's also the implicit ceiling on tunnel frame size.
- **Webhook latency vs RPC latency.** Twilio's payment / status callbacks are not latency-sensitive (humans say digits). The controller is the synchronous HTTP responder anyway — it returns 200 to the upstream immediately and forwards async over the WS, so the upstream never sees connector queue depth.

Each `ServerDescriptor` in the manifest carries an `author: string` field — derived by the connector from the spec, never configured. Today's values: `"twilio"` for any MCP resolved via the `bundled:` yaml form (Type 3 — definitionally Twilio-shipped, pre-installed in the connector image), `"customer"` for everything else. The controller uses this to group MCPs in its UI (e.g. Twilio-shipped vs customer-side MCPs in different sections of the connector detail view); Type 2 (3rd-party) MCPs pushed by the controller — including the standalone Twilio + Segment packages — arrive with `"customer"` and the controller does its own author-tagging server-side. Typed as `string` rather than a union literal so the controller forward-compats new author values without a wire-format break. The derivation lives in `authorOf(spec)` in [packages/connector/src/config.ts](packages/connector/src/config.ts) and is invoked once per server in [packages/connector/src/manifest/build.ts](packages/connector/src/manifest/build.ts) — change the rule there if the bundled-shape convention shifts.

## Workspaces

npm workspaces, **one package**: `@mcp-shim/connector`. That's the only thing that ships.

**Module system: native ESM.** [packages/connector/package.json](packages/connector/package.json) declares `"type": "module"`; tsc emits `dist/**/*.js` as ESM (paired with `module: NodeNext` in [tsconfig.base.json](tsconfig.base.json)). Source files use `import`/`export` exclusively; relative imports MUST carry the `.js` extension (NodeNext requirement). For CJS-only ergonomics: use `createRequire(import.meta.url)` from `node:module` (see `TSX_BIN` resolution in [src/mcp-supervisor.ts](packages/connector/src/mcp-supervisor.ts)) and `fileURLToPath(import.meta.url)` from `node:url` for `__dirname`/`__filename` equivalents (see [src/dropin.ts](packages/connector/src/dropin.ts)). **Don't add `require()` calls or `__dirname` references in new code** — they fail at runtime under ESM. The CJS emit was retired in S6.5 of [.claude/plans/Done/MCP-SHIM-MERGE.md](.claude/plans/Done/MCP-SHIM-MERGE.md) because the tsx CJS-bridge had a quirk where dynamic `import()` of a `.ts` file inside a CJS dependency reported the wrong namespace shape under `Object.values()`, breaking the drop-in runner's named-export fallback for customer drop-ins.

Type 1 MCPs are **not** workspaces, but every one carries a minimal `package.json` so it can grow third-party SDKs in isolation. The rule:

- **Framework deps (`zod`, `@mcp-shim/connector/sdk`)** are not listed per-folder. They resolve via Node's parent-dir walk to the workspace root `node_modules`, where npm hoists them once.
- **Third-party SDKs (`twilio`, future `axios`, `@salesforce/sf-cli`, etc.)** are declared in the MCP's own `package.json` `dependencies` block and install into that folder's `node_modules`. They never hoist to the workspace root, so other MCPs can't accidentally `import "twilio"`.

A folder's `package.json` may have an empty `dependencies` block (or none at all) when it imports only framework deps — `mcp/local/sample/` is like this today. The moment a drop-in grows a third-party SDK, you add a `dependencies` block listing that one SDK; nothing else changes. No in-repo MCP currently uses the third-party-SDK shape (the prior `mcp/bundled/twilio/` did, but it's been retired in favor of standalone npm packages loaded as Type 2 entries).

`scripts/start-connector.sh` runs `npm install --omit=dev` in any MCP folder whose `package.json` has a non-empty `dependencies` block but is missing `node_modules` — first-boot is one-shot. The Dockerfile mirrors the same loop at image-build time. Bumping a dep *version* in `package.json` while `node_modules` already exists is a case the auto-install doesn't catch — run `npm install` in that folder yourself.

The `packages/` workspace shape is internal build machinery (dep hoisting via npm workspaces, TypeScript project references, dev-time `file:` linking with sibling repos). It is **not** a customer-facing delivery model — customers consume the OCI image, never the npm package. `packages/connector/package.json` stays `"private": true` permanently; the `bin`, `exports`, and `files` fields are retained because they're used by the `mcp-connector` CLI running *inside* the container and by the SDK re-export path for drop-in MCPs.

- **`packages/connector`** — the customer-side process. Config, MCP clients to local servers, WSS tunnel, dispatcher, supervisor (Type 1 child supervisor + drop-in spawner + Type 2/3 connector), inspector UI, CLI (`start` / `init` / `discover` / `register` / `version`). The connector + its `tsx` runtime + the `mcp/` tree are what go in the OCI image.
- **`packages/connector/src/sdk/`** — the surface customer-authored Type 1 servers import. `Tool` interface (incl. optional `envKeys?: string[]`) + `createMcpHttpServer({name, tools, port?, envKeys?, capabilities?})` factory. Re-exported from `@mcp-shim/connector/sdk`. The factory's HTTP server exposes `/envkeys` returning the de-duped union of every tool's `envKeys` (or the server-level list when `opts.envKeys` is set) — the supervisor queries it post-spawn so the connector can include it in `creds-request` frames. Server-level `envKeys` exists for creds-gated MCPs whose per-tool aggregate is empty at boot. `capabilities?: Record<string, unknown>` is the seam for protocol extensions that need custom capability groups on the MCP `initialize` response (e.g. `mcp/local/agentic-memory` per [docs/AGENTIC-MEMORY-MOCK.md](docs/AGENTIC-MEMORY-MOCK.md)); MCP's `ServerCapabilitiesSchema` is `.strip()`, so custom shapes MUST nest under `experimental` or `extensions` with a vendor namespace — the standard `tools`/`prompts`/`resources` presence keys stay auto-managed regardless. Drop-ins pick up an optional per-folder `capabilities.ts` (default-exported Record) via `loadCapabilities` in [`dropin-discovery.ts`](packages/connector/src/sdk/dropin-discovery.ts) — no yaml or code changes needed on the connector side. The factory also installs a compliance shim for empty-tools servers (creds-gated resting state) — see the inline block in [`packages/connector/src/sdk/http-server.ts`](packages/connector/src/sdk/http-server.ts) before removing it.
- **`packages/connector/src/sdk/dropin-runner.ts`** — synthesized child entrypoint for drop-in MCPs. Auto-discovers default-exported (or first-named-export-of-shape) `Tool` / `Prompt` / `Resource` objects from `${DROPIN_DIR}/{tools,prompts,resources}/*.{ts,js}` and calls `createMcpHttpServer({ name: ${DROPIN_NAME}, tools, prompts, resources })`. The three sibling categories are independently optional — a tools-only folder still works (today's shape). Discovery logic lives in [packages/connector/src/sdk/dropin-discovery.ts](packages/connector/src/sdk/dropin-discovery.ts) so it's unit-testable without spawning a real child process. One shared bin parameterized by env, not a per-folder file write.
- **`packages/connector/src/dropin.ts`** — `discoverDropins({ yamlNames })` scans `MCP_DROPIN_DIR`, returns synthesized Type 1 specs (`Extract<HttpServer> & { __dropin: true }`, assignable to `McpServerSpec`). Skips folders with a yaml entry or a hand-written `server.ts`.
- **`packages/connector/src/mcp-supervisor.ts`** — owns the lifecycle of every MCP child (Type 1 hand-written, Type 1 drop-in, Type 2 stdio, Type 2 http, Type 3 bundled). Exposes `register(specs) / startAll() / restart(name, reason) / stopAll()`, applies controller-supplied env via `applyControllerEnv(mcp, env, source, reason)`, tracks per-MCP `McpStatus` (process / credsSource / credsLastUpdated / restartCount / lastRestartReason / toolsCount / **source** / **mcpId**), and mutates the SHARED `servers: Map<string, McpServerConnection>` so the dispatcher and inspector pick up new connections without re-wiring. `McpStatus.source` is one of `"yaml"` / `"local"` / `"controller-config"` — L2 rescan filters by `"local"` so yaml + controller-config entries are immune. **Before editing, read the invariant blocks in the source file** — spawn-mutation (`__port` gating in `stopEntry`), auth resolution ordering, `NODE_PATH` computed-once for drop-in spawns, sync-vs-async auth cache keying. Pinned by `tests/mcp-supervisor/*.test.ts` and `tests/servers/connect-dispatch.test.ts`.
- **`packages/connector/src/tunnel/creds-coordinator.ts`** — fans out `creds-request` per MCP after register-ack, awaits the 5s soft-wait, applies responses via `supervisor.applyControllerEnv`. Late `creds-response` frames and `creds-update` push frames go through the same code path. Re-built per tunnel — the `pending: Map<requestId, …>` is pending IPC; a reply from a stale tunnel landing on a fresh one would be wrong. Exposed to the inspector via `mcpActions.reloadCreds(name)` for the per-MCP "Reload creds" button.
- **`packages/connector/src/servers/connect.ts`** — transport dispatch for outbound MCP connections. `stdio` specs go to `connectStdio`; `http` specs branch on the internal `__transportKind` marker (mirrors `__dropin` / `__port`): `"sse"` → `connectSse`, `"websocket"` → `connectWebSocket`, anything else → `connectHttp` (today's default for Type 1 spawned children, Type 2 author-supplied http endpoints, and `streamable-http` 3rd-party MCPs). The wire-side `McpConfigEntry.transport` is multi-valued (http / streamable-http / sse / websocket / stdio); the supervisor-side `McpServerSpec` stays two-valued (`http` / `stdio`) so the four HTTP-family wire variants collapse to the `http` spec with the SUB-transport on `__transportKind`. WebSocket caveat: the SDK's `WebSocketClientTransport` accepts only a URL — custom headers from the W-E3/W-E4 auth resolver are dropped with a warn; operators on a WebSocket upstream must embed auth in the URL (token query param, etc.). SSE forwards `spec.headers` through `requestInit.headers` on recurring POSTs same as `connectHttp`.
- **`packages/connector/src/tunnel/mcp-config-coordinator.ts`** — in-memory roster of controller-pushed 3rd-party MCPs (v1.1). Handles `mcp-config-snapshot` / `mcp-config-delta` / `mcp-config-resync` over the WS, translates `McpConfigEntry` → `SupervisedSpec`, reconciles via `supervisor.{hasEntry,registerOne,startOne,replaceSpec,unregister}`. Threads `mcpId` into `creds-request` so the controller can scope `(connectorId, mcpId)`. **Lifetime contract**: constructed once per process (in `boot()`), rebound per tunnel via `bind({send, log?})` — see the source file's LIFETIME block for the 2026-06-21 repro this prevents and why it differs from `creds-coordinator.ts`.
- **`packages/connector/src/tunnel/local-mcps-coordinator.ts`** — W-L2 controller-triggered `local-mcps-rescan` + inspector loopback `/mcp/rescan-local`. Re-runs `discoverDropins({yamlNames})` and reconciles against supervisor entries filtered to `source === "local"`. Same lifetime contract as `mcp-config-coordinator.ts`. Single-flight (a second click during a mid-flight scan returns an empty ack). `onMcpAdded` fans out a `creds-request` for rescan-added MCPs (they miss the boot-time fan-out).
- **`mcp/local/sample`** — Type 1 drop-in demo. `tools/now.ts`, `slow-echo.ts`, `uuid.ts`, `weather.ts` (weather.gov, US-only) + `prompts/weather-briefing.ts` + `resources/uuids-recent.ts`. No `server.ts`, no `package.json`, no yaml entry — picked up by the drop-in scanner.
- **`mcp/bundled/enterprise-knowledge`** — Type 3 config stub. Just a `.env.example`. Bundle *source* lives at [`bundles/enterprise-knowledge/`](bundles/enterprise-knowledge/); this folder exists so the customer's yaml can `dir: ../../mcp/bundled/enterprise-knowledge` and the standard per-entry `.env` loader picks up the customer's secrets without dragging the bundle's source into the runtime image.
- **`bundles/enterprise-knowledge`** — Type 3 source. Python package (`pyproject.toml`, `src/customer_ek_mcp/`, `migrations/`, `dev-launch.sh`). Read by `pip install` during the Dockerfile's bundle-build stage to populate `/opt/bundled-mcps/enterprise-knowledge/.venv/` in the runtime image; the source tree itself does *not* ship.

Type 1 servers use a stateful `StreamableHTTPServerTransport` with `randomUUID` session IDs. **Stateless mode does not work** with the SDK's HTTP transport — it requires a per-request transport instance. The factory in `sdk/http-server.ts` is the one place this is set up.

## Config files

Live config sits at the **root of the working directory** (repo root in dev; the customer's mount path — typically `/etc/mcp-connector/` — in production containers). Templates ship inside the connector's runtime image at `/app/packages/connector/*.example` so `mcp-connector init` (run inside the container, e.g. via `docker exec` or `fly ssh console`) can copy them out to the customer's mounted config volume. The two customer-facing delivery paths (derived image / volume mount — see [docs/deploy/DERIVED-IMAGE.md](docs/deploy/DERIVED-IMAGE.md) and [docs/deploy/VOLUME-MOUNT.md](docs/deploy/VOLUME-MOUNT.md)) both land config files at this path; the connector's boot code doesn't distinguish.

**Two modes for tunnel credentials, chosen by `CONNECTOR_CREDS_SOURCE`.** As of the env-to-db migration (`feature/env-to-db`, 2026-07-11) the connector supports two mutually-exclusive ways to load the controller URL, connector name, and bearer/OAuth secret needed to open the WSS tunnel:

- **`db` (default, recommended).** Tunnel identity + creds live in a `controllers` row in Postgres, sealed at rest with libsodium `crypto_secretbox_easy`. The 32-byte master key comes from `CONNECTOR_KEY_FILE` (typically a K8s / Docker secret mount). Operators manage the row via the inspector's Tunnel panel — no shell access needed; no process restart on rotation. **Empty DB at boot is a valid state**: the inspector renders "Configure tunnel", MCPs still spawn, no `TunnelClient` is constructed until an operator submits the form. See [.claude/plans/ENV-TO-DB.md](.claude/plans/ENV-TO-DB.md) for the full design; the routes live in [`src/inspector/tunnel-routes.ts`](packages/connector/src/inspector/tunnel-routes.ts).
- **`env` (legacy, being removed one release after `db` is proven stable).** Tunnel identity from `.env` + `connector.yaml`'s `tunnel:` block + `.connector-state.json`. Editing requires `vim .env` + restart. Preserved for one release cycle as a rollback lane; do NOT choose it for new deployments. The Step 14 follow-up PR (per [.claude/plans/ENV-TO-DB.md](.claude/plans/ENV-TO-DB.md)) will delete this branch entirely.

Dispatch is a single point in [`src/boot/lifecycle.ts`](packages/connector/src/boot/lifecycle.ts)'s `boot()`: `resolveCredsSource()` picks the flag value (default `"db"`) and calls `bootFromDb()` or `bootFromEnv()`. Do NOT add `if (credsSource === "db")` checks anywhere else — the two branches diverge cleanly at boot and everything downstream (dispatcher, supervisor, reconnect controller) is mode-agnostic.

**TDZ discipline inside `bootFromDb`.** Empty-DB boot returns from `bootFromDb` early, but the inspector's tunnel routes wire `dialTunnel` BEFORE that return — an operator submitting the Configure Tunnel modal invokes the closure while the function is still in its resting state. Any binding the closure (or `connectTunnelDb`) references MUST be declared ABOVE the `if (!row) return` early exit, else JavaScript's Temporal Dead Zone throws `Cannot access 'X' before initialization`. Pinned by [`tests/boot/lifecycle-tdz.test.ts`](packages/connector/tests/boot/lifecycle-tdz.test.ts), a source-level static analyzer that fails CI if a captured identifier moves back below the empty-DB return. To add a new binding for the paste flow: hoist it with `| undefined` at the top of `bootFromDb` and guard on read.

**One-shot env→db migration.** Operators upgrading from `env` mode have a stale `./.connector-state.json` holding the `registrationToken` the controller minted for their prior connector row. The db-mode boot doesn't auto-import it (D10 says no auto-import; D11 only deletes-after-success), so the first register-ack under `db` mode is rejected with `code: "organisation_has_connector"`. Recovery is [`scripts/migrate-registration-token.mjs`](scripts/migrate-registration-token.mjs) — reads the state file, seals + writes the token into `controllers.registration_token_ct`, then the operator clicks Reconnect. Step 14 (feature-flag removal, follow-up PR) will promote this to unconditional in-boot logic so the env→db path is friction-free. Do NOT add auto-import to `bootFromDb` before Step 14 — the deliberate friction is what forces operators to acknowledge the migration.

`CONTROLLER_URL` is the controller's HTTPS root; it's used for both the register API call and the WS tunnel dial. The YAML supports `${VAR}` and `${VAR:-default}` interpolation; unknown vars without a default throw with the variable name and YAML line so the customer can fix the right line. In Docker, set the same vars via container env — there is no `.env` inside the image; the customer mounts `connector.yaml` at `CONNECTOR_CONFIG` (default `/etc/mcp-connector/config.yaml`) and a writable volume for `.connector-state.json` (or accepts re-mint on every restart, which the controller's dup-name guard catches). The image bundles `mcp/` at `/app/mcp/` for Type 1 entries to spawn from and Type 2/3 `dir:` resolution.

### Per-entry env precedence (subtle)

The plan called this out as the highest-risk piece — read carefully before changing it. Four layers, lowest to highest precedence:

1. `dotenv/config` loads `./.env` (from CWD) once at startup → populates `process.env`.
2. `loadConfig` parses the yaml. Top-level `${VAR}` interpolation reads from `process.env` only. For each `mcp_servers[]` entry with `dir:`, the loader reads `<dir>/.env` into a **per-spec env map** (does **not** mutate `process.env`).
3. Inline `env:` map on the yaml entry (rare today; layered above `dir/.env`).
4. **Controller-supplied env from `creds-response` / `creds-update` frames.** The supervisor stores these in a per-MCP `controllerEnv` map and they win on conflict. See `mergeEnv` in [packages/connector/src/mcp-supervisor.ts](packages/connector/src/mcp-supervisor.ts) — the merge order is `process.env ⊕ spec.env (yaml inline + dir/.env) ⊕ controllerEnv`.

When the supervisor launches a Type 1 child / drop-in / Type 2 stdio / Type 3 bundled child, it passes the merged env. Cross-entry leakage is still impossible — child A's `API_TOKEN` (whether from `dir/.env` or controller-supplied) does not reach child B even if both declare the same key.

**Stdio entries go through the same merge.** The supervisor pre-builds merged env in `startEntry` and threads it through `connectServer(spec, env)` → `connectStdio(spec, env)` → `new StdioClientTransport({command, args, env})`. Same code path also decides restart-on-creds-rotation via `entry.child || entry.connection` — stdio entries leave `entry.child` undefined (the SDK owns the spawn), so the OR-clause is what catches them. Both invariants pinned by `tests/servers/connect-dispatch.test.ts` + `tests/mcp-supervisor/apply-controller-env.test.ts`.

Per-spawn env-source telemetry: every spawn logs `mcp spawn env-sources` with `controller: [...]` and `dirDotEnv: [...]` — watch `dirDotEnv` trend toward `[]` as customers move creds into the controller (D2 deprecation tracker).

Don't replace the per-spec env map with calls to `dotenv.config({path: ...})` in `loadConfig` — that mutates `process.env` and breaks the isolation guarantee. Don't widen the merge order without thinking through the cross-product with `applyControllerEnv` (which restarts the child with the new merged env).

### Env reading rule — empty string == not set

All `process.env` reads in `src/` go through [`src/env.ts`](packages/connector/src/env.ts) (`envString` / `envOptional` / `envNumber`). The whole-module rule: **an empty-string env var is treated as "not set"** — fall back to the documented default. An admin who writes `FOO=` (blank line) in `.env` expects "leave this unset"; `??` previously let `""` flow through (`Number("")=0`, `resolve("")=cwd`, pino throws on empty level). `envNumber` additionally throws an admin-actionable error when set to a non-numeric value (naming the var, the bad value, and the recovery), instead of silently coercing to `NaN`. The single deliberate exception is the YAML `${VAR}` interpolator in [`config.ts`](packages/connector/src/config.ts), which substitutes the literal empty string. For the `tunnel:` block specifically, empty strings pass zod validation (the schema `preprocess`es null → "" and accepts `controller_url: ""` / `name: ""`); enforcement lives in the boot-mode guards — `bootFromEnv` throws with an operator-actionable error if empty, `bootFromDb` logs an "ignored" WARN and continues. This is deliberate: it lets `${VAR:-}` defaults in the yaml survive the env→db migration without hard-failing boot before the WARN can fire.

Boot-time required-env preflight runs once in [`src/boot/require-env.ts`](packages/connector/src/boot/require-env.ts) (`requireEnv()`) before yaml load or auth resolution. It consolidates every missing required var into a single error block so an admin fixes them in one `.env` edit pass. The function branches on `resolveCredsSource(env)` at its start — under `db` mode it requires `POSTGRES_URL` + `CONNECTOR_KEY_FILE` only; under `env` mode it requires `CONNECTOR_CONFIG`, `CONTROLLER_URL`, `CONNECTOR_NAME`, plus the static-bearer-vs-OAuth2 posture. The auth-posture branch (env mode) is posture-aware: setting `OAUTH_CLIENT_ID` triggers a "you started OAuth2; here's what else you need" message rather than three separate "X is required" lines.

In production, each connector deployment is its own container — same yaml shape, just one container per `tunnel.name`.

## Reconnect semantics

- WS close does **not** kill the connector process. It transitions the inspector to `closed` state and stops timers.
- Auto-reconnect is **on by default** (`policy.reconnect.enabled: true`). On an unexpected close the connector schedules a redial via `scheduleAutoReconnect()` in `index.ts` and the inspector enters a fourth `reconnecting` state showing "reconnecting in N.Ns · attempt K". A successful register-ack resets the attempt counter. SIGTERM/SIGINT and a manual click on the inspector's Reconnect button both cancel any pending auto-reconnect timer (`cancelAutoReconnect()`) so a manual click fires immediately.
- Auto-reconnect is **suppressed when the controller rejects the register frame** (e.g. `unknown_registration_token` after the controller's connector row was deleted or the DB was reset). The connector sets a `registrationRejected` flag in the `register-ack` handler; the next `onclose` logs `auto-reconnect suppressed` and stays in `closed` instead of looping forever on a token the controller already said it doesn't recognize. The operator's recovery is to clear `.connector-state.json` and click Reconnect — the manual reconnect path clears the flag, so the next attempt re-mints a fresh row.
- Backoff is computed by `nextReconnectDelay(attempt, policy)` at the bottom of `index.ts`. Today it returns a fixed delay (= `initial_backoff_ms`); swapping in a real backoff curve (full jitter / decorrelated jitter / etc.) is a localized change that doesn't touch the rest of the loop.
- Set `policy.reconnect.enabled: false` to opt out — useful in deployed containers where the orchestrator (Fargate / Container Apps / GKE) is the supervisor and you want the inspector to surface a hard `closed` state. With auto-reconnect disabled, behavior matches the original PoC: `closed` until a manual click or SIGHUP.
- Reconnect re-reads the YAML. `sameMcpServers()` in `index.ts` compares name + transport + endpoint + command + dir + env across the prior and new lists. If anything in `mcp_servers` changed, the connector logs a warning and uses the prior list (live MCP server reconnect is out of scope — the spawned children, the stdio transport, the per-entry env are all wired at boot). `policy` changes take effect.
- Controller-side restarts (e.g. ngrok tunnel cycling) are recovered automatically; the inspector pill flips through closed → reconnecting → connecting → open as the controller comes back. No action required.

## Process lifecycle gotcha

`scripts/start-connector.sh` boots one connector process; the connector itself spawns Type 1 children. The script's pre-cleanup uses `pgrep -f 'scripts/start-connector\.sh'` and skips its own PID — do NOT replace this with `pkill -f` patterns that match `node dist/index.js`, because that catches unrelated node processes and does not catch orphan wrapper shells. The pgrep pattern must match the script's filename — if you rename the file, update the pattern in the same change or the pre-cleanup silently misses prior runs.

The connector's SIGTERM handler calls `supervisor.stopAll()`, which sends SIGTERM to every Type 1 / drop-in / Type 2 stdio / Type 3 child it spawned (with a SIGKILL fallback after timeout). Combined with the script's `trap cleanup EXIT INT TERM` (which `kill 0`s the process group), Ctrl-C cleans up the whole tree.

## Distribution

Primary shape is a signed multi-arch OCI image. Build:

```bash
./scripts/build-image.sh                                # local single-arch
IMAGE=registry/mcp-connector:0.1.0 PUSH=1 ./scripts/build-image.sh  # multi-arch + push
```

[packages/connector/Dockerfile](packages/connector/Dockerfile) is multi-stage; runtime image carries the connector's `dist/` + `public/` + production `node_modules` (incl. `tsx`) + the `mcp/` tree + Python venvs for Type 3 bundles under `/opt/bundled-mcps/<name>/`. The `mcp/` tree is bundled because Type 1 entries in `connector.yaml` reference them via `dir:` and the spawner must be able to `tsx <dir>/server.ts`.

Customers who want their own Type 1 MCPs extend the image via one of two first-class delivery paths, both landing at the same `MCP_DROPIN_DIR` mount point (`/var/lib/mcp-connector/customer-mcps/`) and the same discovery code in [`src/dropin.ts`](packages/connector/src/dropin.ts) — no branching in the connector:

- **Derived image** — `FROM twilio/mcp-connector:1.0` + `COPY ./my-mcps/ /var/lib/mcp-connector/customer-mcps/`, build their own image. Enterprise-friendly, image-signing shops, prod runbooks. Walkthrough: [docs/deploy/DERIVED-IMAGE.md](docs/deploy/DERIVED-IMAGE.md).
- **Volume mount** — bind-mount a host / K8s PVC / Fly volume / EFS at the same path. Faster dev loop, unlocks the W-L2 controller-triggered "Refresh local MCPs" hot-rescan feature. Walkthrough: [docs/deploy/VOLUME-MOUNT.md](docs/deploy/VOLUME-MOUNT.md).

There is no "customer imports the npm package into their own Node service" path — the connector is a daemon, not a library. `packages/connector/package.json` stays `"private": true` permanently (see the Workspaces section above).

The build stage runs `npm install --omit=dev --no-package-lock` inside any `mcp/local/*/` or `mcp/bundled/*/` that has a non-empty `dependencies` block. No in-repo MCP carries Node deps today, so the loop is a no-op — it stays in the Dockerfile because a future bundle (or a customer-extended image) might add one. Folders whose `package.json` only declares the MCP's identity (sample shipped, crm dev-only) skip cleanly — `zod` and `@mcp-shim/connector/sdk` resolve up to `/app/node_modules` from the hoisted workspace install. Folders without any `package.json` at all (enterprise-knowledge — no Node code in this repo) skip too.

[scripts/build-image.sh](scripts/build-image.sh) defaults to `linux/amd64,linux/arm64` (Graviton + ARM Macs). Per-cloud guides at [docs/deploy/](docs/deploy/) (AWS Fargate, Azure Container Apps, GCP GKE, Fly.io) document the foot-guns of each platform — most importantly, **don't put a load balancer in front of the connector** (nothing inbound) and **don't use Cloud Run / App Service / Fly `auto_stop_machines` / scale-to-zero anything** (kills the WSS).

The runtime `ENTRYPOINT` is a shell script at [`packages/connector/entrypoint.sh`](packages/connector/entrypoint.sh). If `$CONNECTOR_KEY_B64` is set (Fly.io, Azure Container Apps, or any secret-store-as-env platform), it base64-decodes the value into `$CONNECTOR_KEY_FILE` (default `/etc/mcp-connector/connector.key`) with mode 0400, then execs `node dist/index.js "$@"`. If `$CONNECTOR_KEY_B64` is unset (docker-compose, K8s Secret volume, hand-provisioned VM), it's a strict no-op — the mounted file is used as-is. Pinned by [`packages/connector/tests/deploy/entrypoint.test.ts`](packages/connector/tests/deploy/entrypoint.test.ts). Don't add validation logic in the entrypoint (key-length, path writability, etc.) — that's the connector's env-loading path's job; keep the entrypoint minimal.

## Deployment scaffolding

Three complementary shapes ship alongside the OCI image so a customer can choose what fits their infrastructure — see [architectural-plans/DEPLOYMENT-SCRIPTS.md](architectural-plans/DEPLOYMENT-SCRIPTS.md) for the rationale:

- **`docker-compose.prod.yml`** at repo root — single-VM shape, `docker compose up -d` to a running connector. Ships with a sibling Postgres for db mode. **The `127.0.0.1:9090:9090` port binding is load-bearing** — binding the inspector to `0.0.0.0` leaks the bcrypt-protected webhook URL. Pinned by [`packages/connector/tests/compose/compose-lint.test.ts`](packages/connector/tests/compose/compose-lint.test.ts).
- **`mcp-connector deploy init --target {fargate|gke|aca|compose|fly|fly-mock}`** — CLI verb that renders the target's manifests with `{{NAME}}` / `{{CONTROLLER_URL}}` substituted from flags (or interactive prompts). Split into `scaffoldTo(target, vars, outDir)` (pure — testable) and `runDeployInit(argv)` (CLI wrapper with `--yes` non-interactive mode). Templates in [`src/deploy/templates.ts`](packages/connector/src/deploy/templates.ts). `fly` emits `fly.toml` + `secrets-hint.sh` (connector); `fly-mock` emits `fly.toml` + `Dockerfile` for the private demo backend (default outDir `./mock/customers` — output lives in-tree with the mock source it packages). The `fly` target's fly.toml deliberately has NO `[[services]]` / `[http_service]` / `auto_stop_machines` — pinned by [`packages/connector/tests/deploy/scaffold.test.ts`](packages/connector/tests/deploy/scaffold.test.ts) via line-start regex so a comment mention of the invariants is fine but active TOML syntax fails the build.
- **Reference bundles** — [`deploy/fly/`](deploy/fly/README.md) ships hand-authored `fly.toml.example` + a full operator runbook covering Fly Postgres attach quirks, master-key rotation, and the graduation path to managed Postgres. Complements the scaffold-generated files; humans read the runbook, the scaffold generates the paste-ready copy.
- **IaC modules** — [`deploy/terraform/aws-fargate/`](deploy/terraform/aws-fargate/README.md) and [`deploy/helm/mcp-connector/`](deploy/helm/mcp-connector/README.md). Terraform module owns log group + Secrets Manager slot (customer populates value out-of-band — **never lands in tfstate**) + task def + service. Helm chart uses `required` for `connector.name` / `connector.controllerUrl` so `helm install` fails loudly. Both hardcode `replicas: 1` / `desired_count: 1` — dup-name guard, don't template that.

`mcp-connector deploy apply --target fly` pairs with `deploy init` to give operators a uniform CLI surface across "generate" (init) and "execute" (apply). Under the hood, `apply` spawns Fly's CLI directly — five commands with idempotency guards (see [`src/deploy/apply.ts`](packages/connector/src/deploy/apply.ts) for the flow). No bash script is emitted; `deploy init --target fly` writes only `fly.toml` and the CLI verb does everything else. Other targets return "not yet implemented" from `apply` today; operators use the cloud's native tool (`aws` / `kubectl` / `az` / `docker compose`) per the init readmeAppendix.

`mcp-connector doctor` complements all three: run before boot to catch missing env / bad key file / unreachable Postgres. It is intentionally decoupled from `deploy init` — doctor is standalone and callable from any orchestration wrapper.
