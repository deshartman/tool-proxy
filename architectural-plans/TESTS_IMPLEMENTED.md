# Tests Implemented — Running Inventory

> **What this is.** A flat inventory of every defensive test that has *landed*
> in `packages/connector/tests/`. One row per individual `it(…)` case. New
> entries go at the **top** so the most recent work is at the front.
>
> **What this is not.** This is not the planning doc — proposals, open
> surfaces, and the boot lifecycle map live in
> [TEST-SUITE.md](TEST-SUITE.md). When a test ships:
>
> 1. Add a row to the table here.
> 2. Flip the catalog row in `TEST-SUITE.md` from `failing` → `passing`.
> 3. If the test covers an env-var surface from the env coverage map in
>    `TEST-SUITE.md`, mark that map row `landed`.
>
> **Env conventions for tests below.** All tests that depend on `process.env`
> use **`vi.stubEnv(name, value)`** with `vi.unstubAllEnvs()` in `afterEach`,
> per the `TEST-SUITE.md` "Env-var testing — preferred approach" section.
> No test reads from a `.env` file. No test sets `process.env.X = "..."`
> directly. If a test below is missing a `vi.stubEnv` row in the "Env state"
> column, it's because the surface it covers takes an injected env map and
> doesn't read `process.env` at all (preferred shape; `resolveAuth(token, env)`
> is the canonical example).

## How to add a row

Run the tests; copy the `it(…)` description verbatim:

```bash
cd packages/connector && npm test
```

Then prepend a row to the table above. Required fields:

- **#** — monotonic. `# of last row + 1`.
- **Date** — today's date in `YYYY-MM-DD`.
- **Test file** — relative to repo root, in backticks.
- **`it(…)` description** — exact text from the test source.
- **Source under test** — the `src/` file the test exercises (one file per
  row even when a test indirectly touches more — pick the *primary* one).
- **Env state** — if the test uses `vi.stubEnv`, list the vars and values
  ("default unset" if explicitly stubbed empty). If the surface accepts
  an injected env arg and the test passes a literal map, write `none —
  injected via arg`. Otherwise `none`.
- **Invariant pinned** — one sentence answering "what would break if this
  test were deleted and the bug it pins came back?".
