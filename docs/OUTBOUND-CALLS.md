# OUTBOUND-CALLS — enterprise-triggers-outbound-call walkthrough

> **Status:** demo — `examples/demos/outbound-demo/` is reference material (not auto-loaded); the mechanism it exercises (v1.4 controller-call) is shipped.
> **Repo location:** `examples/demos/outbound-demo/` — self-contained: MCP tool, capability declaration, driver script, and config all in one folder.

This document walks through the flow that lets an enterprise's own system trigger a real outbound Twilio call or SMS through the tunnel, from the connector side. It's the connector-side companion to the controller's own action-registry contract (`docs/CONTROLLER-ACTIONS.md` in the controller repo) — read that doc for what happens after the frame lands on the controller; this doc covers everything up to and including sending the frame.

## 1. The flow, end to end

```
enterprise's own system
  -> examples/demos/outbound-demo/run-outbound.sh    (plays the role of "the enterprise's own system")
  -> POST /tool/call on the connector's inspector     ({server, tool, args})
  -> outbound-demo's invoke tool
  -> callControllerApi("outbound.place_call" | "outbound.send_message", params, {timeoutMs: 30000})
  -> POST /internal/controller-api/call on the connector's inspector
  -> ControllerApiCoordinator.call() -> controller-call frame over the tunnel WS
  -> controller's ControllerActionRegistry.invoke()
  -> registerOutboundPlaceCallAction / registerOutboundSendMessageAction
  -> Twilio Voice / Messaging API
  -> result flows back down the same path as controller-call-response -> tool result -> HTTP response
```

Every hop after the driver script is generic mechanism, not outbound-specific — see `docs/MCP-PROTOCOL.md` §"v1.4 — Controller API calls (Twilio-bundled only)" for the wire contract (`ControllerCallFrame` / `ControllerCallResponseFrame`) that everything below rides on.

## 2. Why a driver script, not a direct call

A production enterprise integration would call this from whatever internal system needs to trigger the outbound action — not from a standalone script. The demo's driver script exists to prove the connector-side mechanism works without needing that enterprise system built. It talks to the connector's inspector loopback (`/tool/call`), the same route an operator's inspector-UI click uses to invoke any tool — not a raw MCP client against the bundled MCP's own HTTP endpoint, because that endpoint's port is an internal implementation detail (auto-probed at boot, never surfaced externally) and isn't meant to be reached directly from outside the connector process tree.

## 3. Params and result

Both `outbound.place_call` and `outbound.send_message` take the identical shape (controller-owned contract; the connector treats it as opaque):

```ts
{
  agentId: string;
  channelId: string;
  to: string;              // E.164
  callContext?: Record<string, string>;
  idempotencyKey: string;  // generated by the calling tool, not the caller
}

// result
outbound.place_call    -> { callSid: string }
outbound.send_message  -> { providerId?: string }
```

`agentId` / `channelId` must already exist in the controller's own data — a real Agent and Channel, with the Agent bound to a supervisor procedure. An unknown pair fails with `agent_not_found` / `channel_not_found` / `no_supervisor`, mapped to the connector-visible `controller_error` code (see §5).

`idempotencyKey` matters here specifically because dialing or texting twice is a real side effect, not a no-op — the demo tool mints a fresh one (`randomUUID()`) per call rather than accepting it as input, since the whole point of a dedup key is that the *caller* who might retry owns it, not the entity being called.

## 4. Running it

Full setup (activation, `tool_timeout_ms` prerequisite, config format) lives in [`examples/demos/outbound-demo/README.md`](../examples/demos/outbound-demo/README.md) — the short version:

```bash
# 1. Activate the drop-in (author-gated to "twilio" — see the README for why
#    this can't go through the usual customer-mcps/ dev path).
cp -r examples/demos/outbound-demo bundled-mcps/outbound-demo

# 2. Raise connector.yaml's policy.tool_timeout_ms to 35000+ (see §6) and
#    boot the connector.
./scripts/start-connector.sh

# 3. Configure and run the driver — config file (below) or CLI flags,
#    see examples/demos/outbound-demo/README.md for both.
cd examples/demos/outbound-demo
cp config.example.json config.json
# edit: action ("place_call" | "send_message"), to, agentId, channelId
./run-outbound.sh
```

The script prints a summary and prompts `Proceed? [y/N]` before sending anything — declining exits cleanly with no request made.

**This places/sends a real call or message.** There is no dry-run or sandbox mode; the controller action calls the same Twilio-backed core the controller's own `POST /api/outbound/calls` / `POST /api/outbound/messages` routes call.

## 5. Error codes

Everything after `unknown_action` / `not_authorized` is controller-owned and passed through opaquely (`error: { code, message }`); `timeout` is the one connector-side code, raised when no `controller-call-response` lands within the timeout window:

| Code | Where it comes from |
|---|---|
| `timeout` | Connector-side only — the controller didn't reply in time. |
| `unknown_action` | Controller has no handler for the requested action. |
| `not_authorized` | Either the connector's local gate (calling MCP isn't Twilio-authored) or the controller's own session check. |
| `cross_account` | Controller: the target Agent/Channel doesn't belong to this tunnel's account. |
| `no_supervisor` | Controller: the target Agent has no supervisor procedure bound. |
| `invalid_params` | Controller: `params` failed the action's own schema validation. |
| `controller_error` | Controller: everything else — a richer taxonomy exists on the controller's own HTTP routes, but the tunnel surface only distinguishes the codes above. |

## 6. The `tool_timeout_ms` gotcha

`outbound.place_call` / `outbound.send_message` run a synchronous LLM turn on the controller side and need `callControllerApi`'s 30-second timeout window to have a chance to complete. But the demo script reaches the tool through the connector's inspector `/tool/call` route, which wraps every MCP tool call in the connector's own outer `policy.tool_timeout_ms` — **5000ms by default** (`connector/src/config.ts`). That outer timeout fires first regardless of how long the inner controller round-trip is actually taking, so without raising it, the demo fails with a generic timeout before the outbound action ever gets a fair chance to answer.

Raise it in `connector.yaml` before running the demo:

```yaml
policy:
  tool_timeout_ms: 35000
```

This is a deliberate manual step, not a change to the shipped default — the default protects every other tool call on every other MCP from hanging for 35 seconds on a genuine failure; only this one demo needs the wider window.
